# 本轮修改记录：stop 可靠性审核修复

## 1. 修改背景

本轮根据代码审核结果处理三项会影响可靠关闭语义的问题：

1. `PROCESSING` 任务在普通异常释放和超时回收时始终回到 `PENDING`，缺少重试硬上限，持续失败任务可能永久占用 worker。
2. 电解槽快照单条 fallback 没有遵循 `ASYNC/DUAL_WRITE/SYNC` 模式，`ASYNC` 下可能绕过可靠命令表直接写投影。
3. start 后到补偿的单条关闭路径会吞掉 side effect outbox 创建异常，可能提交 `alarm_endTime + route CLOSED + APPLIED`，但永久丢失后续副作用。

审核中的另外两项风险本轮只登记，不改运行逻辑：

- 重复 stop 在并发认领期间是否始终以最新 `stop_time` 完成关闭，需要继续增加真实并发门禁。
- side effect worker 多实例认领隔离尚未完成，生产多实例前必须专项治理。

## 2. 修改范围

- `AlarmStopWorkerProperties`
- `AlarmStopEventMapper`、`AlarmStopEventMapper.xml`
- `AlarmStopEventClaimService`
- `AlarmElectrolyticCellServiceImpl`
- `AlarmStopEventService`
- 对应 focused 单测和 XML 契约测试

## 3. 运行行为变化

### 3.1 PROCESSING 异常释放

- 普通异常释放和超时回收都会增加 `retry_count`。
- `retry_count + 1 >= safeMaxRetry()` 时转 `FAILED`，否则延迟回到 `PENDING`。
- `safeMaxRetry()` 运行时钳制为 `1-100`，避免 Nacos 配置错误造成无限重试或极端热循环。

### 3.2 电解槽快照单条 fallback

- `ASYNC`：只写可靠快照命令，不再直接写 ectype 投影。
- `DUAL_WRITE`：同时写可靠快照命令和 ectype 投影。
- `SYNC`：保持只写 ectype 投影。

单条 fallback 继续复用已经准备好的 alarm 上下文，不重新分配 `alarm_id/shardSuffix`。

### 3.3 start 后到补偿

- 单条补偿仍按 `alarm_endTime -> route CLOSED -> side effect outbox -> APPLIED` 完成。
- outbox 创建失败会向外抛出，让外层 start 事务整体回滚并交给 MQ 重投或后续补偿。
- 远程 side effect 执行仍保持异步，远程失败只影响 outbox 事件状态，不阻塞核心闭环。

## 4. 兼容性边界

- 不修改 MQ queue、消息体、ack/nack 语义和公开接口。
- 不修改 Redis key。
- 不新增数据库字段，不要求额外执行迁移脚本。
- 不修改 push payload。

## 5. 风险与回滚

- `maxRetry` 过小会让短时数据库故障更快转 `FAILED`；灰度保留默认 `5`，并观察 `PROCESSING_TIMEOUT` 和普通异常分布。
- `ASYNC` 快照模式依赖快照命令 worker 正常运行；灰度必须检查命令表最终无持续 `PENDING/PROCESSING/FAILED`。
- outbox 创建失败现在会回滚 start 后到补偿，短时故障下可能增加 MQ 重投，但不会再静默形成半完成状态。

回滚时可回退本轮提交；数据库结构没有变化。
