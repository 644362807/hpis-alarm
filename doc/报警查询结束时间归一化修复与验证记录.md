# 报警查询结束时间归一化修复与验证记录

## 1. 变更目的

本次变更解决报警读接口在未传时间、只传开始时间或传入未来结束时间时，ShardingSphere 无法获得有效时间上界，进而广播到预注册未来物理表的问题。

处理范围只限于查询入口，不修改报警写入、MQ、Redis、推送、`actualDataNodes` 或分片算法的全局兜底行为。

## 2. 时间规则

每个请求只生成一次 `queryNow`，然后生成实际查询范围：

| 请求参数 | 实际开始时间 | 实际结束时间 |
| --- | --- | --- |
| 开始、结束时间均为空 | 空 | `queryNow` |
| 只有开始时间 | 原开始时间 | `queryNow` |
| 只有历史结束时间 | 空 | 原结束时间 |
| 结束时间晚于当前时间 | 原开始时间 | `queryNow` |
| 开始、结束时间均有效 | 原开始时间 | 原结束时间 |

SQL 保持开放区间语义：

```sql
alarm_beginTime > :startTime
alarm_beginTime < :effectiveEndTime
```

调用方传入的查询对象不被修改；统计接口使用参数副本，避免同一个对象在多次调用中残留时间或状态条件。

## 3. 生效接口

本次归一化只接入以下接口：

- `POST /alarm/list`
- `POST /alarm/countAlarm`
- `POST /alarm/alarmTimeCountByMonth`
- `POST /alarm/alarmModeCount`
- `POST /alarm/alarmCountByTime`
- `POST /alarm/AlarmOfDay`

通过网关访问时，若网关路由保留服务前缀，对应地址为 `/alarm/alarm/...`。

导出控制器当前仍未启用。本次只修正了 Mapper 中未来恢复导出时应遵守的结束时间条件，不恢复导出功能。

## 4. 分片路由约束

ShardingSphere 4.1.1 需要从 SQL 中识别 `alarm_beginTime` 的范围条件。结束时间条件必须保持分片列在比较符左侧：

```xml
<if test="endTime != null">
    and alarm_beginTime &lt; #{endTime}
</if>
```

不要改回以下反向写法：

```xml
and #{endTime} &gt; alarm_beginTime
```

两者在 MySQL 中逻辑等价，但反向写法可能无法被当前 ShardingSphere 版本识别为分片上界，导致查询广播到预注册的未来月份或未来物理片。

`alarmCountByTime` 还包含电解槽报警的二级统计查询。该查询必须复用主查询标准化后的参数，确保主查询和二级查询具有相同的开始时间、结束时间及租户范围。

## 5. 代码位置

- `AlarmQueryTimeNormalizer`：纯 Java 时间归一化，不依赖 Spring 上下文。
- `AlarmServiceImpl`：在限定接口进入 Mapper 前应用统一规则。
- `AlarmMapper.xml`：统一使用分片列在左侧的结束时间条件。
- `AlarmElectrolyticCellMapper.xml`：为 `currentAlarmCount` 二级查询补充时间和租户条件。

没有修改 `AlarmTimeCapacityShardingAlgorithm` 的广播兜底。其他未接入的查询接口保持原有行为。

## 8. 回归检查清单

后续修改相关查询时至少确认：

1. 每个请求只生成一次 `queryNow`。
2. 空结束时间和未来结束时间最终都转换为 `alarm_beginTime < queryNow`。
3. 分片列位于比较符左侧。
4. 主查询和二级查询复用相同的有效时间范围。
5. 不通过分片算法全局兜底扩大本次接口范围。
6. 历史结束时间不被错误扩展到当天 23:59:59.999。
