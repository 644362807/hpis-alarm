# 报警电解槽快照异步拆分实施计划

## 背景

Phase A 的 `MIXED_ALTERNATE 20000 MQ/min x 10min` 已证明核心关闭链路接近目标，但同步写入 `alarm_electrolytic_cell_ectype` 仍出现 MySQL deadlock。该表表达的是当前点位快照，不是报警历史事实，允许短暂最终一致。

本阶段只拆分当前点位快照。`alarm` 主表、`alarm_electrolytic_cell` 历史扩展表、route、stop event、MQ ack 和 Redis key 保持不变。

## 分支

从 Phase A 检查点提交创建：

```text
test/alarm-ec-snapshot-outbox
```

当前工作树包含未提交的 Phase A 和更早阶段改动。建立 Phase B 分支前必须先确认 Phase A 检查点提交边界，不能把 `target/`、`logs/` 或本地压测产物纳入提交。

## 数据模型

新增可靠命令表 `alarm_electrolytic_cell_snapshot_command`：

| 字段 | 用途 |
| --- | --- |
| `point_hash varchar(64)` | 稳定点位主键，不使用自增尾部热点 |
| `command_type varchar(16)` | `ACTIVE` 或 `DELETED` |
| `alarm_id varchar(64)` | 当前命令关联报警 |
| `alarm_begin_time datetime` | 当前报警开始时间 |
| `payload_json text` | 生成快照投影所需字段 |
| `command_status varchar(16)` | `PENDING / PROCESSING / DONE / FAILED` |
| `lock_token varchar(64)` | 区分认领批次和执行线程 |
| `locked_at datetime` | worker 超时回收 |
| `available_time datetime` | 延迟重试 |
| `version bigint` | 防止旧线程覆盖新命令 |
| `retry_count int` | 有限重试计数 |
| `last_error varchar(1000)` | 失败摘要 |
| `created_time datetime` | 创建时间 |
| `updated_time datetime` | 更新时间 |

索引：

```sql
primary key (point_hash)
index idx_ec_snapshot_claim(command_status, available_time, updated_time, point_hash)
index idx_ec_snapshot_processing_timeout(command_status, locked_at)
```

点位键固定由以下字段规范化后生成：

```text
irmsSn + sequenceId + rowIndex + grooveNumber + observationPlace + subdivideNumber
```

## 核心事务改造

### Start

1. `alarm_electrolytic_cell` 历史扩展表继续在 start 核心事务内批量写入。
2. 不再同步 upsert `alarm_electrolytic_cell_ectype`。
3. 在同一核心事务内按 `point_hash` upsert `ACTIVE` 快照命令。
4. 新 start 覆盖旧命令时，更新 `alarm_id`、payload 和 `version=version+1`，状态回到 `PENDING`。

### Stop

1. 核心报警关闭和 route 关闭语义不变。
2. 仅当快照命令当前 `alarm_id` 与 stop 对应 `alarm_id` 一致时，upsert `DELETED` 命令。
3. 旧 stop 晚到时不得删除新 start 已覆盖的点位。

## Worker

- 新增独立 snapshot executor，不复用 MQ consumer、stop worker 或 push 线程池。
- 默认 `workerThreads=2`、`claimBatchSize=100`、`maxInFlightBatches=2`。
- 原子认领：`PENDING -> PROCESSING`，写入 `lock_token` 和 `locked_at`。
- 按 `point_hash` 稳定排序处理，降低锁顺序反转风险。
- 单次 `IN`、multi-values SQL 和 JDBC batch 最大 `100`，仍受全局 `500` 硬边界保护。
- `ACTIVE` 命令 upsert 快照投影；`DELETED` 命令仅在 `alarm_id` 匹配时删除投影。
- 提交必须校验 `point_hash + lock_token + version`；旧线程不得覆盖新状态。
- `PROCESSING` 超时后回收到延迟 `PENDING`。
- 超过重试上限进入 `FAILED` 并报警，不允许热循环。

## 灰度开关

```yaml
alarm:
  batch:
    electrolyticSnapshotMode: SYNC
  ec-snapshot-worker:
    dispatchEnabled: false
    workerThreads: 2
    claimBatchSize: 100
    maxInFlightBatches: 2
    processingTimeoutMs: 60000
    retryDelayMs: 5000
```

灰度步骤：

1. 先部署新增表和 worker，保持 `SYNC`。
2. 开启 worker，但不产生异步命令，确认空跑稳定。
3. 切换 `DUAL_WRITE`，同步投影和命令表同时写入，核对最终快照一致性。
4. 切换 `ASYNC`，移除 start 核心事务中的同步快照 upsert。
5. 出现异常时切回 `SYNC`，新增命令表保留，不做破坏性回滚。

## Profiling

新增低频聚合指标：

- start：历史扩展表、命令 upsert、主表、route、补偿处理耗时。
- snapshot worker：claim P50/P95、批次大小 P50/P95、投影 upsert/delete 耗时、重试数、失败数。
- stop worker：claim P50/P95、route missing 数量和最长等待时间。
- side effect：pending slope、最长等待时间。
- 日志：生产压测关闭 MyBatis DEBUG，避免日志 IO 干扰吞吐。

## 单测

- 同点位连续 start：最终快照使用最新报警。
- start 后 stop：最终删除快照。
- 旧 stop 晚到：不得删除新 start 快照。
- 重复命令：保持幂等。
- worker 超时：`PROCESSING` 可回收。
- token 冲突：旧 worker 更新失败。
- version 冲突：旧版本不得覆盖新命令。
- 单次 SQL：不超过 `100`，全局不超过 `500`。

## 压测门禁

重新执行：

1. `GENERAL_ALTERNATE 20000 MQ`
2. `ELECTROLYTIC_ALTERNATE 20000 MQ`
3. `MIXED_ALTERNATE 20000 MQ`
4. `MIXED_ALTERNATE 20000 MQ/min x 10min`
5. `MIXED_ALTERNATE 50000 / 100000 MQ`
6. 独立 `750000 PENDING`

验收：

- mixed 持续吞吐 `>= 333.33 MQ/s`。
- 核心关闭吞吐 `>= 166.67 alarm/s`。
- `20000 MQ` 核心闭环 `<= 120s`。
- queue 和 pending 不线性增长。
- stop event 终态无 `PENDING/PROCESSING/FAILED`。
- 快照命令终态无持续 `PENDING/PROCESSING/FAILED`。
- ACTIVE 点位最终与最新报警一致。
- 已 stop 且未被新报警替代的点位最终不存在快照。
- 同步 ectype 快照 deadlock、逐条 fallback、持续 requeue 均为 `0`。

只有通过上述门禁，才能进入生产化候选评审。
