# 报警 2w MQ 每分钟 Phase B 后续拆分计划

## 结论

Phase B 已将电解槽当前点位快照从 start 核心事务拆分为可靠异步投影。短时真实 MQ + MySQL 回归中，同步快照 deadlock、逐条 fallback 和持续 requeue 均为 `0`。

下一阶段只选择一个主任务：**降低 route 可见性竞争与无效重试**。

不在本阶段增加 MQ consumer，不放大 SQL 批次，不拆 side effect。单次 `IN`、multi-values `INSERT` 和 JDBC batch 继续保持最大 `500` 条。

## 选择原因

- `MIXED_ALTERNATE 20000 MQ` 短时回归已经满足 `<= 120s`，说明 listener、start 核心写入和 stop worker 具备基本吞吐能力。
- 持续输入下 RabbitMQ `ready` 和 stop event `PENDING` 没有线性增长，说明不是简单的 worker 数量不足。
- 仍可观测到 `ROUTE_MISSING_RETRY`。这表示 stop event 已经可认领，但 start route 尚未提交或尚不可见，造成无效 claim、回滚和延迟重试。
- verifier 的完整 count 会额外占用 MySQL。后续必须把轻量热采样和终态一致性 SQL 分开，避免观测负载掩盖真实瓶颈。

## 最小修改范围

### 1. Profiling 补齐

- 记录 stop event 从 `created_time` 到首次 claim 的等待时间直方图，输出 claim wait `P50/P95`。
- 记录每轮 claim 实际批次大小 `P50/P95`。
- 记录 `ROUTE_MISSING_RETRY` 的批次数、涉及行数、最长等待时间。
- 将 route 查询、业务表关闭、route 关闭、mark applied 分段耗时写入低频聚合指标。

### 2. route 可见性窗口实验

- 保持 `claimBatchSize=200`、`workerThreads=4`。
- 仅调整 `alarm.stop-worker.initialAvailableDelayMs`：`200 / 300 / 500ms`。
- 每档运行 `MIXED_ALTERNATE 20000 MQ/min x 10min`。
- 以 `ROUTE_MISSING_RETRY` 最少且闭环吞吐不下降的档位作为候选值。

### 3. verifier 负载隔离

- 热采样只读取 MQ 状态、stop event 按状态的轻量聚合和低频 route missing 指标。
- 完整主表 count、扩展表一致性、route 一致性只在终态执行。
- 单独记录 verifier SQL 耗时，报告中区分业务闭环和终态校验耗时。

## 验收

- `200000 MQ / 10min` 持续输入期间 queue 和 pending 不线性增长。
- 终态 `PENDING=0`、`PROCESSING=0`、`FAILED=0`。
- `ROUTE_MISSING_RETRY` 相比 Phase B 基线明显下降。
- 严格发送吞吐 `>= 333.33 MQ/s`。
- 核心关闭吞吐 `>= 166.67 alarm/s`。
- 主表、扩展表、route 和快照投影最终一致。
- MyBatis DEBUG 在性能环境关闭。

## 边界

该任务必须在独立测试分支执行。只有严格门禁通过，才进入生产化候选评审。未通过时继续生成拆分分析，不合并 `main`。
