# 报警时间容量分片设计说明

## 设计目标

原规则按 `alarm_id % 5` 固定分到 `alarm_0..4`、`alarm_handle_0..4`、`alarm_electrolytic_cell_0..4`。该方式无法按时间治理历史数据，也无法在单月数据暴涨时继续切分。

当前方案改为时间 + 容量分片：

- 按 `alarm_beginTime` 先定位月份。
- 单月内按容量切 slice。
- 物理表后缀为 `yyyyMM_nn`，例如 `alarm_202511_00`。
- 三张绑定表使用同一 `table_suffix`。

## 物理表规则

| 逻辑表 | 物理表格式 | 示例 |
| --- | --- | --- |
| `alarm` | `alarm_yyyyMM_nn` | `alarm_202511_00` |
| `alarm_handle` | `alarm_handle_yyyyMM_nn` | `alarm_handle_202511_00` |
| `alarm_electrolytic_cell` | `alarm_electrolytic_cell_yyyyMM_nn` | `alarm_electrolytic_cell_202511_00` |

`nn` 是月内 slice 序号，从 `00` 开始。单月当前 slice 达到 `alarm.sharding.maxRowsPerSlice` 后，创建下一组物理表。

## 核心元数据

### `alarm_shard_slice`

用于记录每个月每个 slice 的容量分配状态。

关键字段：

- `month_key`：月份，例如 `202511`。
- `slice_no`：月内 slice 序号。
- `table_suffix`：物理表后缀，例如 `202511_00`。
- `current_rows`：已预占行数，不等于真实行数。
- `max_rows`：当前 slice 最大容量。

### `alarm_cid_index`

hot cid 路由表，只服务正在报警和刚关闭待清理的记录。

关键字段：

- `alarm_cid`：外部报警 ID。
- `alarm_id`：内部可解析 ID。
- `table_suffix`：业务分片后缀。
- `route_status`：`ACTIVE` 或 `CLOSED`。
- `delete_after`：关闭后允许物理清理的时间。

### `alarm_cid_stale_index`

stale cid 路由表，用于长时间未关闭报警。它不是永久历史索引，过期前必须先对业务报警做超时关闭，再删除路由。

## ShardingSphere 配置口径

- 保留 ShardingSphere 4.1.1，不升级 5.x。
- 复用 `hpis-quad` 类似的 Java API 动态建表思路。
- Nacos 中旧的 `alarm_id % 5` inline 规则需要关闭，避免两套分片数据源同时生效。
- 使用 `spring.shardingsphere.enabled=false` 禁用 starter 自动配置，由业务 Java 配置创建分片数据源。

建议 Nacos 核心配置：

```yaml
spring:
  shardingsphere:
    enabled: false
    datasource:
      names: ds
      ds:
        type: com.zaxxer.hikari.HikariDataSource
        driver-class-name: com.mysql.cj.jdbc.Driver
        url: jdbc:mysql://127.0.0.1:3306/hpis_alarm?useUnicode=true&characterEncoding=utf8&serverTimezone=Asia/Shanghai
        username: root
        password: 123456

alarm:
  sharding:
    enabled: true
    max-rows-per-slice: 5000000
    allocation-segment-size: 1000
    pre-create-months: 0
    include-legacy-tables: false
    id:
      worker-id: 0
    actual-data-nodes:
      current-month-max-slice-no: 255
      next-month-max-slice-no: 9
    rule-refresh:
      enabled: true
      cron: "0 5 0 1 * ?"
      close-old-delay-ms: 300000
      active-on-table-created-enabled: true
      active-on-table-created-debounce-ms: 30000
      active-on-table-created-async: true
      month-end-pre-create-enabled: true
      month-end-pre-create-cron: "0 50 23 * * ?"
      month-end-pre-create-check-last-day: true
      month-end-pre-create-next-month-max-slice-no: 0
```

当前配置口径：

- 启动时创建当前月 `00` 三张业务物理表。
- 当前月 actualDataNodes 注册 `00..255`，覆盖单月全部可编码 slice。
- 下个月 actualDataNodes 默认注册 `00..09`，作为跨月高峰缓冲。
- 月末预热任务默认只物理创建下个月 `00`，完成后显式刷新 DataSource。
- 动态建表后的主动刷新是补充机制，只缩短后续请求感知新表的窗口，不替代预注册。

## 路由优先级

1. 写入链路优先使用 `AlarmShardContext`，确保绑定表同 suffix。
2. 按 `alarm_id` 查询时优先解析内部 ID，直达目标表。
3. 按 cid 停止时查 hot/stale cid route。
4. 按时间范围查询时根据月份和 slice 命中业务分片。
5. 无有效分片键时可能广播，应在接口层尽量带时间条件或 ID 条件。

## 当前边界

- 不维护永久 cid 历史索引。
- 删除 cid route 后，不能仅凭 cid 快速查长期历史。
- `alarm_cid` 默认基本唯一；若现场存在重复，应将唯一键调整为 `(alarm_cid, device_sn)`。
- 旧 `0..4` 分片已经清理，新链路只支持 `yyyyMM_nn` 分片，不再提供 legacy fallback。
## 2026-06-04 actualDataNodes 注册与刷新

ShardingSphere 4.1.1 的 `actualDataNodes` 是 DataSource 创建时的静态规则，运行中新建 `alarm_yyyyMM_nn` 物理表后，已有 ShardingSphere DataSource 不会自动把新表加入路由配置。不能只依赖数据库表扫描来“即时生效”，否则运行时间一长仍会遇到 `Actual table is not in table config`。

本轮采用低风险刷新方案：

- 历史月份：刷新时扫描数据库实际存在的 `yyyyMM_nn` 分片表并注册。
- 当前月份：预注册 `00..255`，覆盖当前月内所有可编码 slice。
- 下个月：默认预注册 `00..09`，可通过 `alarm.sharding.actual-data-nodes.next-month-max-slice-no` 调整为 `00..N`。
- 刷新方式：重建新的 ShardingSphere DataSource，成功后通过 `RefreshableAlarmShardingDataSource` 原子切换，失败则继续使用旧实例。
- legacy 边界：旧 `alarm_0..4`、`alarm_handle_0..4`、`alarm_electrolytic_cell_0..4` 已清理，不再注册、不再兜底查询。

这个方案避免修改 ShardingSphere 内部规则对象，也避免每次动态建表都重启服务。主要成本是每月低峰刷新一次 DataSource，并在当前月预注册最多 256 个节点。

## 2026-06-07 月末预热定位

- 启动阶段默认只创建当前月 `00` 物理表，当前月 actualDataNodes 仍注册 `00..255`。
- 月末预热任务默认在本月最后一天创建下个月 `00` 物理表，并刷新一次 DataSource。
- 下个月 actualDataNodes 默认注册 `00..09`，但物理表默认只创建 `00`，其余节点作为跨月高峰的路由预注册缓冲。
- 当前服务按单实例运行设计，本轮不引入分布式锁；单实例内依赖本地表级锁、`CREATE TABLE IF NOT EXISTS` 和刷新单飞锁控制并发。
- 月末预热刷新是主路径，动态建表后的主动刷新仍是补充保险，不替代当前月/下个月预注册策略。

## 2026-06-05 建表后主动刷新定位

建表后主动刷新是补充机制，不是主路径：

- 主路径仍是当前月 `00..255` 预注册和下月 `00..N` 预注册。
- 当运行期确实创建了新的 `yyyyMM_nn` 物理表后，系统在同一 suffix 的三张业务表创建完成后发起一次刷新请求。
- 存在事务同步时，刷新请求只在 `afterCommit` 后执行；事务回滚时不刷新，避免规则看到未提交或已回滚的建表状态。
- 主动刷新带 30 秒默认去抖，防止压测、补数或连续切片时频繁重建 DataSource。
- 本机制不暂停 MQ、不改变分片算法、不恢复 legacy `0..4` 表。
