# 报警停止可靠化与批量关闭设计说明

## 设计目标

现场高流量场景中，1 万 start + 1 万 stop 可能让消警链路长时间堆积，线程池队列满后出现 stop 丢失或 `alarm_endTime` 长时间缺失。

当前生产化候选采用：

- MQ 手动 ack。
- stop event 可靠落库。
- 后台 worker 批量关闭。
- `PROCESSING + lock_token` 短事务认领。
- stop 专用线程池并行处理小事务。
- side effect 独立执行。
- 空闲时暂停 worker 查库，新 stop 入库后唤醒。

## stop event 表定位

`alarm_stop_event` 是短生命周期可靠缓冲表，不是历史表。

状态：

- `PENDING`：stop 已收到，但核心消警尚未完成。
- `PROCESSING`：已经被一个 worker 批次认领，只有相同 `lock_token` 能提交结果。
- `APPLIED`：业务表和 cid route 已关闭。
- `FAILED`：超过最大重试次数，需要人工排查。

同一 `alarm_cid` 重复 stop 时，通过 upsert 保留最新 `stop_time`，避免重复堆积。已经处于
`PROCESSING` 或 `APPLIED` 的事件不会被重复 stop 重置回 `PENDING`。

## MQ ack 策略

- start 消息：业务插入成功后 ack；异常时 nack/requeue。
- stop 消息：写入 `alarm_stop_event` 成功后 ack；异常时 nack/requeue。

这样 stop 不依赖业务关闭是否立即完成，只要 stop event 落库，最终 worker 会继续处理。落库成功后会唤醒空闲 worker；如果发生漏唤醒、重启或多实例路由不均，低频兜底扫描仍会重新发现 `PENDING`。

## 批量关闭流程

`AlarmStopEventWorker` 和 `AlarmStopEventClaimService` 负责认领，`AlarmStopEventService.processClaimedBatch`
负责核心批处理：

1. scheduled 派发器每 `dispatchIntervalMs` 只向 stop 专用线程池补充任务，不在调度线程跑长循环。
2. 每个任务用短事务执行 `UPDATE ... ORDER BY ... LIMIT claimBatchSize`，把可用的 `PENDING` 原子更新为 `PROCESSING` 并写入唯一 `lock_token`。
3. 认领事务提交后，按 token 查询自己的事件并在独立事务中处理。
4. 按 `alarm.batch.inLimit` 把 `alarm_cid` 拆成多段 `IN` 查询，批量读取 hot/stale route；只有小批查询异常时才允许带保险丝降级单条查询。
5. active route 按 `table_suffix` 分组，每个认领批次默认最多 `200` 条。
6. 每个 suffix 设置 `AlarmShardContext`，批量更新 `alarm_endTime`，并校验实际更新行数。
7. 批量查询生成 side effect 所需的业务报警最小字段。
8. 按 hot/stale 拆分后批量关闭 cid route。
9. 使用 `PROCESSING + lock_token + id in (...)` 条件批量标记 stop event 为 `APPLIED`。
10. 生成 side effect event。route 暂不可见时回到延迟 `PENDING`；事务失败时释放 token 并退避重试。

单实例内，步骤 2 和步骤 3 使用 `READ_COMMITTED` 短串行临界区，避免多个认领 SQL 同时扫描相邻
索引范围时产生 MySQL next-key 锁竞争。claim 对瞬时数据库锁冲突做有限退避重试。临界区不包含物理表
更新和 route 关闭，因此核心关闭事务仍可在线程池并行。超时回收、历史恢复和清理任务在存在 in-flight
核心批次时跳过，避免维护 SQL 挤入热路径。多实例同时开启 dispatcher 前必须单独做锁竞争灰度验证。

低频恢复任务会把超过 `processingTimeoutMs` 的 `PROCESSING` 释放回 `PENDING`，用于服务崩溃恢复。

## 空闲暂停与唤醒

`AlarmStopEventWorker` 仍保留 `@Scheduled` 派发入口，但默认启用 `alarm.stop-worker.idlePauseEnabled=true`：

- worker 启动默认 active，保证应用重启后能先扫描已有 `PENDING`。
- 连续 `idleConfirmCount` 轮核心消警和 side effect 都无处理量后进入 idle pause。
- idle pause 后 scheduled 方法只做内存判断，不再高频查询 `alarm_stop_event`。
- `AlarmStopEventService.recordStop` 在 stop event 落库成功后唤醒 worker。
- `applyPendingStopForNewAlarm` 补偿成功后也会唤醒 worker，避免新生成的 side effect 等待兜底扫描。
- `idleProbeIntervalMs` 控制低频兜底查库，默认 60000ms，防止漏唤醒或多实例场景下 `PENDING` 长期卡住。

## 本轮批量化点

| 批量点 | 原方式 | 新方式 |
| --- | --- | --- |
| route 查询 | 每条 stop event 查询 hot/stale route | 按 `alarm.batch.inLimit` 做 `alarm_cid in (...)` 批量查询 |
| route 关闭 | 每条 `closeHotByAlarmId/closeStaleByAlarmId` | `closeHotBatch/closeStaleBatch` |
| stop event 完成 | 每条 `markApplied` | `markAppliedBatch` |
| route 缺失重试 | 立即继续扫描 | 批量回到延迟 `PENDING`，`last_error=ROUTE_MISSING` |
| 并发认领 | 串行 scheduled 拉取 | `PROCESSING + lock_token` 原子认领 |
| side effect 完成 | 每条 `markDone` | `markDoneBatch` |

route 批量关闭使用：

```sql
alarm_endTime = case alarm_id
  when ? then ?
  when ? then ?
end
```

这样同一批内每条报警仍写入自己的 `stop_time`，不会被统一时间覆盖。

## side effect 策略

核心消警只保证：

- 业务表 `alarm_endTime` 写入。
- cid route 关闭。
- stop event 标记 `APPLIED`。

设备恢复、电解槽扩展清理、推送等都作为 side effect：

- side effect 失败不会回滚核心消警。
- 高流量时可以延迟执行。
- 成功 event id 收集后批量 `markDoneBatch`。

`EC_ECTYPE_DELETE` 只允许 `sceneType=2` 的电解槽报警生成。为了保证判断正确，批量关闭后补查业务报警时必须包含 `scene_type` 字段。

## 幂等与乱序

- stop 先到、start 后到：stop event 保持 `PENDING`，start 成功后调用补偿路径立即关闭。
- 重复 stop：如果 route 已经 `CLOSED`，event 可直接标记 `APPLIED`。
- 找不到 active route：批量链路会继续查 hot/stale 全状态 route；如果已 `CLOSED`，按重复 stop 标记 `APPLIED`；如果 hot/stale 都查不到，按 `available_time` 延迟重试，达到上限才转 `FAILED/ROUTE_MISSING`。
- stop 先到、start 后到补偿仍保留在 start 写入 route 后的 `applyPendingStopsForNewAlarms`；历史 `FAILED/ROUTE_MISSING` 也保留恢复扫描。
- side effect 重复生成：通过 `alarm_id + effect_type` 唯一约束避免重复执行。

## 高低流量策略

低流量：

- 小批量处理。
- side effect 正常执行。
- 清理到期 `APPLIED` stop event 和 closed route。
- 连续空轮次后进入 idle pause，减少无任务时的 DB 查询和 SQL 日志。

高流量：

- 专用线程池并发处理固定小批，不通过超大 SQL 换吞吐。
- cleanup 暂停或降频。
- side effect 不阻塞核心消警。

当前压测显示核心批量化有效，但剩余耗时主要在 MQ 消费节奏、start 插入链路、stop event upsert 和电解槽 side effect。

## SQL 日志边界

stop-worker 的普通完成日志、核心批次 Profiling 和 side effect 批量成功日志受
`alarm.stop-worker.logEnabled` 控制；异常、重试和失败日志始终保留。SQL 日志不归它控制。SQL info 由 `alarm.sql-log.*` 控制：

- `enabled=false`：不打印 SQL info。
- `mode=alarm-write`：只打印报警主链路写 SQL 和非 worker 慢 SQL。
- `mode=all`：恢复旧的全量 SQL 打印，不建议生产长期开启。
- stop-worker 相关 mapper SQL 默认不打印，只保留异常日志兜底。

## 2026-06-01 stop 入队聚批与可靠 outbox 补充

本节覆盖旧版中“side effect 创建失败可继续完成核心关闭”的宽松语义。当前实现要求可靠 outbox 与核心关闭在同一事务内成功：

- 连续 stop 由 batch listener 默认每 `100` 条执行一次 multi-values upsert，单次仍不得超过 `500`。
- upsert 成功后逐条 ack；数据库异常整批 requeue，不允许在 listener 内无界逐条降级。
- 重复 stop 保留最新 `stop_time`。已经 `APPLIED` 的事件收到更晚结束时间时重新进入 `PENDING`。
- `PROCESSING` 完成时必须同时匹配 `lock_token` 和 `event_version`，且更新行数与 claim 数量完全一致，否则事务回滚。
- outbox 创建失败会回滚主表关闭、route 关闭和事件完成标记，由可靠 stop event 后续重试。
- `initialAvailableDelayMs` 用于灰度调整首次 claim 窗口，建议从 `200ms` 开始验证 route 可见性。
