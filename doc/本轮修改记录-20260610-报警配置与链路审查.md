## 审查结论

### 新增报警链路

- MQ start 链路仍符合当前分片写入边界：先准备分片身份，再保持 `alarm`、`alarm_handle`、`alarm_electrolytic_cell` 同 suffix 写入。
- 批量 start 仍通过 `AlarmInsertContext` 复用已分配的 `alarm_id/shardSuffix`，批量失败拆单不重新分配。
- `/alarm/alarmAdd` 仍存在异常吞掉后 HTTP 调用方难以判断失败的问题，但该入口一般不使用，本轮不改行为。

### 关闭报警链路

- MQ stop 主路径通过 `alarm_stop_event` 可靠落库后 ack，再由 worker 按 suffix 批量关闭业务表和 cid route，当前设计合理。
- HTTP/direct stop 仍是兼容路径，异常处理和远程副作用仍有历史风险；本轮只记录，不迁移。
- device/irms 批量 direct stop 会按 active route 分 suffix 更新，随后关闭 route；如果没有 active route，业务表不会广播扫描历史分片。

### 分片与刷新链路

- 当前月 `00..255` 预注册是主保护，避免当前月动态切片写入命中未注册节点。
- 下个月 `00..09` 预注册和月末创建下个月 `00` 可以覆盖跨月首表闭环。
- 动态建表后 afterCommit 防抖刷新只服务后续请求，不替代预注册。
- DataSource 刷新失败会保留旧实例，符合失败保护预期。

### 修改和删除链路

- `updateAlarm` 仍存在 `identify` 写入 `update_by` 的历史映射风险，需业务确认后再决定是否改为处理表字段或移除。
- `deleteAlarmByIds` 已统一为业务表假删、cid route 真删。删除返回值仍以主表 `alarm` 影响行数为准，保持 Controller `toAjax(...)` 判断语义。
