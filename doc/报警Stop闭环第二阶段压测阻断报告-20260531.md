# 报警 Stop 闭环第二阶段压测阻断报告

## 结论

第二阶段 `PROCESSING + lock_token` 并发认领链路已经完成代码实现和单元测试，但暂不提交、不推送，也不进入 `main`。

`GENERAL_ALTERNATE 10000` 核心闭环通过且 stop claim 日志干净。`MIXED_ALTERNATE 10000` 虽然每轮都能依靠批量失败拆单兜底最终闭合，但电解槽当前点位快照表仍存在并发写 deadlock。低档门禁未通过，因此按测试计划停止执行 `50000 / 100000 / 750000 PENDING`。

## 已完成实现

- `alarm_stop_event` 增加 `PROCESSING`、`lock_token`、`locked_at`、`available_time`。
- stop worker 改为短事务认领和专用线程池处理，默认 `4 x 200`。
- 热路径移除全量 `countPending`，使用 `exists limit 1`。
- APPLIED、重试、失败更新增加 `PROCESSING + lock_token` 条件。
- route missing 改为延迟重试，增加超时 PROCESSING 释放。
- verifier 改为轻量热采样和终态完整校验。
- 电解槽当前点位写入从多组 `OR` 删旧改为按点位去重、稳定排序、分块原子 upsert。
- 电解槽当前点位表迁移草案改为稳定自增 `ectype_id` 主键、普通 `idx_ec_ectype_alarm_id`、点位唯一 `uk_ec_ectype_point`。

## 剩余阻断

### 电解槽当前点位快照写竞争

最新 InnoDB deadlock 快照显示，多个 Rabbit consumer 并发执行多 values upsert 时，仍会在
`alarm_electrolytic_cell_ectype` 自增主键尾部 `supremum` 位置争抢 insert intention 锁。

当前链路能够通过批量失败后拆单恢复，所以没有留下半成品数据，但这会：

- 增加事务回滚和重复 SQL；
- 拉低 mixed 场景吞吐；
- 在更高数据量下放大锁竞争；
- 让压测结果依赖异常兜底，不符合生产门禁。

推荐下一步把 `alarm_electrolytic_cell_ectype` 定位为最终一致快照：start 核心事务只写点位变更事件，使用单独的按点位 hash 分区 worker 合并更新快照。短期缓解方案是限制电解槽快照 writer 并发并增加有限 deadlock 重试，但不能作为最终生产方案。

### 本机配置表 schema 漂移

仓库 Mapper 已使用：

```text
alarm_device_configure.device_sn
alarm_configure.device_sn
```

本机旧表仍是：

```text
alarm_device_configure.device_id
alarm_configure.device_serial_number
```

mixed 场景异步逻辑持续出现 `Unknown column 'd.device_sn' in 'field list'`。该问题已存在于 `main`，不是本次 stop worker 引入，但必须在生产灰度前核对正式库 DDL 和迁移版本。
