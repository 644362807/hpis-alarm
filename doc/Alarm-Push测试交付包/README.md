# Alarm-Push 测试交付包

## 1. 适用人员

本文档包面向不了解 Alarm、Push 内部实现的接口测试人员。测试目标是独立走完“运行环境准备 → 报警配置 → 报警上报 → 报警记录 → 查看与处理 → 工单 → Push 路由 → 最终接收人/接收端 → 数据清理”的完整流程。

当前迭代日期：2026-08-02。版本范围：Alarm 工单闭环、Push 消息类型目录、按字典值过滤、服务配置、旧库升级迁移及交付验收。

## 2. 开始前必须准备

- 可访问 System、Alarm、Push、Nacos、MySQL、Redis 和 RabbitMQ 的测试环境；未启用的 Push 通道不要求配置。
- 当前租户有效 Token，并具备报警、处理、工单、Push 配置权限。
- 当前租户至少三个可用于测试的设备 ID、设备 SN 和网关 SN。
- 一个测试专用正数 `workorderConfigId`；当前代码仅作工单启用关联门禁，不校验模板实体。
- 如测试企业微信，准备测试企业微信应用、三个测试用户及其平台用户绑定。
- 仅使用测试租户和测试数据，不在生产环境执行清理 SQL。

## 3. 推荐执行顺序

1. 阅读[服务配置与启动手册](docs/07-Alarm-Push服务配置与启动手册.md)，按当前单实例推荐模式配置并启动依赖和服务。
2. 现场从旧库升级时，先按[现场旧库升级迁移手册](docs/08-现场旧库升级迁移手册.md)执行旧库只读预检、备份、迁移和升级后检查；新环境仍参考[运行配置与 SQL 同步说明](docs/03-运行配置与SQL同步说明.md)。
3. 在测试库执行[环境预检 SQL](sql/alarm-push-api-setup.sql)。该脚本只读，不会创建或修改配置。
4. 阅读[Postman 导入与执行说明](docs/04-Postman导入与执行说明.md)，依次导入 Collection 和 Environment，并确认字典过滤开关已开启。
5. 按[全流程测试使用手册](docs/01-全流程测试使用手册.md)完成报警配置、报警上传、记录查询、处理、工单和 Push 字典过滤测试。
6. 需要专项验证报警、处理和工单全部状态时，按[报警与工单真实运行状态矩阵测试流程](docs/06-报警与工单真实运行状态矩阵测试流程.md)使用独立 CID 执行。
7. 遇到接口字段、枚举或输入输出疑问时查阅[API 接口文档](docs/02-API接口文档.md)。
8. 执行[测试证据查询 SQL](sql/alarm-push-api-check.sql)，保存报警记录、工单、过滤结果和 Push 日志证据。
9. 按[发布验收与回滚清单](docs/09-发布验收与回滚清单.md)完成签字验收；先通过 API 删除本轮配置，获得清理授权后才可执行[运行数据清理 SQL](sql/alarm-push-api-cleanup.sql)。
10. 查阅[本轮中断恢复与环境核验报告](docs/10-本轮中断恢复与环境核验报告.md)，区分已通过的只读/构建检查与尚未执行的真实服务联调。

## 5. Postman 自动化覆盖边界

Postman Collection 自动覆盖：

- Alarm 配置新增、列表、详情和删除；
- Alarm 配置修改以及 HTTP/企业微信 Push 配置 `messageType=10/25` 的完整生命周期；
- System 消息组、`alarm_rank` 字典，Push 消息类型目录树和过滤选项查询；
- `messageType=10` 对等级 1 放行、等级 2/3 排除，以及无等级报警按消息类型正常推送；
- 企业微信应用读写、用户绑定增查改删、接收组增查改删；
- HTTP 报警上传、最终 HTTP 接收器验证；
- 候选目标、报警确认、`null/0/正数`工单推送三态、我的督促记录、编辑、转派、`/handle/save`联动完成、stop 自动关闭、异常关闭和重复请求失败；
- Push 禁用、不可达地址和缺失字段等失败场景；
- 测试配置和接收器事件清理。

Postman Collection 已覆盖企业微信应用、平台用户绑定、接收组、Push 配置、候选人接口以及工单详情/转派的跨租户拒绝，但不自动执行数据库迁移。企业微信客户端到达能力已由当前测试方确认，可作为本轮通道基线；最新状态矩阵仍必须逐事件核对配置、接收目标、`messageId`和成功发送日志，不能只凭历史到达结论放过当前发送失败。

当前 Collection 共 87 个请求。字典过滤用例只有在 Push 配置 `push.routing.dict-exclude-filter-enabled=true` 时有效；未开启时属于兼容模式，等级不参与过滤。企业微信仅在现场启用时测试，其余通道同样为选配，未配置的通道不得因此阻断服务启动。

## 6. SQL 安全边界

- `alarm-push-api-setup.sql` 和 `alarm-push-api-check.sql` 是只读脚本。
- `alarm-legacy-source-precheck.sql`、`alarm-upgrade-postcheck.sql` 和 `push-dict-filter-precheck.sql` 都是只读脚本，但目标不同：前者只查`hpis_alarm1`，中者只查升级后`hpis_alarm`，后者只查`hpis_push`。迁移 DDL 只能在已备份并确认的演练/目标库执行。
- `alarm-push-api-cleanup.sql` 包含 `DELETE`，只允许清理本轮明确测试标识对应的数据。
- Alarm 配置和 Push 配置必须通过接口增删改查，禁止使用 SQL 代替配置 API。
- 生产结构迁移 SQL 不复制到本交付包。正式同步时以仓库 `src/main/resources/sql/` 为唯一事实来源，并严格遵守运行配置与 SQL 同步说明的顺序和预检条件。
- 执行任何 DDL 或清理 SQL 前都要确认数据库、租户、备份和回滚条件。

## 7. 最终通过标准

只有同时满足以下条件，整体流程才可判定 PASS：

1. 报警配置可新增、查询、修改和删除，且设备、场景、报警类型和推送消息类型匹配。
2. 报警上传后能按外部 `alarmCid` 回查到内部 Long `alarmId`，不能只依据 HTTP 2xx。
3. 报警记录查看、修改、处理、停止和删除符合接口文档的状态语义。
4. 无推送、组推送、定向推送、“我的工单”、转派、报警处理联动、异常关闭和所有终态门禁符合手册要求。
5. HTTP、企业微信或其他实际启用通道到达最终接收端；只进入 MQ 不算最终推送成功。
6. 企业微信普通报警按组解析，工单正数负责人只解析当前负责人，未分配按组解析，转派只解析新负责人；如声明客户端实收，还需真实到达证据。
7. 只读 SQL 证据与接口、接收器或收件截图相互一致。
8. 本轮配置、测试运行数据和接收器事件已按授权清理，且未影响其他租户数据。
9. 字典过滤开启时，目录元数据、配置排除值与实际投递一致；无等级报警不因缺少 `messageLevel` 被误过滤，站内推送行为不受本功能影响。

任一依赖不可用但测试步骤本身没有失败时标记 BLOCKED，并记录缺少的服务、权限、凭证或测试数据；不得写成 PASS。
