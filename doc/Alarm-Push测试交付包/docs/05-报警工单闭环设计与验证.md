# 报警处理与工单督促闭环设计及验证

> 文档版本：2026-07-23
> 适用服务：`hpis-alarm`、`hpis-push`
> 本文是本次工单闭环的正式设计记录；接口字段和调用示例以 `02-API接口文档.md` 为准。

## 1. 目标和设计结论

本轮使用最小迭代完成以下闭环：工单只记录一次处理督促及其推送目标，报警处理仍以 `alarm + alarm_handle`为唯一业务入口；实际登录处理人提交说明和图片后，报警、处理记录和活动工单在同一事务内收口。设备自然结束报警时，未处理的活动工单自动关闭，不能继续显示为可处理。

不增加审批流、抢单池、工单审核负责人、流转历史表或候选人快照表。`assigneeId`只表示督促推送目标，不再作为谁有权处理报警的依据。

## 2. 既有问题和本轮处理

| 既有问题 | 本轮处理 |
| --- | --- |
| 工单列表、详情、编辑、删除存在租户边界缺口 | 所有读写由服务端强制使用当前租户 |
| 工单完成与报警处理存在两套入口和两套权限语义 | 统一通过 `POST /handle/save`处理报警并联动活动工单；旧 `/workorder/complete`固定返回退役提示 |
| 通用编辑可以绕过转派和状态流转 | 通用编辑只修改标题和内容 |
| 状态更新只有 Java 前置判断 | 完成、转派、关闭、删除同时增加 SQL 状态条件 |
| 工单图片没有明确存储位置 | 图片只存 `alarm_handle.handle_picture`，工单详情/列表批量回填 |
| Push 接收组不能直接用于前端选负责人 | 增加租户内候选负责人只读接口 |

## 3. 数据职责

| 数据对象 | 职责 |
| --- | --- |
| `alarm` | 设备报警事实和处理/停止终态，是能否处理的主判断 |
| `alarm_workorder` | 督促推送目标、督促状态和处理/关闭结果，不是报警所有权 |
| `alarm_handle` | 报警确认/处理记录及处理图片 |
| `active_push_config` | 按租户、消息类型和路由范围确定推送策略 |
| Push 接收组和成员 | 普通报警接收范围、未分配工单通知范围及负责人候选来源 |
| 企业微信用户绑定 | 当前租户内 `userId → wecomUserId` 的可达关系 |

Push 消息是否发送成功不改变 Alarm 中已经提交的工单事实。

## 4. 督促目标三态和推送关系

- `assigneeId == null`（字段缺失或显式 `null`）：数据库保存 SQL `NULL`，表示只记录督促工单但本次不推送。
- `assigneeId == 0`：数据库保存 `0`，创建消息交给 Push 按 `ActivePushConfig.recipientGroupId`解析接收组。
- `assigneeId > 0`：数据库保存具体业务用户 ID，Push 在当前租户内定向解析该用户绑定。
- `assigneeId < 0`：非法并拒绝创建。
- 转派仍只接受正数目标，成功后只通知新的督促目标。
- `/workorder/my`只是“定向督促给我的记录”，不是“只有我能处理”；`null/0`不会进入任何人的该列表。
- 无论三态中的哪一种，只要报警仍处于可处理状态，当前租户内具备报警处理接口权限的登录用户都可通过 `/handle/save`处理，实际处理人取登录上下文。

## 5. 状态机

| 状态 | 含义 | 允许操作 |
| --- | --- | --- |
| `0` | 待处理督促 | 编辑标题/内容、转派、由报警处理联动完成、异常关闭、删除 |
| `1` | 处理中（兼容状态） | 编辑标题/内容、转派、由报警处理联动完成、异常关闭、删除 |
| `2` | 已完成 | `/handle/save`成功后的正常终态 |
| `3` | 已关闭 | 手工异常关闭，或报警先自然结束时自动关闭 |
| `4` | 已退回 | 本轮可转派、异常关闭或删除，不增加新的退回流程 |

工单是否可处理必须同时满足：工单状态为 `0/1`、`alarm.alarm_status='0'`、`alarm_handle.handle_status='2'`。列表返回 `alarmStatus`、`alarmEndtime`、`handleStatus`、实际处理人、`processable`和 `unprocessableReason`；分页后一次批量查询关系，禁止 N+1。

报警处理成功时：真实报警写 `alarm_status='2'`，误报写 `-1`，处理记录写 `handle_status='1'`及实际处理人/说明/图片，活动工单写 `2`。报警自然停止时写 `alarm_status='1'`及结束时间，活动工单写 `3/ALARM_ENDED`。所有终态更新都带原状态条件，重复请求不会产生第二次有效写入。

## 6. 接口闭环

### 6.1 查询

- `GET /workorder/list`：当前租户全部工单，返回标准分页结构。
- `GET /workorder/{workorderId}`：当前租户管理详情。
- `GET /workorder/my`：当前租户且 `assignee_id=当前用户`的定向督促记录。
- `GET /workorder/my/{workorderId}`：仅用于查看定向给当前用户的督促详情。

请求中的 `tenantId`不能改变查询范围；“我的工单”也不接受请求中的负责人覆盖当前用户。

### 6.2 创建和转派

- 创建前确认报警属于当前租户、报警已确认且命中的报警配置含正数 `workorderConfigId`。当前仓库不含模板实体校验，因此这里只是兼容关联门禁，不宣称模板内容已加载。
- 服务端固定初始状态为 `0`并保证一警一单。
- 负责人字段缺失/`null`保存 SQL `NULL`且不推送；`0`按组推送；正数定向推送。
- 转派只接受正数新负责人，成功后状态重置为 `0`。
- 创建和转派消息均在本地事务提交后发送；转派消息只包含新负责人。

### 6.3 正常处理并联动工单

请求只接受：

```json
{
  "alarmId": 671599294431815216,
  "identify": "0",
  "opinion": "现场复位并确认设备恢复",
  "handlePicture": "/upload/workorder/300.jpg"
}
```

`alarmId`、`opinion`、`handlePicture`必填；`identify`为 `0`表示真实处理、`1`表示误报。服务端强制当前租户，并要求报警仍在进行且处理记录已确认。成功后在同一事务中更新报警、处理记录和存在的活动工单；没有工单时仍可正常处理报警。处理权限不比较 `assigneeId`。

兼容接口 `PUT /workorder/complete`不再执行业务更新，固定返回：`工单完成已并入报警处理，请调用 /handle/save`。

### 6.4 异常关闭

`PUT /workorder/close`使用 `alarm:workorder:close`权限，不额外硬编码管理员身份。`workorderId`和关闭原因 `handleResult`必填，图片选填；它只关闭督促记录，不把报警伪装成已处理。设备 stop、HTTP stop、CID 超时关闭等报警结束路径会自动把仍活动的工单置为 `3`。

## 7. Push 候选负责人

```http
GET /recipientGroup/workorderCandidates?messageType={type}&deviceSn={sn}
```

解析顺序：

1. 强制当前租户。
2. 匹配启用、未删除、企业微信通道且 `messageType`相同的 Push 配置。
3. `TENANT`路由直接匹配；`DEVICE`路由必须命中 `deviceSn`。
4. 批量读取命中配置的启用接收组成员。
5. 批量读取当前租户企业微信绑定并按 `userId`去重。
6. 返回 `userId`、`wecomUserId`、`wecomReachable`；没有绑定的组成员仍可作为业务候选人，但明确标记不可通过企业微信触达。

## 8. 数据库变化和回滚

本轮不新增业务表，也不新增 `alarm_workorder.handle_picture`。只增加幂等索引：

```sql
KEY idx_alarm_workorder_tenant_assignee_status
    (tenant_id, assignee_id, status, create_time)
```

接口可以停止调用而不影响旧报警入口；候选人接口无写操作；索引可以单独删除。回滚代码时不得删除已经产生的工单或处理记录。
