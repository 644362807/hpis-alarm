# 报警工单负责人闭环设计与验证

> 文档版本：2026-07-23
> 适用服务：`hpis-alarm`、`hpis-push`
> 本文是本次工单闭环的正式设计记录；接口字段和调用示例以 `02-API接口文档.md` 为准。

## 1. 目标和设计结论

本轮使用最小迭代完成以下闭环：Push 接收组提供候选人和未分配时的通知范围；具体业务用户成为工单负责人；负责人完成后工单进入正常终态；拥有关闭权限的人员只处理异常关闭。

不增加审批流、抢单池、流转历史表、候选人快照表或 Alarm 到 Push 的同步调用，也不修改报警主记录的状态和结束时间。

## 2. 既有问题和本轮处理

| 既有问题 | 本轮处理 |
| --- | --- |
| 工单列表、详情、编辑、删除存在租户边界缺口 | 所有读写由服务端强制使用当前租户 |
| 完成接口信任请求中的 `alarmId`、`assigneeId`和 `status` | 请求只保留工单 ID、说明和图片；其余字段从数据库和登录上下文取得 |
| 通用编辑可以绕过转派和状态流转 | 通用编辑只修改标题和内容 |
| 状态更新只有 Java 前置判断 | 完成、转派、关闭、删除同时增加 SQL 状态条件 |
| 工单图片没有明确存储位置 | 图片只存 `alarm_handle.handle_picture`，工单详情/列表批量回填 |
| Push 接收组不能直接用于前端选负责人 | 增加租户内候选负责人只读接口 |

## 3. 数据职责

| 数据对象 | 职责 |
| --- | --- |
| `alarm` | 设备报警事实和设备生命周期 |
| `alarm_workorder` | 当前负责人、工单状态和最终处理说明 |
| `alarm_handle` | 报警确认/处理记录及处理图片 |
| `active_push_config` | 按租户、消息类型和路由范围确定推送策略 |
| Push 接收组和成员 | 普通报警接收范围、未分配工单通知范围及负责人候选来源 |
| 企业微信用户绑定 | 当前租户内 `userId → wecomUserId` 的可达关系 |

Push 消息是否发送成功不改变 Alarm 中已经提交的工单事实。

## 4. 负责人和推送关系

- `assigneeId > 0`：工单属于该业务用户；创建或转派消息由 Push 定向解析该用户的企业微信绑定。
- `assigneeId`缺失、`null`或 `0`：兼容推送组模式，工单保存为未分配并按 `ActivePushConfig.recipientGroupId`解析接收人。
- 负数负责人非法。
- 前端正式创建流程应先查询候选人并选择具体负责人；后端仍保留 `0`兼容能力。
- 未分配工单不属于任何人的“我的工单”，且不能直接完成，必须先转派。
- 转派只允许正数负责人，并且只通知新负责人。

## 5. 状态机

| 状态 | 含义 | 允许操作 |
| --- | --- | --- |
| `0` | 待处理 | 编辑标题/内容、转派、完成、异常关闭、删除 |
| `1` | 处理中 | 编辑标题/内容、转派、完成、异常关闭、删除 |
| `2` | 已完成 | 正常终态，不允许再次完成、转派、关闭、编辑或删除 |
| `3` | 已关闭 | 异常终态，不允许再次完成、转派、关闭、编辑或删除 |
| `4` | 已退回 | 本轮可转派、异常关闭或删除，不增加新的退回流程 |

状态变更使用带 `tenant_id`、当前状态和必要负责人条件的原子 SQL。并发请求只有一个能够更新成功，其余请求返回状态已变化。

## 6. 接口闭环

### 6.1 查询

- `GET /workorder/list`：当前租户全部工单，返回标准分页结构。
- `GET /workorder/{workorderId}`：当前租户管理详情。
- `GET /workorder/my`：当前租户且 `assignee_id=当前用户`的工单。
- `GET /workorder/my/{workorderId}`：仅当前负责人可以取得详情。

请求中的 `tenantId`不能改变查询范围；“我的工单”也不接受请求中的负责人覆盖当前用户。

### 6.2 创建和转派

- 创建前确认报警属于当前租户、报警已确认且命中的报警配置含正数 `workorderConfigId`。当前仓库不含模板实体校验，因此这里只是兼容关联门禁，不宣称模板内容已加载。
- 服务端固定初始状态为 `0`并保证一警一单。
- 负责人为空时规范化为 `0`；正数按具体负责人保存。
- 转派只接受正数新负责人，成功后状态重置为 `0`。
- 创建和转派消息均在本地事务提交后发送；转派消息只包含新负责人。

### 6.3 正常完成

请求只接受：

```json
{
  "workorderId": 300,
  "handleResult": "现场复位并确认设备恢复",
  "handlePicture": "/upload/workorder/300.jpg"
}
```

三个字段均必填。服务端校验当前用户就是正数负责人，只允许 `0/1 → 2`；随后在同一事务中把说明写入 `alarm_workorder.handle_result`，并把工单 ID、当前处理人、说明和图片写入既有 `alarm_handle`。

### 6.4 异常关闭

`PUT /workorder/close`使用 `alarm:workorder:close`权限，不额外硬编码管理员身份。`workorderId`和关闭原因 `handleResult`必填，图片选填；只允许非终态进入状态 `3`，关闭原因同步记录到既有处理记录。

## 7. Push 候选负责人

```http
GET /recipientGroup/workorderCandidates?messageType={type}&deviceSn={sn}
```

解析顺序：

1. 强制当前租户。
2. 匹配启用、未删除、企业微信通道且 `messageType`相同的 Push 配置。
3. `TENANT`路由直接匹配；`DEVICE`路由必须命中 `deviceSn`。
4. 批量读取命中配置的启用接收组成员。
5. 批量读取当前租户企业微信绑定并按 `userId`去重。
6. 返回 `userId`、`wecomUserId`、`wecomReachable`；没有绑定的组成员仍可作为业务候选人，但明确标记不可通过企业微信触达。

## 8. 数据库变化和回滚

本轮不新增业务表，也不新增 `alarm_workorder.handle_picture`。只增加幂等索引：

```sql
KEY idx_alarm_workorder_tenant_assignee_status
    (tenant_id, assignee_id, status, create_time)
```

接口可以停止调用而不影响旧报警入口；候选人接口无写操作；索引可以单独删除。回滚代码时不得删除已经产生的工单或处理记录。
