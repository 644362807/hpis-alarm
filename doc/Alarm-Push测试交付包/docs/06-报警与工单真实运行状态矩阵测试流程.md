# 报警与工单真实运行状态矩阵测试流程

## 1. 测试目标

本流程使用真实运行的 Alarm、RabbitMQ、Push、Redis、MySQL 和企业微信配置，验证以下完整链路：

```text
设备报警消息
→ RabbitMQ alarm_queue
→ Alarm 入库并生成处理记录
→ 普通报警 Push
→ 报警确认
→ 直接处理，或创建/转派督促工单
→ 工单 Push
→ 报警处理或自然结束
→ Alarm、AlarmHandle、Workorder、Push 日志状态一致
```

企业微信通道到达能力已经单独验证，本轮不重新验证 CorpID、Secret 和应用可见范围的正确性，但每个推送用例仍须核对实际匹配的配置、目标、`messageId`和 `push_message_log`结果。发送失败不能按“通道以前通过”忽略。

本流程只通过接口维护配置、确认报警、处理报警和操作工单；报警开始/结束通过真实 RabbitMQ 消息触发。SQL 只做结构预检和只读证据核验，不用 SQL 制造业务状态。

## 2. 状态字典与真实可达边界

### 2.1 报警状态 `alarm.alarm_status`

| 值 | 含义 | 合法来源 |
|---|---|---|
| `0` | 未处理、仍在报警 | 报警开始入库 |
| `1` | 已停止 | MQ stop、设备 stop、HTTP stop 或 CID 生命周期关闭 |
| `2` | 已按真实报警处理 | `/handle/save`且`identify=0` |
| `-1` | 已按误报处理 | `/handle/save`且`identify=1` |

### 2.2 处理状态 `alarm_handle.handle_status`

| 值 | 含义 | 合法来源 |
|---|---|---|
| `0` | 未处理 | 报警开始时创建处理记录；正式 Schema 应提供该默认值 |
| `2` | 已确认 | `/handle/update` |
| `1` | 已处理 | `/handle/save` |

### 2.3 工单状态 `alarm_workorder.status`

| 值 | 含义 | 本轮处理方式 |
|---|---|---|
| `0` | 待处理 | 创建工单后的初始状态，必须真实验证 |
| `1` | 处理中 | 当前没有正式状态转换接口，不用 SQL 伪造 |
| `2` | 已完成 | `/handle/save`处理报警时联动活动工单，必须真实验证 |
| `3` | 已关闭 | 手工异常关闭或报警自然结束，必须真实验证 |
| `4` | 已退回 | 当前没有正式状态转换接口，不用 SQL 伪造 |

工单`assigneeId`只表示督促推送目标，不表示报警处理权限：

| `assigneeId` | `pushTargetMode` | 行为 |
|---|---|---|
| 缺失或`null` | `NONE` | 工单保存为 SQL `NULL`，不发布工单创建事件 |
| `0` | `GROUP` | 按工单 Push 配置关联的接收组推送 |
| 正整数 | `DIRECT` | 只向该业务用户对应的企业微信用户推送 |

## 3. 测试资源和前置条件

### 3.1 固定资源

开始前记录以下值，不在文档或 Git 中保存真实密码、Token、CorpSecret：

| 变量 | 含义 |
|---|---|
| `$RunId` | 本轮唯一编号，推荐`yyyyMMddHHmmss` |
| `$TenantId` | 专用测试租户 |
| `$DeviceId/$DeviceSn/$GatewaySn` | 当前租户真实测试设备 |
| `$UserAId/$UserAToken` | 用户A，默认操作人及定向督促目标 |
| `$UserBId/$UserBToken` | 用户B，转派目标及其他实际处理人 |
| `$OtherTenantToken` | 另一租户账号，仅做越权负向测试 |
| `$AlarmBaseUrl/$PushBaseUrl` | 通过网关访问的服务地址 |
| `$RabbitManagementUrl` | RabbitMQ 管理端地址 |

用户A、用户B必须属于同一测试租户，并已建立租户内企业微信用户绑定。接收组至少包含A、B；如组内还有其他人，必须记录实际成员，避免把额外接收者误判为泄漏。

### 3.2 配置契约

本轮可以复用已经通过接口创建的专用测试配置，也可以先按接口文档重新创建，但必须回查并记录：

- Alarm配置命中`TenantId + DeviceSn + alarmType=10 + sceneType=1`。
- `pushEnabled=1`。
- `pushMessageType=10`。
- `workorderPushMessageType=25`。
- `workorderConfigId>0`。当前代码只把它作为工单启用门禁，不宣称工单模板实体已生效。
- Push中`messageType=10`的普通报警配置启用。
- Push中`messageType=25`的工单配置启用并关联正确接收组。
- 企业微信应用、用户绑定、接收组和动态队列均启用，队列 Consumer 大于0。

### 3.3 数据库结构预检

执行迁移说明中的预检并保存结果，至少确认：

```sql
SELECT table_name, column_name, is_nullable, column_default
FROM information_schema.columns
WHERE table_schema = 'hpis_alarm'
  AND ((table_name = 'alarm_workorder' AND column_name = 'assignee_id')
    OR (table_name = 'alarm_handle' AND column_name = 'handle_status'));
```

通过条件：`assignee_id`允许`NULL`且默认`NULL`；`handle_status`的默认值符合正式基础库契约。缺少字段或`assignee_id`仍强制默认`0`时标记`BLOCKED`，先同步结构，不能继续三态测试。

### 3.4 服务探活

- Push先启动，Alarm后启动。
- Alarm没有持续 Mapper 缺失、表字段缺失或分片路由错误。
- `alarm_queue`存在且有Alarm Consumer。
- Push普通报警和工单配置专属队列存在且 Consumer 为1或符合部署实例数。
- RabbitMQ无持续堆积，Redis和数据库连接正常。

## 4. 独立报警样本矩阵

所有CID均使用以下格式，不能复用旧CID：

```text
REAL-ALARM-{RunId}-A01
...
REAL-ALARM-{RunId}-A12
```

| 样本 | 主流程 | 最终报警状态 | 最终处理状态 | 最终工单状态 |
|---|---|---:|---:|---:|
| A01 | 只产生报警，不确认 | `0` | `0` | 无 |
| A02 | 确认后直接真实处理 | `2` | `1` | 无 |
| A03 | 确认后按误报处理 | `-1` | `1` | 无 |
| A04 | 确认→工单给自己→自己处理 | `2` | `1` | `2` |
| A05 | 确认→工单给别人→对方处理 | `2` | `1` | `2` |
| A06 | 确认→工单给自己→其他用户处理 | `2` | `1` | `2` |
| A07 | 确认→`assigneeId=0`组推送→处理 | `2` | `1` | `2` |
| A08 | 确认→不传`assigneeId`→不推送→处理 | `2` | `1` | `2` |
| A09 | 未确认时设备自然结束 | `1` | `0` | 无 |
| A10 | 确认→工单待处理→设备自然结束 | `1` | `2` | `3/ALARM_ENDED` |
| A11 | 确认→工单→人工异常关闭→再处理报警 | `2` | `1` | `3` |
| A12 | 确认→工单给自己→转派别人→处理 | `2` | `1` | `2` |

每条样本独立执行。不要因为A02已处理成功，就复用A02验证停止或工单关闭。

## 5. 真实MQ报警开始和回查

### 5.1 发布开始消息

向默认交换机、routing key `alarm_queue`发布`operCode=259`。下面只替换CID、序号和当前时间，其余设备字段固定：

```json
{
  "cmd":"dataSync",
  "cmdData":{
    "confItems":1000,
    "deviceSn":"${GatewaySn}",
    "operCode":259,
    "rawData":{
      "alarmDegree":"1",
      "alarmId":"REAL-ALARM-${RunId}-A01",
      "alarmType":"10",
      "cameraType":"1",
      "deviceSn":"${DeviceSn}",
      "gatewaySn":"${GatewaySn}",
      "sceneType":"1",
      "time":"2026-07-23 20:30:00"
    },
    "version":1
  },
  "cmdSeq":101,
  "servId":"alarm-real-state-test",
  "times":1
}
```

`cmdSeq`必须是合法int。RabbitMQ返回`routed=true`只表示进入队列，不代表Alarm已完成业务处理。

### 5.2 回查内部ID

每发一条消息都轮询：

```http
GET /alarm/list?pageNum=1&pageSize=200&deviceSn={DeviceSn}
```

在`rows`中精确匹配完整`alarmCid`，保存对应内部Long型`alarmId`。通过条件：

- 每个CID只有一条Alarm记录。
- `alarmStatus="0"`、`alarmEndtime=null`。
- 对应AlarmHandle存在，初始状态符合第3.3节确认的Schema默认值。
- `alarm_cid_index`存在ACTIVE路由且指向正确月度分片。
- 普通报警通过`messageType=10`进入正确Push配置，并留下目标和发送日志。

任何样本未入库或重复入库都先停止测试，保留MQ、Alarm和分片日志，不继续用错误ID测试后续状态。

## 6. 公共确认与处理请求

### 6.1 确认报警

除A01、A09外，其他样本在后续操作前调用：

```http
POST /handle/update
Content-Type: application/json
```

```json
{
  "alarmId":671599294431815216,
  "alarmIds":[671599294431815216],
  "handleStatus":"2",
  "opinion":"状态矩阵测试确认 REAL-ALARM-{RunId}-A02"
}
```

确认后立即回查：`alarmStatus`仍为`0`，`handleStatus`变为`2`，`confirmUserId`为当前用户。确认不是处理，不能提前写`handlerId`或把报警改成终态。

### 6.2 真实报警处理

```http
POST /handle/save
Content-Type: application/json
```

```json
{
  "alarmId":671599294431815216,
  "identify":"0",
  "opinion":"现场复核并完成处理 REAL-ALARM-{RunId}-A02",
  "handlePicture":"/test/alarm-state/{RunId}/A02.jpg"
}
```

成功后：Alarm为`2`，AlarmHandle为`1`，处理人取登录用户，说明和图片一致；如果存在活动工单，工单同步为`2`并写入同一`handleResult`。

### 6.3 误报处理

A03使用同一接口，只把`identify`改为`1`。成功后Alarm为`-1`，AlarmHandle仍为`1`，处理人、说明和图片必须完整。

## 7. 十二个样本的逐项执行步骤

### 7.1 A01：未确认、未处理基线

1. 发布开始消息并取得内部Alarm ID。
2. 回查Alarm和AlarmHandle，不执行确认。
3. 调用`POST /workorder`必须失败，原因是报警未确认。
4. 调用`POST /handle/save`必须失败，且不能写处理人、说明或图片。
5. 保存当前`alarmStatus=0`和初始`handleStatus`证据。

### 7.2 A02：确认后直接真实处理

1. 确认到`handleStatus=2`。
2. 不创建工单，用户A调用`/handle/save`且`identify=0`。
3. 验证Alarm为`2`、Handle为`1`、不存在工单。
4. 使用相同请求重复处理必须失败，数据库不能产生第二次有效更新。

### 7.3 A03：确认后按误报处理

1. 确认报警。
2. 用户A调用`/handle/save`且`identify=1`。
3. 验证Alarm为`-1`、Handle为`1`、不存在工单。
4. 再按真实报警处理必须失败，原误报状态和首次处理证据不能被覆盖。

### 7.4 A04：工单给自己并由自己处理

1. 用户A确认报警。
2. 创建工单：

```json
{"alarmId":671599294431815216,"assigneeId":501,"assigneeName":"用户A","title":"A04自派督促"}
```

3. 回查工单为`status=0`、`pushTargetMode=DIRECT`、`processable=true`。
4. 用户A的`/workorder/my`包含该工单；用户B的“我的工单”不包含。
5. 验证创建事件只定向用户A，消息类型为`25`。
6. 用户A调用`/handle/save`。
7. 验证Alarm=`2`、Handle=`1`、Workorder=`2`，工单回填实际处理人和图片。

### 7.5 A05：工单给别人并由对方处理

1. 用户A确认报警，创建`assigneeId=UserBId`的工单。
2. 用户B的“我的工单”可见，用户A不可见该定向记录。
3. 验证创建事件只定向用户B。
4. 用户B调用`/handle/save`。
5. 验证实际`handlerId=UserBId`，工单状态为`2`。

### 7.6 A06：督促目标与实际处理人分离

1. 用户A确认并创建`assigneeId=UserAId`的工单。
2. 验证创建推送给A。
3. 改用用户B调用`/handle/save`，不做转派。
4. 请求必须成功：工单`assigneeId`仍为A，实际`handlerId`为B，工单状态为`2`。
5. 该用例证明`assigneeId`只决定督促推送，不构成报警处理所有权。

### 7.7 A07：接收组督促

1. 用户A确认报警，创建`assigneeId=0`的工单。
2. 验证工单保存`assigneeId=0`、`pushTargetMode=GROUP`，不进入任何用户的`/workorder/my`。
3. 验证创建事件按接收组展开，目标与当前启用组成员一致。
4. 用户A或B调用`/handle/save`。
5. 验证工单联动为`2`，实际处理人取调用者。

### 7.8 A08：创建工单但不推送

1. 用户A确认报警，创建工单时完全不传`assigneeId`和`assigneeName`。
2. 验证数据库`assignee_id IS NULL`，接口返回`pushTargetMode=NONE`。
3. 验证不进入`/workorder/my`，且不存在该Alarm ID对应的工单创建Push事件或发送日志。
4. 用户A调用`/handle/save`，验证工单仍正常联动为`2`。

### 7.9 A09：未确认时自然结束

1. 保持未确认状态。
2. 通过第8章MQ stop发送同CID结束消息。
3. 轮询到Alarm=`1`且`alarmEndtime`非空。
4. AlarmHandle保持初始未处理状态，不存在工单。
5. 后续确认、处理均不得把已停止报警改成已处理。

### 7.10 A10：待处理工单随报警自然结束

1. 用户A确认报警并创建定向A的工单。
2. 先保存Workorder=`0`、`processable=true`证据。
3. 发送同CID的MQ stop。
4. 验证Alarm=`1`、`alarmEndtime`非空、Handle仍为`2`。
5. 验证Workorder自动变为`3`、`handleResult=ALARM_ENDED`、`processable=false`。
6. 再处理报警、转派或关闭工单均必须失败。

### 7.11 A11：异常关闭督促记录后继续处理报警

1. 用户A确认报警并创建定向A的工单。
2. 调用：

```http
PUT /workorder/close
```

```json
{"workorderId":990011,"handleResult":"状态矩阵测试人工异常关闭","handlePicture":"/test/alarm-state/{RunId}/A11-close.jpg"}
```

3. 验证Workorder=`3`，但Alarm仍为`0`、Handle仍为`2`。
4. 工单列表`processable=false`，报警列表仍可作为活动且已确认报警处理。
5. 用户B调用`/handle/save`，验证Alarm=`2`、Handle=`1`，Workorder保持`3`不改成`2`。
6. 重复关闭工单必须失败。

### 7.12 A12：转派后由新目标处理

1. 用户A确认并创建定向A的工单，验证A收到创建事件。
2. 先用`assigneeId=0`尝试转派，必须失败且原目标不变。
3. 正式转派：

```http
PUT /workorder/transfer
```

```json
{"workorderId":990012,"assigneeId":502,"assigneeName":"用户B"}
```

4. 验证工单仍为`0`，目标更新为B；A的“我的工单”消失，B的“我的工单”出现。
5. 验证转派事件只定向B，不重新通知A或整个组。
6. 用缺图片请求处理，必须失败且状态不变。
7. 用户B提交完整说明和图片处理，验证Alarm=`2`、Handle=`1`、Workorder=`2`。

## 8. 真实MQ自然结束

向同一队列发布`operCode=260`，必须复用开始消息的CID和设备：

```json
{
  "cmd":"dataSync",
  "cmdData":{
    "confItems":1000,
    "deviceSn":"${GatewaySn}",
    "operCode":260,
    "rawData":{
      "alarmId":"REAL-ALARM-${RunId}-A10",
      "deviceSn":"${DeviceSn}",
      "gatewaySn":"${GatewaySn}",
      "time":"2026-07-23 20:40:00"
    },
    "version":1
  },
  "cmdSeq":210,
  "servId":"alarm-real-state-test",
  "times":1
}
```

stop进入队列后应轮询业务状态和`alarm_stop_event`，不能只看RabbitMQ队列归零。重复发送相同stop时不得产生第二次业务终态变更或误关其他CID。

## 9. 必须执行的负向门禁

| 编号 | 使用样本 | 操作 | 预期 |
|---|---|---|---|
| N01 | A01 | 未确认创建工单 | 失败，无工单 |
| N02 | A01 | 未确认处理 | 失败，状态不变 |
| N03 | A02 | 重复处理 | 失败，不覆盖首次说明/图片/处理人 |
| N04 | A03 | 误报后改真实处理 | 失败，保持`-1` |
| N05 | A04 | 同一报警重复创建工单 | 失败，仍只有一张工单 |
| N06 | A04 | 调用旧`/workorder/complete` | 固定返回改用`/handle/save`，不写库 |
| N07 | A05 | 其他租户查详情/转派/处理 | 失败或不可见，无跨租户写入 |
| N08 | A10 | 已自然结束报警再处理 | 失败，保持Alarm=`1`、Workorder=`3` |
| N09 | A10 | 终态工单转派/关闭 | 失败，目标和关闭原因不变 |
| N10 | A11 | 重复异常关闭 | 失败，无第二次业务写入 |
| N11 | A12 | 转派目标`null/0/负数` | 失败，原目标不变 |
| N12 | A12 | 处理缺`opinion`或`handlePicture` | 失败，三表状态不变 |
| N13 | A01 | 保存基线证据后，其他租户调用`/handle/update`确认 | 必须失败；若成功改为已确认，判定租户隔离严重失败并停止复用A01 |

负向请求的HTTP状态可能仍为200但业务`code`不是200；判定必须读取响应体并回查数据库状态。

## 10. 每一步的四层证据

### 10.1 接口证据

保存请求时间、操作用户、请求体和完整响应，并回查：

```http
GET /alarm/query/{alarmId}
GET /handle/list?alarmId={alarmId}&pageNum=1&pageSize=10
GET /workorder/list?alarmId={alarmId}&pageNum=1&pageSize=10
GET /workorder/{workorderId}
GET /workorder/my?pageNum=1&pageSize=100
```

### 10.2 RabbitMQ与日志证据

- 开始/结束消息的routing key、CID、`operCode`、`cmdSeq`和`routed`结果。
- `alarm_queue` Consumer和Ready/Unacked变化。
- Alarm按CID消费、内部Alarm ID和stop worker日志。
- Push动态队列名称、Consumer、消息进入与ACK情况。

### 10.3 Push证据

普通报警按`messageType=10`，工单创建/转派按`messageType=25`核对：

- `tenantId`
- `messageId`
- `activePushConfigId`
- `eventType`
- `alarmId/workorderId`
- `assigneeId`或接收组成员
- `pushChannelType`
- `pushStatus`
- 失败时的`messageData`
