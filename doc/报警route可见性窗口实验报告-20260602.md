# 报警 route 可见性窗口实验报告

## 结论

本轮完成 `500ms` 和 `1000ms` 两档 route 可见窗口真实 RabbitMQ + MySQL 持续压测。

两个档位都能跟住 `20000 MQ/min` 输入：RabbitMQ 和 stop event 没有线性积压，最终数据一致，deadlock、fallback 和持续 requeue 均为 `0`。

严格门禁仍略低于目标，因此当前不合并 `main`。下一步不应继续盲目增加可见窗口，而应先关闭 Nacos 中的 MyBatis DEBUG，并校准压测门禁口径。

## 固定条件

- 场景：`MIXED_ALTERNATE`
- 数量：`200000 MQ / 10min`
- 报警数量：`100000`
- consumer batch：`100`，并发 `2-4`
- stop worker：`workerThreads=4`、`claimBatchSize=200`
- snapshot worker：`workerThreads=2`、`claimBatchSize=100`
- verifier：`terminalOnlyFullSample=true`

## route-missing 对比

`500ms` 档聚合日志至少记录：

```text
retryBatches=500
retryRows=15353
maxWaitMs=1252
```

`1000ms` 档聚合日志至少记录：

```text
retryBatches=100
retryRows=1849
maxWaitMs=1290
```

聚合日志每 `100` 批打印一次，因此上面是可靠下界，不是精确终值。`1000ms` 显著减少无效 route claim，但核心闭环没有继续变快，说明 route 可见性已经不是唯一主瓶颈。

## 正确性

两个档位均满足：

- MQ 终态 `ready=0`、`unacked=0`
- stop event 终态 `APPLIED=100000`
- side effect 空闲后终态 `DONE=55000`
- snapshot command 空闲后终态 `DONE/DELETED=48`
- snapshot command 无 `PENDING/PROCESSING/FAILED`
- 电解槽扩展表 `45000` 条，`alarm_id` 一致且非空
- route 终态 `CLOSED=100000`
- `Deadlock found=0`
- `PERSIST_LOCK_RETRY=0`
- `PERSIST_FALLBACK=0`
- snapshot claim deadlock retry `=0`
- 快照投影批次失败 `=0`

## 环境污染

Nacos 配置仍将 MyBatis 日志级别覆盖为 DEBUG。单轮服务日志：

- `500ms` 档约 `181.85MB`
- `1000ms` 档约 `170.18MB`

日志 I/O 会污染性能结论。正式门禁前必须关闭。

## 参数建议

暂以 `500ms` 作为下一轮灰度候选值：

- 它比 `200ms` 明显减少 DB 收尾时间。
- 它比 `1000ms` 有更低的终态闭环耗时。
- `1000ms` 虽然进一步压低 route missing，但没有改善闭环吞吐。

正式决定前必须在关闭 MyBatis DEBUG 后，每档至少再跑两次。
