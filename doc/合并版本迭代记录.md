## 2026.06.08-报警分片节点刷新与月末预热

- 合并时间：2026-06-08
- 功能分支：`codex/alarm-sharding-rule-refresh-test`
- 合并提交：`20b8354 merge: alarm sharding rule refresh`
- 关联功能提交：`2d08d76 feat: refresh alarm sharding data nodes`
- 关联验证提交：`90e64d1 docs: record alarm sharding merge validation`
- 合并目标：`main`

### 变更范围

- ShardingSphere actualDataNodes 改为显式生成和注册：
  - 历史月份只注册数据库实际存在的 `yyyyMM_nn` 表。
  - 当前月默认注册 `00..255`。
  - 下个月默认注册 `00..09`。
  - 不再注册 legacy `alarm_0..4`、`alarm_handle_0..4`、`alarm_electrolytic_cell_0..4`。
- 新增可刷新 DataSource 代理：
  - `RefreshableAlarmShardingDataSource` 保持 Spring 外部引用稳定。
  - `AlarmShardingDataSourceFactory` 负责重建 ShardingSphere DataSource。
  - `AlarmShardingRuleRefreshService` 统一处理刷新、单飞锁、失败保护和旧 DataSource 延迟关闭。
- 新增动态建表后主动刷新：
  - 同一 suffix 三张业务表创建完成后只触发一次刷新请求。
  - 有事务同步时在 `afterCommit` 后刷新。
  - 事务回滚不刷新。
  - 防抖和单飞保护避免频繁重建。
- 新增月末预热任务：
  - 启动默认只预建当前月 `00`。
  - 月末任务创建下个月 `00` 三张物理表。
  - 月末任务完成后显式刷新 DataSource。
  - 本地快速测试可关闭月末判断，直接验证“下月物理表 + DataSource 刷新”链路。
- 接口文档修正：
  - `/alarm/list` 列表分页时间范围明确使用 `startTime/endTime`。
  - 不再使用 `alarmBegintime/alarmEndtime` 作为列表分页时间入参。

### 风险与后续

- 当前方案按单实例服务设计，不覆盖多实例同时月末建表的分布式互斥。
- 当前月注册 `00..255` 但默认只物理创建当前月 `00`，列表分页必须携带服务可识别的 `startTime/endTime`，避免广播到未物理创建的预注册节点。
- `/alarm/alarmAdd` 会吞异常并返回 HTTP `200`，后续真实新增验收应以数据库反查为准。
- 快速预热测试中下个月 `00` 物理表已存在，因此本轮服务 smoke 覆盖了定时触发和刷新闭环，没有覆盖从无到有 `created=true` 的真实建表场景。
- 本地测试使用 `alarm.internal-test.remote-call-stub-enabled=true`，验证的是 alarm 内部接口、分片和 DB 闭环，不代表跨服务联动已经完成联调。
