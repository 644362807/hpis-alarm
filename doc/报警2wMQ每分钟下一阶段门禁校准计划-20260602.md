# 报警 2w MQ 每分钟下一阶段门禁校准计划

## 单一任务

下一阶段只做一件事：**去除压测环境污染并校准严格门禁口径**。

当前不继续增加 consumer，不放大 SQL 批次，不继续拉长 route 可见窗口，不拆 side effect。

## 原因

- `500ms` 和 `1000ms` 都能跟住持续输入，RabbitMQ 和 stop event 不线性积压。
- `1000ms` 已经显著减少 route missing，但闭环吞吐没有继续提升。
- sender 为了控制 `20000 MQ/min` 主动 sleep，实际发送耗时固定比 `600000ms` 多约 `150ms`。直接要求 `sendElapsed <= 600000ms` 会把发送器调度尾差算成业务失败。
- verifier 终态完整 count 仍会占用 MySQL。
- Nacos 仍开启 MyBatis DEBUG，单轮日志约 `170-182MB`。

## 执行步骤

1. 在 Nacos 关闭 MyBatis、ShardingSphere 和 Spring SQL DEBUG，仅保留 WARN。
2. 保持 `alarm.stop-worker.initialAvailableDelayMs=500`。
3. 每轮记录 sender 目标节拍、实际发送耗时、发送尾差、发送结束时 pending、DB 收尾耗时和终态完整校验耗时。
4. `MIXED_ALTERNATE 200000 MQ / 10min` 至少执行两轮正式测试。
5. 业务吞吐门禁使用：
   - 持续输入期间 MQ ready 和 stop pending 不线性增长。
   - 发送结束时 pending 保持有界。
   - DB 核心闭环在发送结束后快速回落。
   - 终态一致性全部通过。
6. sender 节拍单独报告，不再与 DB 核心吞吐混为一个失败原因。

## 决策

- 如果关闭 DEBUG 后闭环稳定达到目标，进入生产化候选评审。
- 如果仍未达到目标，下一轮只选择一个 DB 主任务：对 start 补偿处理、主表写入和 route 写入做分段直方图，选占比最高的一项优化。
