# 最终设计口径确认

本文件记录本轮报警配置、报警处理、工单和推送改造的最终设计口径。

本文件只记录已确认的需求、流程、字段边界、风险和验收口径，不包含 Java、XML、SQL 或配置文件修改。后续代码实现以本文为准；早期文档中与本文冲突的“报警产生后自动生成工单”“`alarm.workorder_id`”“`alarm.alarm_configure_id` 必加”等描述，以本文修正后的口径为准。

## 1. 已确认需求

- 不同 `alarm_type` 可以有不同报警规则。
- 同一 `tenant_id + scene_type + device_sn + alarm_type` 下最多一个启用报警配置。
- 工单不是报警产生时自动创建。
- 报警确认后，页面允许人工点击创建工单。
- 只有当前命中的报警配置存在 `workorder_config_id` 时，才允许创建工单。
- 报警配置只绑定 `push_message_type` 推送策略编码，不直接绑定单个推送配置 ID。
- 报警通知可以命中多人；谁能确认报警继续走报警管理现有权限控制。
- 推送绑定只用于通知报警确认人或工单负责人，不作为工单事实。
- 创建工单时，`alarm_workorder_config` 提供默认负责人，确认人可以临时改派，最终负责人写入 `alarm_workorder.assignee_id` 和 `alarm_workorder.assignee_name`。
- 工单创建人使用 `alarm_workorder.create_by` 和 `alarm_handle` 创建工单动作记录，不额外新增创建人字段。
- 历史报警列表只展示 `alarm` 表中的报警事实。
- 历史报警详情以 `alarm` 为主，关联 `alarm_handle` 展示确认、处理、创建工单等动作历史。
- `alarm_handle` 可以保存工单绑定字段，用于在详情时间线中展开工单。
- 工单列表和工单详情只以 `alarm_workorder` 工单实例表为准。
- 一条报警最多一个工单实例。
- 工单关闭后必须写入一条 `alarm_handle` 工单同步记录，用于报警详情展示本次人工处置已完成。

## 2. 表职责边界

### 2.1 alarm

`alarm` 只表达报警事实和报警生命周期，不承载确认、处理中、已转工单、工单处理完成等业务处理状态。

保留现有职责：

- 报警 ID。
- 设备 SN。
- 报警类型。
- 报警级别。
- 报警事实状态。
- 行业。
- 租户。
- 报警开始时间。
- 报警结束时间。
- 图片、视频、点位、位置等现有报警事实字段。

本轮不新增：

- `alarm_configure_id`
- `config_version`
- `device_type`
- `alarm_title`
- `alarm_content`
- `workorder_id`
- `rule_snapshot_json`
- `raw_payload_json`

设计说明：

- 历史报警列表只查 `alarm`。
- `alarm_beginTime` 只表示报警开始时间，也继续用于分片路由。
- `alarm_endTime` 只表示报警结束时间，不表示工单完成时间或处理时间。
- 确认、直接处理、创建工单、工单关闭同步等业务处理状态写入 `alarm_handle` 或 `alarm_workorder`。
- 工单创建按“用户点击创建工单时的当前配置”判断，不追溯报警产生时的配置版本。

### 2.2 alarm_configure

`alarm_configure` 继续作为报警配置主表。

本轮建议新增或保留：

| 字段 | 功能 |
| --- | --- |
| `push_message_type` | 推送细分字段，对应推送服务 `active_push_config.message_type`。 |
| `workorder_config_id` | 关联工单配置。为空表示确认后不允许按配置创建工单。 |

匹配口径：

- 设备级规则按 `tenant_id + scene_type + device_sn + alarm_type` 匹配。
- 行业级规则可按 `tenant_id + scene_type + alarm_type` 匹配。
- 行业全部报警可用 `alarm_type` 为空或 `*` 表达。
- 本轮最小改动优先保证设备级和报警类型级规则可靠，不强行建设完整策略引擎。

### 2.3 alarm_handle

`alarm_handle` 是报警动作历史表，不是工单主表。

现有用途：

- 确认。
- 处理。
- 误报。
- 处理意见。
- 处理图片。
- 确认人、处理人、处理时间。

本轮建议新增：

| 字段 | 功能 |
| --- | --- |
| `handle_type` | 动作类型，如确认、处理、关闭、误报、创建工单、工单同步。 |
| `workorder_id` | 当前动作关联的工单实例 ID。创建工单动作成功后写入。 |
| `status_before` | 动作前状态，可用于审计和排查。 |
| `status_after` | 动作后状态，可用于审计和排查。 |

设计说明：

- 历史报警详情关联 `alarm_handle` 展示时间线。
- 如果某条动作是创建工单，则 `handle_type=CREATE_WORKORDER`，并带 `workorder_id`。
- 详情页需要展示工单信息时，通过 `alarm_handle.workorder_id` 查询 `alarm_workorder`。
- 后续工单同步、工单关闭、转派等动作也可以写入 `alarm_handle`，但不新增第二张工单实例。
- 现有按 `alarm_id` 覆盖更新的旧逻辑要保留兼容，但新增动作应优先新增流水，避免覆盖历史。

### 2.4 alarm_workorder

`alarm_workorder` 是工单事实表。

最小字段建议：

| 字段 | 功能 |
| --- | --- |
| `workorder_id` | 工单实例 ID。 |
| `workorder_no` | 工单编号。 |
| `alarm_id` | 关联报警 ID。必须唯一。 |
| `workorder_config_id` | 来源工单配置 ID。 |
| `status` | 工单状态。 |
| `assignee_id` | 工单负责人 ID。 |
| `assignee_name` | 工单负责人名称快照。 |
| `title` | 工单标题。 |
| `content` | 工单内容。 |
| `handle_result` | 工单处理结果。 |
| `tenant_id` | 租户 ID。 |
| `del_flag` | 逻辑删除标识。 |
| `create_time` | 创建时间。 |
| `update_time` | 更新时间。 |

约束：

- `PRIMARY KEY (workorder_id)`。
- `UNIQUE KEY uk_alarm_workorder_alarm (alarm_id)`。
- `UNIQUE KEY uk_alarm_workorder_no (workorder_no)`。

设计说明：

- 工单列表和工单详情只查 `alarm_workorder`。
- 一条报警最多一个工单实例。
- `alarm_workorder_config.assignee_id/name` 是模板默认负责人，`alarm_workorder.assignee_id/name` 是本次工单实际负责人。
- 创建工单页面默认带出模板负责人，确认人可以临时改派。
- 工单关闭表示本次人工处置完成，不保证异常永久消失；后续仍异常时由重复报警或新报警重新进入流程。
- 工单转派、回退、催办不创建第二张工单。
- 重复点击创建工单时，唯一键冲突按幂等成功或已存在处理。

## 3. 已确认流程

### 3.1 报警产生

1. 设备或边缘端上报告警。
2. 报警服务写入 `alarm`。
3. 当前保留原有入库、分片和 stop 闭环逻辑。
4. 根据现有逻辑初始化 `alarm_handle`。
5. after-commit 发送报警推送消息。

### 3.2 报警推送

1. 报警服务发送基础报警事实。
2. 后续可增加 `pushMessageType`，优先来自 `alarm_configure.push_message_type`。
3. 推送服务使用设备 SN 和消息类型匹配推送配置。
4. 同一推送策略可以通知多人，确认权限不由推送配置决定。
5. 老 `messageType` 逻辑必须继续兼容。

### 3.3 报警确认

1. 用户确认报警。
2. 写入或更新确认信息。
3. 新增动作流水时使用 `handle_type=CONFIRM`。
4. 确认不自动创建工单。
5. 确认后可以直接处理，也可以在页面点击创建工单。

### 3.4 创建工单

创建工单入口必须满足：

- 报警已确认。
- 当前报警按 `tenant_id + scene_type + device_sn + alarm_type` 能命中启用报警配置。
- 命中的报警配置存在 `workorder_config_id`。
- `alarm_workorder` 中不存在该 `alarm_id` 的有效工单。

创建流程：

1. 用户在确认后的报警详情页点击创建工单。
2. 服务端按当前配置校验是否允许创建。
3. 服务端读取 `alarm_workorder_config` 默认负责人，页面允许确认人临时改派。
4. 创建 `alarm_workorder`，实际负责人写入 `assignee_id` 和 `assignee_name`。
5. 创建成功后新增 `alarm_handle` 流水：
   - `handle_type=CREATE_WORKORDER`
   - `workorder_id=新工单 ID`
   - `alarm_id=当前报警 ID`
6. 工单创建成功后推送通知实际负责人。

### 3.5 报警处理

- 未创建工单的报警可以处理。
- 未创建工单时，直接处理动作写 `alarm_handle.handle_type=HANDLE`，表示本次人工处置闭环。
- 已创建工单后，报警处理主链路交给工单；报警侧不再创建第二张工单。
- 工单关闭后写 `alarm_handle.handle_type=WORKORDER_SYNC` 或等价工单同步动作，表示工单已处理完成并同步到报警详情。
- 确认、处理、创建工单、工单同步等状态不写入 `alarm` 主表。
- 报警结束仍由 `alarm.alarm_endTime` 表达。
- 如果现场后续仍异常，通过重复报警或新报警再次进入流程。

### 3.6 历史查询

| 场景 | 查询方式 |
| --- | --- |
| 历史报警列表 | 只查 `alarm`。 |
| 历史报警详情 | 查 `alarm`，并关联 `alarm_handle` 时间线。 |
| 详情展示工单绑定 | 通过 `alarm_handle.workorder_id` 查询 `alarm_workorder`。 |
| 创建工单前幂等判断 | 查 `alarm_workorder.alarm_id`，依赖唯一约束。 |
| 工单列表和详情 | 只查 `alarm_workorder`。 |
| 工单关闭同步到报警详情 | 写入并查询 `alarm_handle` 工单同步动作。 |

## 4. 最小改动可行性

该方案属于最小改动方案，原因：

- 不修改 `alarm` 主表字段，降低报警入库、历史查询、分片和 stop 闭环风险。
- 不引入完整流程引擎。
- 不拆分复杂策略表。
- 不把推送配置和工单事实耦合。
- 工单事实新增独立表，后续扩展状态、派单、转派时不污染报警事实。
- `alarm_handle` 只增强动作记录能力，贴合现有确认和处理链路。

该方案不是临时方案，原因：

- `alarm`、`alarm_handle`、`alarm_workorder` 职责清晰。
- 工单幂等由数据库唯一约束兜底。
- 历史列表和详情查询职责分离。
- 推送负责人通知与工单事实解耦。
- 后续如果要自动建单，可在工单配置上增加模式，不需要重写表职责。
- 工单作为跨人协作任务存在；简单报警可以只写 `alarm_handle` 直接处理，不强制生成工单。

## 5. 需要修正的旧文档口径

早期文档中以下描述需要以后续修订为准：

- “报警产生后自动生成工单”应改为“报警确认后人工点击创建工单”。
- “`alarm.workorder_id`”应删除。
- “`alarm.alarm_configure_id` 必加”应改为“不新增，创建工单按当前配置判断”。
- “一个设备一种规则”应改为“同一 `tenant_id + scene_type + device_sn + alarm_type` 下最多一个启用规则”。
- “历史报警详情仅查 alarm”应改为“历史报警列表只查 alarm，详情关联 alarm_handle”。
- “工单状态依赖 alarm_handle”应改为“工单事实依赖 alarm_workorder，alarm_handle 只记录动作绑定”。
- “已创建工单的报警仍可在报警侧直接处理完成”应改为“已创建工单后由工单闭环，工单关闭后同步写入 alarm_handle”。

## 6. 主要风险和控制

| 风险 | 说明 | 控制方式 |
| --- | --- | --- |
| 配置漂移 | 不保存 `alarm_configure_id`，创建工单按点击时当前配置判断。 | 文档明确该语义；创建工单时记录 `workorder_config_id` 到工单实例。 |
| 一警多单 | 重复点击或接口重试可能重复创建。 | `alarm_workorder.alarm_id` 唯一约束；唯一冲突按已存在处理。 |
| 处理流水覆盖 | 现有 `alarm_handle` 按 `alarm_id` 更新，可能覆盖历史动作。 | 新增动作使用 insert；旧接口保留兼容。 |
| 推送误解 | 推送绑定被误认为工单事实。 | 文档和代码边界明确：推送只通知负责人。 |
| 报警和工单双入口处理冲突 | 已创建工单后，如果报警侧仍直接处理完成，会与工单状态冲突。 | 创建工单后以工单闭环为主；工单关闭同步写 `alarm_handle`。 |
| 分片缺字段 | `alarm_handle` 是分片链路，新增字段漏同步会写入失败。 | 同步基础表、分片物理表、建表逻辑、Mapper。 |
| 配置重复 | 同设备同类型多个启用配置会导致创建工单规则不确定。 | 服务层校验 `tenant_id + scene_type + device_sn + alarm_type` 唯一启用。 |

## 7. 验收口径

- 历史报警列表不依赖工单表或处理表。
- 历史报警详情可以展示确认、处理、创建工单等 `alarm_handle` 时间线。
- 创建工单按钮只在报警已确认且当前配置存在 `workorder_config_id` 时出现或可执行。
- 重复点击创建工单不会产生第二张工单。
- 创建工单成功后，`alarm_workorder` 有实例，`alarm_handle` 有 `CREATE_WORKORDER` 记录。
- 工单负责人通知只在工单创建成功后触发。
- 没有工单的报警仍可处理。
- 有工单的报警由工单处理闭环，工单关闭后同步写入 `alarm_handle`。
- 工单列表和工单详情只以 `alarm_workorder` 为事实来源。
- `alarm_beginTime` 和 `alarm_endTime` 不承载工单时间。
