# 当前最小修改范围与过时文档清理

## 1. 当前需求确认

当前需求以最小改动支持以下能力：

- 报警配置可以控制某类报警是否进入推送。
- 报警配置可以指定推送策略编码。
- 报警确认后可以直接处理，也可以按配置创建工单。
- 一个报警最多对应一个工单。
- 一个工单只维护当前状态和当前负责人；转派直接更新 `alarm_workorder`，不保留完整流转历史。
- `alarm_handle` 不再作为多条动作时间线表，而作为报警最终处置记录表。

## 2. 对比旧设计后的关键变化

旧设计中，`alarm_handle` 被设计为动作时间线：

- 确认报警写一条 `handle_type=CONFIRM`。
- 直接处理写一条 `handle_type=HANDLE`。
- 创建工单写一条 `handle_type=CREATE_WORKORDER`。
- 工单转派或关闭同步写一条 `handle_type=WORKORDER_SYNC`。

该方案与当前需求冲突。当前需求要求“一个报警最多一个工单，工单只维护当前状态，关闭完成后最多形成一条最终 handle 处理记录”，因此不能让工单创建、转派、关闭都写多条 `alarm_handle`。

当前口径调整为：

- `alarm_handle` 只表达报警最终处置结果。
- 报警直接处理时写一条 `alarm_handle`。
- 报警通过工单处理完成时写一条 `alarm_handle`，关联该工单。
- 工单创建、接单、转派、退回、关闭等动作不写多条 `alarm_handle`。
- 转派、退回、接单只更新 `alarm_workorder` 当前状态、当前负责人和更新时间；本阶段不新增工单流转历史表。

## 3. 表职责

| 表 | 当前职责 |
| --- | --- |
| `alarm` | 报警事实表，保存报警发生、状态、开始结束时间、设备、类型、租户等事实。 |
| `alarm_configure` | 报警配置表，保存报警规则、推送开关、推送策略编码、可选工单模板。 |
| `alarm_handle` | 报警最终处置记录表，直接处理或工单处理完成后最多写一条有效记录。 |
| `alarm_workorder` | 工单事实表，一个报警最多一张工单，保存当前工单状态、负责人、处理结果。 |

## 4. 最小数据库修改

### 4.1 `alarm_configure`

新增字段：

```sql
ALTER TABLE alarm_configure
  ADD COLUMN push_enabled char(1) NOT NULL DEFAULT '1'
    COMMENT '是否进入报警推送：0不推送 1推送',
  ADD COLUMN push_message_type varchar(30) NULL
    COMMENT '推送策略编码，对应推送配置 message_type；为空时回退 alarm_type',
  ADD COLUMN workorder_config_id bigint NULL
    COMMENT '关联报警工单模板ID，为空表示确认后不能按模板创建工单';
```

字段语义：

- `push_enabled=0`：报警照常入库，但不进入报警推送。
- `push_enabled=1`：报警入库后进入推送。
- `push_message_type`：只表示推送策略编码，不表示是否推送。
- `workorder_config_id`：只表示确认后是否允许按模板创建工单，不表示是否自动建单。

### 4.2 `alarm_handle`

当前口径下，`alarm_handle` 不是过程表，所以不新增过程追踪字段。

保留现有字段的业务语义：

| 字段 | 用途 |
| --- | --- |
| `alarm_handle_id` | 处理记录主键。 |
| `alarm_id` | 关联报警。 |
| `handler_id` / `handler_name` | 最终处理人。 |
| `handle_status` | 处理后的结果状态，兼容现有查询。 |
| `identify` | 真实/误报标识，兼容现有处理口径。 |
| `opinion` | 处理意见；工单处理完成时写工单结果摘要。 |
| `handle_picture` | 处理图片或附件。 |
| `handle_time` | 最终处理完成时间。 |
| `confirm_user_id` | 兼容现有确认人字段；不作为多动作流水字段使用。 |
| `alarm_beginTime` | 分片路由字段，继续保留。 |
| `del_flag` | 逻辑删除。 |

只补充一个必要关联字段：

```sql
ALTER TABLE alarm_handle
  ADD COLUMN workorder_id bigint NULL
    COMMENT '关联工单ID，直接处理为空，工单处理完成时填写';
```

不再新增：

- `status_before`
- `status_after`

原因：

- 这两个字段是过程追踪字段，适合动作流水表，不适合最终处置记录表。
- 当前需求不保留完整流转历史；如未来必须审计处理前后状态，应另起审计方案，不回填到 `alarm_handle`。

`handle_type` 是否新增：

- 最小方案不强制新增。
- 直接处理和工单处理可以通过 `workorder_id` 区分：为空表示报警侧直接处理，非空表示工单处理完成。
- 如果页面或报表需要显式区分处理方式，可以新增 `handle_type`，但只允许最终处置类枚举，不允许恢复旧动作时间线枚举。

可选 `handle_type` 口径：

```sql
ALTER TABLE alarm_handle
  ADD COLUMN handle_type char(2) NULL
    COMMENT '最终处置方式：1直接处理 2工单处理 3误报 4人工关闭';
```

不允许使用以下旧动作口径：

- `CONFIRM`
- `CREATE_WORKORDER`
- `WORKORDER_SYNC`

### 4.3 `alarm_workorder`

新增工单事实表，最小字段：

```sql
CREATE TABLE IF NOT EXISTS alarm_workorder (
  workorder_id bigint NOT NULL COMMENT '工单ID',
  workorder_no varchar(50) NOT NULL COMMENT '工单编号',
  alarm_id bigint NOT NULL COMMENT '报警ID',
  workorder_config_id bigint NULL COMMENT '来源工单模板ID',
  status char(2) NOT NULL DEFAULT '0' COMMENT '工单状态：0待处理 1处理中 2已完成 3已关闭 4退回',
  assignee_id bigint NULL COMMENT '当前负责人ID',
  assignee_name varchar(100) NULL COMMENT '当前负责人名称',
  title varchar(200) NULL COMMENT '工单标题',
  content varchar(1000) NULL COMMENT '工单内容',
  handle_result varchar(500) NULL COMMENT '工单处理结果',
  tenant_id bigint NULL COMMENT '租户ID',
  del_flag char(2) DEFAULT '0' COMMENT '逻辑删除：0存在 2删除',
  create_by varchar(64) NULL COMMENT '创建人',
  create_time datetime DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  update_by varchar(64) NULL COMMENT '更新人',
  update_time datetime NULL DEFAULT NULL ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  PRIMARY KEY (workorder_id),
  UNIQUE KEY uk_alarm_workorder_alarm (alarm_id),
  UNIQUE KEY uk_alarm_workorder_no (workorder_no),
  KEY idx_alarm_workorder_status (tenant_id, status, create_time),
  KEY idx_alarm_workorder_assignee (assignee_id, status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='报警工单表';
```

关键约束：

- `uk_alarm_workorder_alarm(alarm_id)` 是“一警一单”的最终兜底。
- 不在 `alarm` 表新增 `workorder_id`。

## 5. 最小代码修改范围

### 5.1 报警配置

涉及：

- `AlarmConfigure.java`
- `AlarmConfigureMapper.java`
- `AlarmConfigure.xml`
- `AlarmConfigureServiceImpl.java`

修改：

- 增加 `pushEnabled`、`pushMessageType`、`workorderConfigId`。
- 保存配置时写入新字段。
- 查询配置时返回新字段。
- 增加按 `tenant_id + scene_type + device_sn + alarm_type` 解析当前启用配置的方法。

### 5.2 报警推送

涉及：

- `AlarmServiceImpl.java`

修改：

- 报警入库后推送前解析当前报警配置。
- 命中配置且 `push_enabled=0` 时跳过推送。
- `push_enabled=1` 时继续推送。
- `messageType` 优先使用 `push_message_type`，为空回退 `alarm_type`。

不改变：

- MQ 消息入口。
- 报警入库顺序。
- 旧 push payload 主结构。
- `push.open` 全局开关。

### 5.3 报警处理

涉及：

- `AlarmHandle.java`
- `AlarmHandleMapper.java`
- `AlarmHandleMapper.xml`
- `AlarmHandleServiceImpl.java`

修改：

- 最小方案只新增 `workorderId`。
- 如果明确需要处理方式字段，再新增 `handleType`。
- 不新增 `statusBefore/statusAfter`。
- 直接处理报警时写或更新一条最终处置型 `alarm_handle`。
- 工单关闭后写或更新一条最终处置型 `alarm_handle`，并关联 `workorder_id`。

不再做：

- 确认报警插入 `handle_type=CONFIRM`。
- 创建工单插入 `handle_type=CREATE_WORKORDER`。
- 工单每次流转插入 `handle_type=WORKORDER_SYNC`。
- 在 `alarm_handle` 中记录处理前状态和处理后状态变化过程。

### 5.4 工单

涉及新增：

- `AlarmWorkorder.java`
- `AlarmWorkorderMapper.java`
- `AlarmWorkorderMapper.xml`
- `IAlarmWorkorderService.java`
- `AlarmWorkorderServiceImpl.java`
- `AlarmWorkorderController.java`

修改：

- 创建工单前校验报警已确认。
- 重新解析当前报警配置。
- `workorder_config_id` 为空时禁止创建工单。
- 创建工单依赖 `uk_alarm_workorder_alarm` 保证一警一单。
- 接单、转派、退回直接更新 `alarm_workorder.status`、`assignee_id`、`assignee_name`、`update_by`、`update_time`。
- 工单关闭后同步最终处理结果到 `alarm_handle`。

## 6. 当前不做事项

- 不新增 `alarm.workorder_id`。
- 不新增 `alarm.alarm_configure_id`。
- 不新增 `alarm.config_version`。
- 不把工单创建动作写成一条 `alarm_handle`。
- 不把工单转派、退回、接单、关闭都写成多条 `alarm_handle`。
- 不在 `alarm_handle` 新增 `status_before/status_after`。
- 不新增 `alarm_workorder_flow`。
- 不保存完整工单流转历史。
- 不重写 MQ ack/nack。
- 不改变报警 stop 闭环。
- 不改变报警历史列表主查询职责。

## 7. 最小验收标准

- `alarm_configure.push_enabled=0` 的报警入库但不推送。
- `alarm_configure.push_enabled=1` 的报警继续推送。
- `push_message_type` 有值时进入推送 payload；为空回退 `alarm_type`。
- 一个报警重复创建工单不会产生第二张工单。
- 工单创建不写 `alarm.workorder_id`。
- 工单创建不新增一条处理完成的 `alarm_handle`。
- 工单转派后，只更新 `alarm_workorder` 当前负责人和状态，不新增 `alarm_handle`。
- 工单关闭后，该报警有且最多有一条有效最终处置型 `alarm_handle`。
- 直接处理报警时，该报警有且最多有一条有效最终处置型 `alarm_handle`。
- `alarm_handle` 不包含新增的 `status_before/status_after` 过程字段。
- 当前设计不提供完整工单流转历史查询。

## 8. 过时文档清理

以下文档不再作为实现依据：

- `10-最终设计口径确认.md`
- `11-确认后人工创建工单实施计划.md`

- `14-报警确认工单闭环最终执行计划.md`

过时原因：

- 它们把 `alarm_handle` 定位为多条动作时间线表。
- 它们要求确认、直接处理、创建工单、工单同步分别写多条 `alarm_handle`。
- 它们在 `alarm_handle` 上保留 `status_before/status_after` 等过程字段。
- 这与当前“工单只维护当前状态，关闭完成后最多形成一条最终 handle 处理记录”的需求冲突。

当前清理策略：

- README 已标记这些文档为过时。
- 后续实现只以本文档为准。
- 如果需要物理删除，可在确认后删除过时文档或移动到 `archive/`。

- 新增 `alarm_configure.push_enabled`。
- 新增 `alarm_configure.push_message_type`。
