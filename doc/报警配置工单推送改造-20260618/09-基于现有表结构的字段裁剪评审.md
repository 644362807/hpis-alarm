# 基于现有表结构的字段裁剪评审

本文件基于当前已有 SQL 表结构、现有 `hpis-alarm` 静态代码，以及《基于机器人平台的多源气体泄漏智能检测系统-系统方案详细设计文档》中“告警闭环流程”和“告警工单系统”部分进行评审。

本文件只记录字段裁剪、设计审核和后续实现边界，不包含 Java、XML、SQL 或配置文件修改。

## 1. 当前结论

本轮应收敛 `alarm` 表改动，不再把推送展示、工单处理、规则快照和设备缓存信息塞进报警事实表。

推荐裁剪后的方向：

- `alarm` 继续只表达报警事实和报警生命周期。
- `alarm_beginTime`、`alarm_endTime` 仍只表达报警开始和结束，不表达工单时间或处理时间。
- `alarm_configure_id` 是否落 `alarm` 需要二选一确认：
  - 最小改动口径：同一设备当前只允许绑定一种启用报警规则，则可不落库，通过 `device_sn + tenant_id + scene_type` 从绑定关系反查当前配置。
  - 可追溯口径：仍建议保留可空 `alarm_configure_id`，用于记录报警产生时命中的配置 ID，避免设备后续重新绑定后历史报警无法解释。
- `config_version` 本期不需要，`alarm` 和 `alarm_configure` 都不新增。
- `device_type` 本期不需要，从设备内存或设备缓存查询。
- `alarm_title`、`alarm_content` 不放 `alarm`，由推送配置负责推送标题和推送内容模板。
- `workorder_id` 不放 `alarm`，工单关联放到 `alarm_handle` 或工单实例表。
- `rule_snapshot_json`、`raw_payload_json` 暂不需要。

## 2. 现有表结构证据

### 2.1 alarm

当前 `alarm` 表已有字段可以支撑报警事实：

- `alarm_id`
- `device_sn`
- `alarm_type`
- `alarm_rank`
- `alarm_status`
- `scene_type`
- `alarm_beginTime`
- `alarm_endTime`
- `picture_path`
- `video_picture`
- `video_path`
- `alarm_cid`
- `irms_sn`
- `area_sn`
- `target_name`
- `tenant_id`
- `remark_data`

评审：

- `alarm_beginTime` 和 `alarm_endTime` 已经是报警生命周期字段。
- 当前代码和分片逻辑大量依赖 `alarm_beginTime` 做时间分片和查询路由。
- 不应把工单创建、接单、处理、关闭时间混入 `alarm_beginTime` 或 `alarm_endTime`。

### 2.2 alarm_configure

当前 `alarm_configure` 已有：

- `alarm_configure_id`
- `alarm_configure_name`
- `alarm_type`
- `device_sn`
- `device_alarm_control`
- `alarm_configure_period`
- `repeat_alarm_duration`
- `scene_type`
- `tenant_id`
- `repeat_cycle_number`

评审：

- 当前配置已能表达租户、行业、报警类型、开关和时间段。
- 如果先默认一个设备只绑定一种报警规则，配置命中逻辑可以先走 `alarm_device_configure.device_sn -> alarm_configure_id`。
- `config_version` 暂不新增后，历史追溯能力会弱化，需要在风险中明确接受。

### 2.3 alarm_device_configure

当前 `alarm_device_configure` 已有：

- `device_id`
- `alarm_configure_id`
- `device_sn`

评审：

- 当前表可以表达设备与报警配置绑定。
- 如果业务要求“一个设备只能有一种启用报警规则”，需要加唯一性或服务层校验，否则数据库仍允许一个 `device_sn` 绑定多个 `alarm_configure_id`。
- 若不加数据库唯一约束，至少在新增/修改配置绑定时校验同租户同设备有效绑定数量。

### 2.4 alarm_configure_time

当前 `alarm_configure_time` 已有：

- `alarm_configure_id`
- `alarm_configure_starttime`
- `alarm_configure_endtime`
- `del_flag`

评审：

- 可以继续支撑自定义生效时间。
- 当前没有主键，编辑单个时间段不方便；但本轮如只做最小改动，可以不补 `alarm_configure_time_id`。

### 2.5 alarm_handle

当前 `alarm_handle` 已有：

- `alarm_handle_id`
- `alarm_id`
- `handle_status`
- `identify`
- `opinion`
- `handler_id`
- `handle_picture`
- `handle_time`
- `confirm_user_id`
- `apparatus_id`
- `handler_name`
- `alarm_beginTime`

评审：

- 当前表已经承担确认、处理、误报、处理图片、处理意见等能力。
- 如果工单关联放 `alarm_handle`，需要新增 `workorder_id`。
- 如果工单转派、回退、催办要形成多条记录，不能继续只按 `alarm_id` 更新同一条处理记录，需要转为新增处理流水。

## 3. 修订后的字段建议

### 3.1 alarm 表

本轮不建议新增：

- `config_version`
- `device_type`
- `alarm_title`
- `alarm_content`
- `workorder_id`
- `rule_snapshot_json`
- `raw_payload_json`

待确认字段：

| 字段 | 建议 | 原因 |
| --- | --- | --- |
| `alarm_configure_id` | 二选一：最小改动可不加；追溯优先则保留可空字段 | 一个设备一种规则时可反查，但配置变更或重新绑定后历史解释会丢失。 |

如果保留 `alarm_configure_id`，它只表达“报警产生时命中的配置 ID”，不承担配置版本、推送标题、工单实例关联。

### 3.2 alarm_configure 表

不新增：

- `config_version`

仍建议保留或新增的配置侧字段需要单独按后续推送和工单需求确认：

- `push_message_type`
- `workorder_config_id`
- `is_device_sync`
- `config_device_type`
- `device_rule_json`
- `sync_status`
- `last_sync_time`
- `last_sync_result`

评审：

- `push_message_type` 仍是推送细分的主字段，不应改名。
- `workorder_config_id` 是否放在 `alarm_configure` 取决于是否需要“某类报警配置默认关联工单策略”。
- 如果你现在的业务是“手动确认后可选择生成工单”，则 `workorder_config_id` 可以不强依赖报警产生阶段，但仍可作为默认工单策略。

### 3.3 alarm_handle 表

建议新增：

| 字段 | 建议类型 | 功能 |
| --- | --- | --- |
| `workorder_id` | `bigint NULL` | 关联工单实例。确认、处理、工单流转记录都可按需带上。 |
| `handle_type` | `char(2) NULL` | 区分确认、处理、关闭、误报、转工单、工单同步、转派、回退等动作。 |
| `status_before` | `char(2) NULL` | 记录动作前报警或工单状态。 |
| `status_after` | `char(2) NULL` | 记录动作后报警或工单状态。 |

可暂缓：

- `source_type`
- `source_id`
- `attachments_json`
- `handle_result`

评审：

- 现有 `opinion`、`handle_picture` 已能承载基础处理意见和图片。
- 如果附件从一张图片扩展为多附件，再考虑 `attachments_json`。
- 如果 `workorder_id` 已能表达来源工单，`source_type/source_id` 可等到接入更多外部来源时再补。

### 3.4 工单实例表

现有 SQL 中没有 `alarm_workorder`。

如果要支持“确认后产生工单”，仍需要新增工单实例表，最小字段建议：

- `workorder_id`
- `workorder_no`
- `alarm_id`
- `status`
- `assignee_id`
- `assignee_name`
- `title`
- `content`
- `handle_result`
- `tenant_id`
- `del_flag`
- `create_time`
- `update_time`

关键约束：

- `alarm_id` 是否唯一取决于一条报警是否允许重复生成工单。
- 按你当前口径“一条报警最多一个工单实例”，建议 `alarm_id` 唯一。
- 转派、回退、催办不新增第二张工单，只写 `alarm_handle` 处理流水或后续独立工单流水。

## 4. 告警闭环流程适配

需求文档要求：

- 告警产生。
- 告警通知。
- 告警确认。
- 告警处理。
- 告警关闭。
- 告警归档。

修订后的落表建议：

| 流程 | 主表 | 说明 |
| --- | --- | --- |
| 告警产生 | `alarm` | 写报警事实、设备、类型、等级、开始时间。 |
| 告警通知 | 推送配置和推送日志 | 标题、内容由推送配置模板生成，不写入 `alarm`。 |
| 告警确认 | `alarm_handle` | 写确认动作、确认人、确认时间。 |
| 生成工单 | `alarm_workorder` + `alarm_handle` | 工单实例单独保存，`alarm_handle.workorder_id` 记录转工单动作。 |
| 告警处理 | `alarm_handle` + `alarm.alarm_status` | 有无工单都可以处理。 |
| 告警关闭 | `alarm.alarm_endTime` + `alarm_status` | 结束时间仍表达报警结束，不表达工单完成。 |
| 告警归档 | 查询/状态 | 不建议新增归档字段，先通过状态和时间查询。 |

## 5. 当前最大风险

### 5.1 一个设备一种规则没有最终约束

如果只在设计上默认“一个设备只能有一种报警规则”，但 DB 和服务层不校验，后续仍可能出现同一设备绑定多个配置。

建议：

- 服务层新增或修改绑定时校验同一 `tenant_id + device_sn` 下启用配置唯一。
- 如确认 DB 约束可接受，再考虑在绑定关系表补唯一键或重构绑定模型。

### 5.2 不保留 alarm_configure_id 会削弱历史追溯

如果 `alarm` 不保存 `alarm_configure_id`，历史报警只能按当前设备绑定关系反查配置。

风险：

- 配置删除后无法解释历史报警。
- 设备重新绑定配置后，历史报警会被错误解释为新配置。
- 后续排查“为什么产生工单/为什么推送给这些人”会缺证据。

低风险建议：

- 如果只加一个报警配置来源字段，优先保留 `alarm.alarm_configure_id`。
- 如果本期极限最小改动，可以不加，但需要在文档中明确接受追溯风险。

### 5.3 alarm_handle 现在更像状态记录，不是完整流水

当前 Mapper 的 `updateAlarmHandle` 以 `alarm_id` 为主更新，适合更新当前处理状态，不适合记录多次转派、回退、催办。

建议：

- 确认、处理、转工单、转派等动作优先新增 `alarm_handle` 记录。
- 修改单条流水时按 `alarm_handle_id` 更新。
- 保留按 `alarm_id` 批量更新只用于旧确认/处理接口兼容。

### 5.4 工单标题和内容放推送配置需要边界

你提出 `alarm_title`、`alarm_content` 放入推送配置处理，这对通知展示是合理的。

但工单也需要标题和内容：

- 推送标题、推送内容属于 `active_push_config` 或推送模板。
- 工单标题、工单描述应属于 `alarm_workorder` 或工单配置模板。

不建议让推送配置同时承担工单标题模板，否则推送和工单会强耦合。

## 6. 推荐的低风险第一步

第一步只做设计裁剪确认和配置命中：

- 暂不新增 `config_version`。
- 暂不新增 `device_type`。
- 暂不新增 `alarm_title`、`alarm_content`。
- 暂不新增 `workorder_id` 到 `alarm`。
- 暂不新增 `rule_snapshot_json`、`raw_payload_json`。
- 明确 `alarm_configure_id` 是否保留。
- 新增或保留 `push_message_type` 在配置侧，用于推送细分。
- 明确工单关联放 `alarm_handle.workorder_id`。

## 7. 后续第二步、第三步

第二步：推送配置增强。

- 推送标题和内容模板放推送配置侧。
- `alarm` after-commit payload 只传基础报警事实和 `pushMessageType`。
- 推送服务按设备、行业、推送细分匹配配置。

第三步：确认后工单闭环。

- 新增 `alarm_workorder`。
- 支持手动确认后生成工单。
- 有无工单都允许报警处理。
- 工单转派、回退、催办写 `alarm_handle` 或后续独立工单流水，不新增第二张工单。

## 8. 验收标准

- 报警产生后 `alarm_beginTime` 仍用于报警时间和分片路由。
- 报警关闭后 `alarm_endTime` 仍只表达报警结束。
- 不新增的字段不会出现在 Mapper insert、batch insert、分片建表和迁移脚本中。
- 同一设备多配置绑定被服务层拦截或明确允许按优先级处理。
- 手动确认后可以生成工单。
- 未生成工单的报警仍可处理。
- 工单转派不会创建第二张工单实例。
- 多次处理或转派不会覆盖历史处理记录。

## 9. 实现前必须确认

1. `alarm.alarm_configure_id` 是否保留可空字段，还是本期完全不加。
2. “一个设备只能有一种报警规则”是全局唯一，还是按 `tenant_id + scene_type + device_sn` 唯一。
3. 一个设备是否还允许不同 `alarm_type` 配不同规则。
4. 推送配置里的标题和内容是否只服务推送，不服务工单。
5. 工单标题和工单内容是否需要独立工单模板字段。
6. `alarm_handle` 是否允许一条报警多条记录作为流水。
