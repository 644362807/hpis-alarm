# 已有文档复核与设计补充建议

本文件基于当前目录 01-07 文档、《报警配置最小改动方案设计文档》和《基于机器人平台的多源气体泄漏智能检测系统-系统方案详细设计文档》进行复核。

本文件只记录设计评审、补充建议和后续确认项，不包含 SQL 执行、Java/XML 修改或配置变更。

## 1. 复核结论

当前迭代路线整体符合“最小改动、分阶段上线、保留旧链路兼容”的方向，可以作为后续代码实现计划。

已对齐的关键点：

- 不新增额外推送细分、处理模式等主链路字段。
- `alarm_configure.push_message_type` 作为唯一推送细分字段，映射 `active_push_config.message_type`。
- 工单能力通过 `alarm_configure.workorder_config_id` 和 `alarm_workorder_config.create_mode` 推导。
- `alarm_handle` 继续作为统一处理流水，不新增 `alarm_workorder_handle`。
- 当前按一条报警最多一个 `alarm_workorder` 设计。
- 推送增强保留旧 `deviceSn#messageType` 兼容路径。
- 设备级和行业级同时命中时采用 `UNION`，按 `active_push_config_id` 去重。

### 2.2 范围边界一致

当前 01-07 文档没有扩大原始最小改动方案的边界：

- 未要求建设完整策略引擎。
- 未要求拆分不同设备类型的报警配置明细表。
- 未要求新增报警配置和推送配置强关联表。
- 未要求一条报警多工单。
- 未要求修改 RabbitMQ 队列名和 ack/nack 语义。

### 2.3 业务目标一致

整体需求文档强调“告警生成、预警通知、工单派发、处理反馈、归档统计”的闭环。当前迭代路线将该目标拆成三期：

1. 报警配置命中和字段落库。
2. 推送路由增强。
3. 工单闭环。

这种拆分能降低一次性改动风险，也方便每期独立验收。

## 3. 需要补强的设计点

### 3.1 行业级推送配置的 DB 来源仍需明确

当前文档确定行业级推送优先通过 Redis key 语义实现：

- `SCENE:{sceneType}#pushMessageType`
- `SCENE:{sceneType}#*`

但 `pushConfigId_deviceSn` 本期不强制扩表，`active_push_config` 当前字段也只明确了 `message_type`、`push_channel_type` 和可选 `bind_ip`。

需要在实现前确认行业级 Redis key 的来源：

- 是从 `active_push_config` 现有行业字段、适用范围字段或租户配置字段生成。
- 还是先在服务层按某种现有配置关系推导。
- 如果当前 DB 完全无法表达行业级推送范围，则不能只加 Redis key，需要补充最小范围字段或独立范围表评审。

建议：

- 第一版实现前先静态确认 `hpis-push` 的 `active_push_config` 实际字段。
- 如果已有可表达行业/场景的字段，则文档补充字段名和取值规则。
- 如果没有，避免把行业级配置只做成“缓存态能力”，否则 Redis 重建后无法从 DB 恢复。

### 3.2 报警配置匹配“唯一命中”与推送路由“多级合并”要继续分开

当前文档中有两类规则：

- 报警配置命中：设备+报警类型 > 行业+报警类型 > 行业+全部报警。
- 推送配置命中：设备级、行业级、行业全部报警同时查询，`UNION` 去重。

这个设计是合理的，但实现时容易混淆。

建议：

- 报警配置解析器只返回一个最优 `alarm_configure`。
- 推送路由解析器返回多个 `active_push_config_id`。
- 日志中分别使用 `alarm_config_match` 和 `push_route_match` 一类的阶段标识，避免排查时混为一谈。

### 3.3 `alarm_workorder.alarm_id` 唯一约束需要确认逻辑删除口径

当前文档建议：

- `alarm_workorder.alarm_id` 唯一。
- 一条报警最多一个工单实例。
- 转派不新增第二张工单。

需要明确：

- 如果工单被取消或逻辑删除，是否允许同一报警重新生成工单。
- 如果不允许，`UNIQUE KEY uk_alarm_workorder_alarm (alarm_id)` 就足够。
- 如果允许，需要重新评审“一警一单”的业务约束，不能直接在唯一键中加入 `del_flag` 绕过。

建议本期保持更严格口径：

- 同一 `alarm_id` 永远最多一条 `alarm_workorder`。
- 取消、退回、转派都通过状态和处理流水表达。
- 不通过逻辑删除制造第二张工单。

### 3.4 `config_version` 递增条件需要收敛

07 文档已经写明影响报警产生、推送或工单行为的配置变更应递增版本。

建议在后续实现清单中再明确必须递增的变更类型：

- `alarm_type`
- `push_message_type`
- `config_device_type`
- `device_rule_json`
- `workorder_config_id`
- 绑定设备范围
- 生效时间段
- 启用/禁用状态

不建议由前端传入最终版本号，版本递增应由服务层控制。

### 3.5 `raw_payload_json` 需要控制体积和敏感字段

整体需求包含视频、图片、设备位置、告警详情等信息。`raw_payload_json` 用于排查是必要的，但不能无限保存所有上报内容。

建议：

- 保存报警触发所需的核心原始字段。
- 大图片、视频、附件只保存 URL 或资源 ID。
- 避免保存鉴权 token、内部通信密钥、完整用户隐私数据。
- 对超长 payload 设置截断或落附件策略。

### 3.6 Redis 路由重建能力需要成为验收项

风险文档已经记录 Redis 与 DB 不一致会漏推。

建议把以下内容加入后续实现验收：

- 支持按租户重建推送路由缓存。
- 支持按配置 ID 重建单个推送配置缓存。
- 重建逻辑必须能覆盖设备级、行业级、行业全部报警和旧兼容 key。
- 缓存重建失败时不影响报警入库，只影响推送并记录明确日志。

## 4. 推荐的低风险实现顺序

### 第一步：只做报警配置命中和报警事实追溯

改动目标：

- 补字段。
- 补 Mapper。
- 补分片建表。
- 新增配置解析组件。
- 报警入库写入 `alarm_configure_id`、`config_version`、`push_message_type` 对应 payload 字段、规则快照。

暂不做：

- 不自动生成工单。
- 不改变推送服务路由。
- 不改变 MQ ack/nack。

验收重点：

- 未命中配置时报警仍能入库。
- 单条和批量报警都能写新增字段。
- 分片新建表字段完整。

### 第二步：只做推送 Redis 路由增强

改动目标：

- 保留旧 `deviceSn#messageType`。
- 增加 `deviceSn#pushMessageType`。
- 增加行业级和行业全部报警 key。
- 合并去重并防空指针。

前置确认：

- 行业级路由从 DB 哪些字段重建。
- Redis key 常量和重建入口。

验收重点：

- 无 key、空 key、配置禁用、配置删除都不影响消费线程。
- 三类路由同时命中时按配置 ID 去重。
- 旧 payload 仍可消费。

### 第三步：只做自动工单最小闭环

改动目标：

- 新增 `alarm_workorder_config`。
- 新增 `alarm_workorder`。
- 只实现 `create_mode=1` 自动生成。
- 工单创建后回写 `alarm.workorder_id`。
- 工单状态变化写 `alarm_handle`。

暂不做：

- 不做复杂流转引擎。
- 不做一警多单。
- 不做完整 SLA 体系。

验收重点：

- 同一报警重复触发只生成一张工单。
- 唯一键冲突按幂等成功或可恢复异常处理。
- 工单转派不新增第二张工单。

## 5. 当前最大风险排序

| 优先级 | 风险 | 原因 | 建议处理 |
| --- | --- | --- | --- |
| P0 | 行业级推送只存在 Redis 语义，DB 无法重建 | Redis 缓存丢失后会漏推 | 实现前确认 DB 来源字段或补最小范围模型 |
| P0 | 分片表缺字段 | 报警主链路写入失败 | 第一阶段必须同步基础表、物理表、建表逻辑、批量 SQL |
| P0 | 工单幂等不足 | MQ 重投或并发导致一警多单 | `alarm_workorder.alarm_id` 唯一，唯一冲突按幂等处理 |
| P1 | 报警配置唯一命中和推送多级合并混淆 | 可能导致错误配置来源或重复推送 | 两个 resolver 分开实现，日志阶段分开 |
| P1 | Redis 与 DB 不一致 | 漏推或误推 | 增加缓存重建、禁用清理和路由 miss 日志 |
| P1 | `raw_payload_json` 过大 | 影响存储和查询性能 | 限制字段、附件外置、必要时截断 |
| P2 | `config_version` 由多处维护 | 历史追溯不可信 | 服务层统一递增，不让前端决定版本 |

## 7. 实现前必须回答的问题

1. `hpis-push` 当前是否已有字段能表达行业级推送范围。
2. 行业级推送配置禁用或删除后，如何从 DB 找到并清理对应 Redis key。
3. 同一报警的工单取消后，是否仍禁止再次生成工单。
4. `config_version` 是否由服务端统一递增，前端只提交业务字段。
5. `raw_payload_json` 是否需要限制最大长度或过滤敏感字段。

## 8. 结论

当前设计可以进入第一阶段实现，但不建议直接同时实现三期。

第一阶段应优先完成报警配置命中、字段落库、分片字段同步和 payload 兼容；推送行业级路由必须在确认 DB 可重建来源后再进入第二阶段；工单闭环应作为第三阶段独立上线，依赖唯一约束和幂等处理兜底。
