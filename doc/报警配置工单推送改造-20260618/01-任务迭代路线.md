# 任务迭代路线

本文件只记录后续代码编写路线和验收口径，不包含代码实现。

## 当前问题

- 报警配置字段不足以直接支撑配置来源、推送细分和工单配置。
- 报警入库后无法稳定追溯命中的 `alarm_configure` 和配置版本。
- 推送侧当前以 `deviceSn#messageType` 为核心路由，缺少行业级和行业全部报警的路由语义。
- 工单表和工单服务未落地，报警到工单闭环尚未形成。

## 第一阶段：报警配置命中与字段落库

目标：

- 按设计文档扩展报警配置、报警事实和报警处理字段。
- 在报警入库链路中识别命中的报警配置。
- 将配置来源、配置版本、推送细分和规则快照写入报警事实。
- 保持现有 MQ、HTTP 入参和旧推送 payload 基础结构兼容。

输入：

- 设备或边缘端上报的报警 JSON。
- 当前设备信息、租户、行业 `sceneType`、设备 SN、报警类型。
- `alarm_configure`、`alarm_configure_time`、`alarm_device_configure`。

输出：

- `alarm.alarm_configure_id`。
- `alarm.config_version`。
- `alarm.device_type`。
- `alarm.rule_snapshot_json`。
- `alarm.raw_payload_json`。
- after-commit 推送 payload 中的 `pushMessageType`。

完成标准：

- 设备+报警类型配置优先命中。
- 行业+报警类型配置可覆盖该行业下全部设备。
- 行业+全部报警配置可覆盖该行业下全部报警类型。
- 未启用、已删除、非生效时间段配置不命中。
- 未命中配置时保留旧报警入库行为，不阻断报警主链路。

暂不做：

- 不引入完整策略引擎。
- 不拆分设备类型专属配置表。
- 不改变 MQ ack 语义。
- 不改变 stop 可靠关闭主链路。

## 第二阶段：推送路由增强

目标：

- 保留当前 `deviceSn#messageType` 兼容路径。
- 将 `push_message_type` 作为推送细分使用。
- 增加行业级和行业全部报警路由。
- 设备级和行业级同时命中时执行 `UNION`，按 `active_push_config_id` 去重。

输入：

- 报警服务 after-commit 推送 payload。
- `deviceSn`、`sceneType`、`pushMessageType`。
- `active_push_config` 和 `pushConfigId_deviceSn`。
- 推送服务 Redis 配置缓存。

输出：

- 去重后的 `active_push_config_id` 列表。
- 对应配置队列或推送消费者的投递结果。
- 可排查的推送匹配日志。

完成标准：

- 设备级配置可命中指定设备。
- 行业级配置可命中该行业下全部设备。
- 行业全部报警配置可命中该行业下全部报警类型。
- 多级配置同时命中时不重复推送同一个配置 ID。
- Redis 无 key、空列表、无配置时不抛异常。
- 没有 `pushMessageType` 时回退旧 `messageType`。

暂不做：

- 不新增报警配置与推送配置的强关联表。
- 不调整 RabbitMQ 队列名。
- 不改变已有 WebSocket、HTTP、MQTT 推送消费者协议。

## 第三阶段：报警工单闭环

目标：

- 新增工单配置和报警工单实例。
- 支持报警产生后自动生成工单。
- 支持工单处理结果通过 `alarm_handle` 同步记录。
- 保证同一报警最多一个工单实例。

输入：

- 命中的 `alarm_configure.workorder_config_id`。
- `alarm_workorder_config`。
- 已持久化的 `alarm`。

输出：

- `alarm_workorder` 工单实例。
- `alarm.workorder_id`。
- `alarm_handle` 工单同步或转派处理流水。

完成标准：

- `create_mode=1` 可在报警生成后自动创建工单。
- 同一报警重复消费不会创建第二个工单实例。
- 工单转派只新增处理或流转记录，不新增第二张工单。
- 工单关闭后按 `auto_close_alarm` 决定是否关闭报警。

暂不做：

- `create_mode=2` 手动转工单和 `create_mode=3` 确认后生成工单可后续迭代。
- 不建设独立复杂工单流转引擎。
- 不新增多工单关联表。
