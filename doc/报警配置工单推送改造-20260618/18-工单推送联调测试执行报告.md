# 工单推送联调测试执行报告

## 1. 结论

本轮 `alarm_configure -> 报警创建 -> 报警确认 -> 创建工单 -> PUSH_ALARM -> push 按 payload 顶层 messageType 路由` 联调测试已完成。

结论范围只覆盖“报警确认后创建工单时的工单创建推送”。转派、退回、完成、关闭等后续工单动作推送不在本轮范围内。

本轮联调的关键结论：

- alarm 能在工单创建成功后，根据 `alarm_configure.workorder_push_message_type=25` 发送顶层 `messageType=25` 的 `PUSH_ALARM` 消息。
- `workorder_push_message_type` 为空、`push.open=false`、重复建单或 `DuplicateKeyException` 时，不发送工单创建推送。
- push 能消费实际队列 `push.alarm`，优先读取 payload 顶层 `messageType`。
- push 以 `deviceSn#messageType` 匹配配置，`messageType=25` 只命中工单推送配置，不回退、不误用 `messageType=22` 的报警推送配置。
- 接收人和通道由 push 配置决定，alarm 只负责发送 `messageType` 和业务 payload。
- push 通道异常不影响 alarm 工单创建事务。

## 5. 前置配置

### 5.1 alarm 配置

核心配置：

```sql
update alarm_configure
set push_enabled = '1',
    push_message_type = '22',
    workorder_push_message_type = '25',
    workorder_config_id = 900
where alarm_configure_name = 'codex-workorder-push-base'
  and tenant_id = 990001;
```

说明：

- `push_message_type=22`：报警产生后的报警推送类型。
- `workorder_push_message_type=25`：报警确认创建工单后的工单创建推送类型。
- `workorder_push_message_type` 为空时，工单仍创建，但不发工单创建推送。

### 5.2 push 配置

通过 `POST /pushConfig/add` 创建两类配置：

| messageType | configName | 接收地址 | 用途 |
| --- | --- | --- | --- |
| `22` | `codex-workorder-alarm-22-A` | `127.0.0.1:19022/codex/alarm-22` | 报警推送配置 |
| `25` | `codex-workorder-workorder-25-B` | `127.0.0.1:19025/codex/workorder-25` | 工单创建推送配置 |

push 配置生成的 Redis 路由示例：

```json
{
  "CODX-WO-PUSH-DEV-001#22": [2074143982048923648],
  "CODX-WO-PUSH-DEV-001#25": [2074143985391783936]
}
```

该路由是本轮判断“22 和 25 不互相覆盖”的关键指标。缺失 `deviceSn#25` 时，push 不应回退到 `deviceSn#22`。

## 7. push 侧最小修复和静态确认

本轮首次联调失败层位于 push 消费边界，不是 alarm 建单或 alarm 发 MQ。

失败现象：

```text
MessageConversionException:
Failed to convert message payload '{... "messageType":"25" ...}' to '[B'
```

原因：

- push 的 Rabbit 监听方法原先使用 `byte[]` 入参。
- 真实 `push.alarm` JSON 消息投递时，Spring AMQP 未能把消息转换成 `byte[]`，导致消费方法未进入业务逻辑。
- 因此 push 还没有机会读取顶层 `messageType=25`，也不会进入配置路由。

最小修复：

```java
public void listenMultiQueueMessage(Message message,
                                    @Header(AmqpHeaders.RECEIVED_ROUTING_KEY) String queueName) {
    String msg = new String(message.getBody(), StandardCharsets.UTF_8);
    MessageReception(msg, queueName);
}
```

保留原有路由语义：

```java
case "push.alarm":
    messageType = msgJson.getString("messageType");
    if (messageType == null || messageType.trim().isEmpty()) {
        messageType = MessageTypeEnums.ALARM_PUSH_TYPE.getKey();
    }
    break;
```

静态确认结论：

| 检查项 | 结果 |
| --- | --- |
| `PUSH_ALARM` 实际队列是否为 `push.alarm` | PASS |
| push 是否消费 `push.alarm` | PASS |
| push 是否优先读取顶层 `messageType` | PASS |
| 是否只读 `data.messageType` | PASS，未发现只读嵌套字段问题 |
| 是否强制覆盖为默认报警类型 | PASS，仅缺失顶层 `messageType` 时回退 |
| 路由 key 是否为 `deviceSn#messageType` | PASS |
| 缺少 `deviceSn#25` 时是否回退到 `deviceSn#22` | PASS，不回退 |

## 8. 联调执行流程

每个正向用例按以下链路执行：

1. 写入 Redis 登录态、租户、设备缓存。
2. 插入或更新 `alarm_configure` 和 `alarm_device_configure`。
3. 通过 push API 创建 `messageType=22` 和 `messageType=25` 配置。
4. 启动 `19022/19025` 本地 HTTP 接收器。
5. 调用 `POST /alarm/alarmAdd` 产生报警。
6. 查询 `alarm_cid_index` 获取内部 `alarm_id` 和分表后缀。
7. 调用 `POST /handle/update` 确认报警。
8. 调用 `POST /workorder` 创建工单。
9. 校验 `alarm_workorder`。
10. 校验 alarm 日志中的 `PUSH_ALARM` payload 顶层 `messageType`。
11. 校验 push 消费日志、Redis 路由、配置队列。
12. 校验 `19025` 是否收到工单创建推送，`19022` 是否未收到工单创建推送。

工单创建推送 payload 示例：

```json
{
  "messageType": "25",
  "tenantId": 990001,
  "deviceSn": "CODX-WO-PUSH-DEV-001",
  "alarmId": 669347494618120969,
  "workorderId": 1,
  "workorderNo": "WO-CODX-WO-PUSH-case1-669347494618120969",
  "workorderConfigId": 900,
  "status": "0",
  "data": {
    "eventType": "ALARM_WORKORDER_CREATED"
  }
}
```

本地接收器收到的通道样例：

```text
port=19025
path=/codex/workorder-25
method=POST
body.messageType=25
body.deviceSn=CODX-WO-PUSH-DEV-001
body.data.eventType=ALARM_WORKORDER_CREATED
```

负向通道断言：

```text
receiver-19022.jsonl 不应出现 data.eventType=ALARM_WORKORDER_CREATED
receiver-19025.jsonl 在 Case 2/3/4/6 不应新增工单创建请求
```

## 12. 失败归因规则

后续如果联调失败，按以下层级归因：

| 失败现象 | 优先归因层 |
| --- | --- |
| `alarm_configure` 未读到 `workorder_push_message_type` | alarm 配置层 |
| `/workorder` 未生成 `alarm_workorder` | alarm 建单层 |
| 工单生成但无 MQ 日志，且 `push.open=true` | alarm 发 MQ 层 |
| MQ 有消息但 push 无消费日志 | RabbitMQ 或 push 消费层 |
| push 消费后解析成默认报警类型 | push `messageType` 解析层 |
| push 解析 25 但未找到配置 | push 配置匹配或 Redis 路由层 |
| 命中配置但接收人不对 | push 接收人解析层 |
| 命中配置但 HTTP/MQTT/WS 失败 | push 通道发送层 |
| push 通道失败导致 alarm 建单回滚 | 事务边界设计问题，应修复 |

## 13. 后续建议

本轮不建议做大范围重构。保留当前最小修复即可。

建议补充的最小后续项：

1. 将 `RabbitMultiQueueListenerTest` 保留为 push 的回归门禁，防止 `messageType=25` 再次被默认报警类型覆盖。
2. 在 push 未命中 `deviceSn#messageType` 路由时，日志中固定输出 `tenantId/deviceSn/messageType`，便于 Case 4 这类问题定位。
3. 对 alarm 报警创建推送 `push_message_type=22` 单独补一个端到端用例；本轮重点是工单创建推送 25，不扩大范围。
