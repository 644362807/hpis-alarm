# 问答确认后的设计修改方案

## 1. 当前问题

当前几轮确认后，需要把报警配置、报警推送过滤、报警工单、报警处理记录的职责重新收敛：

- 当前代码尚不支持基于 `alarm_configure` 的报警推送过滤。
- 旧设计曾把 `alarm_handle` 设计成多动作过程表，包含确认、创建工单、工单同步等动作记录。
- 当前已确认 `alarm_handle` 不是过程表，而是报警最终处置记录表。
- 当前已确认一条报警最多一个工单。
- 当前已确认工单不需要完整流转历史，转派直接更新 `alarm_workorder` 当前负责人和状态。
- 当前已确认不需要新增 `alarm_workorder_flow`。

## 2. 最终设计目标

本次设计以最小改动满足以下能力：

- 报警配置可以控制某类报警是否进入推送。
- 报警配置可以指定推送策略编码。
- 报警确认后可以直接处理，也可以按配置创建工单。
- 一个报警最多对应一个工单。
- 一个报警最多形成一条有效最终处置型 `alarm_handle`。
- 工单创建、接单、转派、退回不写 `alarm_handle`。
- 工单关闭或完成后，才同步一条最终处置型 `alarm_handle`。
- 工单转派不保留完整历史，只更新 `alarm_workorder` 当前负责人和状态。

## 3. 表职责

| 表 | 职责 |
| --- | --- |
| `alarm` | 报警事实表，只保存报警发生、状态、开始结束时间、设备、类型、租户等事实。 |
| `alarm_configure` | 报警规则配置表，承载推送开关、推送策略编码和可选工单模板。 |
| `alarm_workorder` | 报警工单表，一个报警最多一张工单，保存当前工单状态、当前负责人、处理结果。 |
| `alarm_handle` | 报警最终处置记录表，直接处理或工单处理完成后最多写一条有效记录。 |

明确不新增：

- 不新增 `alarm_workorder_flow`。
- 不新增 `alarm.workorder_id`。
- 不新增 `alarm.alarm_configure_id`。
- 不新增 `alarm.config_version`。

## 4. 数据库修改方案

### 4.1 `alarm_configure`

新增：

```sql
ALTER TABLE alarm_configure
  ADD COLUMN push_enabled char(1) NOT NULL DEFAULT '1'
    COMMENT '是否进入报警推送：0不推送 1推送',
  ADD COLUMN push_message_type varchar(30) NULL
    COMMENT '推送策略编码，对应推送配置 message_type；为空时回退 alarm_type',
  ADD COLUMN workorder_config_id bigint NULL
    COMMENT '关联报警工单模板ID，为空表示确认后不能按模板创建工单';
```

字段意图：

- `push_enabled`：控制报警是否进入推送链路；不影响报警入库。
- `push_message_type`：控制推送策略编码；不表示是否推送。
- `workorder_config_id`：控制该报警配置是否允许创建工单；不表示自动建单。

### 4.2 `alarm_handle`

`alarm_handle` 当前定位是最终处置记录表，不是过程表。

最小新增：

```sql
ALTER TABLE alarm_handle
  ADD COLUMN workorder_id bigint NULL
    COMMENT '关联工单ID，直接处理为空，工单处理完成时填写';
```

不新增：

- `status_before`
- `status_after`
- `handle_type=CONFIRM`
- `handle_type=CREATE_WORKORDER`
- `handle_type=WORKORDER_SYNC`

`handle_type` 本次确定不新增：

- 直接处理和工单处理通过 `workorder_id` 区分。
- `workorder_id` 为空表示报警侧直接处理。
- `workorder_id` 非空表示工单处理完成。
- 后续如页面或报表确实需要显式处置方式，再另行评审，不在本次 DDL 中预留。

`handle_status` 的定位：

- `handle_status` 表示报警最终处理后的结果状态。
- 它不是动作类型。
- 它不承担工单流转状态。

### 4.3 `alarm_workorder`

新增工单事实表：

```sql
CREATE TABLE IF NOT EXISTS alarm_workorder (
  workorder_id bigint NOT NULL COMMENT '工单ID',
  workorder_no varchar(50) NOT NULL COMMENT '工单编号',
  alarm_id bigint NOT NULL COMMENT '报警ID',
  workorder_config_id bigint NULL COMMENT '来源工单模板ID',
  status char(2) NOT NULL DEFAULT '0' COMMENT '工单状态：0待处理 1处理中 2已完成 3已关闭 4退回',
  assignee_id bigint NULL COMMENT '当前负责人ID',
  assignee_name varchar(100) NULL COMMENT '当前负责人名称',
  title varchar(200) NULL COMMENT '工单标题',
  content varchar(1000) NULL COMMENT '工单内容',
  handle_result varchar(500) NULL COMMENT '工单处理结果',
  tenant_id bigint NULL COMMENT '租户ID',
  del_flag char(2) DEFAULT '0' COMMENT '逻辑删除：0存在 2删除',
  create_by varchar(64) NULL COMMENT '创建人',
  create_time datetime DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  update_by varchar(64) NULL COMMENT '更新人',
  update_time datetime NULL DEFAULT NULL ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  PRIMARY KEY (workorder_id),
  UNIQUE KEY uk_alarm_workorder_alarm (alarm_id),
  UNIQUE KEY uk_alarm_workorder_no (workorder_no),
  KEY idx_alarm_workorder_status (tenant_id, status, create_time),
  KEY idx_alarm_workorder_assignee (assignee_id, status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='报警工单表';
```

关键约束：

- `uk_alarm_workorder_alarm(alarm_id)` 是一警一单的数据库兜底。
- 转派不新增历史表，只更新当前负责人字段。
- 工单关闭或完成后才同步最终处理结果到 `alarm_handle`。

## 5. 业务流程

### 5.1 报警产生与推送过滤

1. 报警按现有逻辑入库。
2. 入库成功后，在 after-commit 推送前解析当前报警配置。
3. 如果命中配置且 `push_enabled=0`，跳过报警推送。
4. 如果 `push_enabled=1` 或未命中禁推配置，继续现有推送。
5. 推送 `messageType` 优先使用 `push_message_type`，为空回退 `alarm_type`。

注意：

- 不改变 MQ 消费入口。
- 不改变报警入库顺序。
- 不改变 `push.open` 全局开关。
- 不改变旧 push payload 主结构。

### 5.2 报警确认

确认报警只改变报警确认状态，不写最终处置型 `alarm_handle`。

确认后有两个分支：

- 直接处理报警。
- 按 `alarm_configure.workorder_config_id` 创建工单。

### 5.3 直接处理

直接处理报警时：

- 写入或更新一条最终处置型 `alarm_handle`。
- `workorder_id` 为空。
- `handle_status` 表示最终处理后的状态。
- `opinion`、`handle_picture`、`handle_time` 保存处理结果。

### 5.4 创建工单

创建工单时：

1. 校验报警已确认。
2. 重新解析当前报警配置。
3. `workorder_config_id` 为空时禁止创建工单。
4. 插入 `alarm_workorder`。
5. 依赖 `uk_alarm_workorder_alarm(alarm_id)` 防止重复建单。
6. 创建工单不写 `alarm_handle`。
7. 创建工单不回写 `alarm.workorder_id`。

### 5.5 工单接单、转派、退回

这些动作只更新 `alarm_workorder` 当前事实：

- `status`
- `assignee_id`
- `assignee_name`
- `update_by`
- `update_time`

这些动作不写：

- 不写 `alarm_handle`。
- 不写 `alarm_workorder_flow`。
- 不保留完整流转历史。

### 5.6 工单关闭或完成

工单关闭或完成时：

1. 更新 `alarm_workorder.status` 和 `handle_result`。
2. 写入或更新一条最终处置型 `alarm_handle`。
3. `alarm_handle.workorder_id` 填当前工单 ID。
4. `alarm_handle.opinion` 写工单处理结果摘要。
5. 同一报警最多保留一条有效最终处置记录。

## 7. 明确不做

- 不新增 `alarm_workorder_flow`。
- 不保存完整工单流转历史。
- 不把 `alarm_handle` 改成多动作时间线。
- 不让确认报警写一条 `alarm_handle`。
- 不让创建工单写一条 `alarm_handle`。
- 不让转派、接单、退回写 `alarm_handle`。
- 不在 `alarm_handle` 新增 `status_before/status_after`。
- 不在 `alarm` 新增 `workorder_id`。
- 不改变 MQ ack/nack。
- 不改变报警 stop 闭环。
- 不重写推送 payload 主结构。

## 8. 分阶段实施建议

### 第一阶段：报警推送过滤

目标：

- 先解决“什么类型过滤掉不进入报警推送”。

内容：

- 增加 `alarm_configure.push_enabled`。
- 增加 `alarm_configure.push_message_type`。
- `AlarmServiceImpl` after-commit 推送前按配置跳过或继续推送。

风险控制：

- 报警仍然入库。
- 只影响推送分支。
- `push.open` 全局开关仍保留。

### 第二阶段：一警一单

目标：

- 支持确认后按配置创建工单。

内容：

- 增加 `alarm_configure.workorder_config_id`。
- 新增 `alarm_workorder` 表和服务。
- 用 `uk_alarm_workorder_alarm(alarm_id)` 保证一警一单。
- 创建工单不写 `alarm_handle`。

风险控制：

- 创建工单前重新解析配置。
- 重复建单依赖数据库唯一键兜底。
- 不改报警主表结构。

### 第三阶段：最终处置型 `alarm_handle`

目标：

- 统一直接处理和工单完成后的最终处置记录。

内容：

- `alarm_handle` 增加 `workorder_id`。
- 直接处理写最终处置记录。
- 工单关闭或完成写最终处置记录。
- 同一报警最多一条有效处置记录。

风险控制：

- 不新增过程字段。
- 不引入多条 handle 动作流水。
- 已有查询继续兼容 `handle_status`、`identify`、`opinion`。

## 9. 验收标准

- `push_enabled=0` 的报警照常入库，但不进入报警推送。
- `push_enabled=1` 的报警继续推送。
- `push_message_type` 有值时用于推送策略；为空回退 `alarm_type`。
- 确认报警不新增最终处置型 `alarm_handle`。
- 创建工单不新增 `alarm_handle`。
- 同一报警重复创建工单不会生成第二张工单。
- 工单转派只更新 `alarm_workorder` 当前负责人和状态。
- 工单关闭或完成后，该报警有且最多有一条有效最终处置型 `alarm_handle`。
- 直接处理报警后，该报警有且最多有一条有效最终处置型 `alarm_handle`。
- `alarm_handle` 不包含新增的 `status_before/status_after`。
- 当前设计不提供完整工单流转历史查询。

## 10. 回滚策略

- 推送过滤异常时，可先将 `alarm_configure.push_enabled` 统一置为 `1`，恢复全部推送。
- 推送策略异常时，可清空 `push_message_type`，回退使用 `alarm_type`。
- 工单功能异常时，可关闭创建工单入口，不影响报警入库、确认和直接处理。
- `alarm_handle.workorder_id` 为补充关联字段，回滚业务逻辑时可保留字段不读写。
