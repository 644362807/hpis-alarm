# 本轮修改记录：2w MQ/min 最小优化

## 背景

当前报警链路已经完成 consumer batch、SQL 500 条硬边界和 stop event `PROCESSING + lock_token` 认领改造。真实压测仍显示 start 持久化、逐条 stop event upsert、电解槽快照竞争和 stop 闭环可见性存在继续优化空间。

本轮只实施低风险最小修改，用于验证 `20000 MQ/min` 目标。MQ 消息体、Redis key、push payload 和公开接口保持不变。

## 修改范围

### Stop 连续消息聚批

- batch listener 对连续 stop 消息按默认 `100` 条聚合调用 `recordStops(List<AlarmStopRecord>)`。
- `alarm_stop_event` 使用 multi-values upsert，单次 SQL 继续受 `500` 条硬边界保护。
- 聚批成功后逐条 ack；瞬态数据库异常时整批 requeue，不在消费线程展开无界逐条 SQL。
- stop event 支持 `initialAvailableDelayMs`，用于给 start route 提交留出短暂可见窗口。默认值为 `0` 保持兼容，灰度建议从 `200ms` 开始。

### 最新 stop_time 一致性

- `alarm_stop_event` 新增 `event_version` 和 `applied_stop_time`。
- 重复 stop 到达时保留更晚的 `stop_time`。
- 已经 `APPLIED` 的事件收到更晚 stop 时会重新进入 `PENDING`，避免最终主表停留在旧结束时间。
- worker 完成时按 `PROCESSING + lock_token + event_version` 更新；影响行数不等于预期数量时立即回滚，旧线程不能误标新版本事件。

### Start 电解槽快照止血

- 新增 `alarm.batch.electrolyticSnapshotBatchSize`，默认 `100`。电解槽当前点位快照按该上限切块 upsert。
- start 持久化增加 handle、扩展历史表、ectype 快照、主表、route 和补偿处理的分阶段耗时日志。
- start 单条成功阶段日志默认关闭，只保留批次级 Profiling。排查单条链路时可短时开启 `insertItemProfileLogEnabled`，避免 2w MQ/min 下日志 IO 反向成为瓶颈。
- ectype 快照等 start 持久化遇到死锁或锁获取失败时，复用已准备上下文，在新的 `REQUIRES_NEW` 事务中整体重试，默认最多 `3` 次，退避 `50 / 150 / 300ms`。
- 重试耗尽后才进入既有受限 fallback；超过允许数量时整批 requeue。

### Side effect 可靠性

- 核心关闭事务创建 side effect outbox 失败时不再静默忽略。
- outbox 创建失败会回滚本轮主表关闭、route 关闭和 `APPLIED` 标记，保留事件等待重试。
- 远程副作用执行仍然异步，不阻塞核心闭环。

## 配置项

```yaml
alarm:
  batch:
    stopEventBatchEnabled: true
    stopEventUpsertBatchSize: 100
    insertItemProfileLogEnabled: false
    electrolyticSnapshotBatchSize: 100
    startLockRetryMaxAttempts: 3
  stop-worker:
    initialAvailableDelayMs: 0
```

压测灰度时优先测试：

```yaml
alarm:
  stop-worker:
    initialAvailableDelayMs: 200
```

## 数据库变更

`alarm_stop_event` 新增：

| 字段 | 用途 |
| --- | --- |
| `event_version bigint not null default 0` | 防止旧 worker 覆盖新 stop |
| `applied_stop_time datetime null` | 判断 `APPLIED` 后到达的 stop 是否更新 |

## 兼容与回退

- `alarm.batch.stopEventBatchEnabled=false`：回退为 listener 内逐条调用 `recordStop`。
- `alarm.stop-worker.initialAvailableDelayMs=0`：关闭 claim 初始延迟。
- `alarm.batch.electrolyticSnapshotBatchSize=500`：恢复接近旧快照批次行为。
- 数据库新增列保留即可，不需要破坏性回滚。

## 测试口径

从父工程使用 Java 8 和 UTF-8 执行：

```powershell
mvn -pl hpis-alarm -am -DfailIfNoTests=false "-Dfile.encoding=UTF-8" test
```

真实 MQ + MySQL 压测按 warm-up 和正式轮分开记录，优先验证：

- `GENERAL_ALTERNATE 20000 MQ`
- `ELECTROLYTIC_ALTERNATE 20000 MQ`
- `MIXED_ALTERNATE 20000 MQ`
- `MIXED_ALTERNATE 20000 MQ/min x 10min`
- `MIXED_ALTERNATE 50000 / 100000 MQ`
- 独立 `750000 PENDING`

## 剩余风险

- 本轮快照优化仍是同步写入止血方案。如果 ectype 快照占 start 持久化耗时达到 `15%`，或仍出现 deadlock/fallback，应进入可靠快照命令表异步拆分。
- side effect worker 的吞吐不作为核心关闭门禁，但必须监控持续堆积。
- `20000 MQ/min` 未达标时先输出拆分分析，只选择一个最大瓶颈进入下一阶段。

## 2026-06-02 真实压测结论

- Java 8 + UTF-8 focused test 通过：`65` 个测试执行，`0` 失败，`0` 错误，`2` 跳过；package 通过。
- `GENERAL / ELECTROLYTIC / MIXED ALTERNATE 20000 MQ` 三个短时正式轮均通过，核心闭环分别为 `14283ms / 23030ms / 19131ms`。
- `MIXED_ALTERNATE 20000 MQ/min x 10min` 完成 `200000 MQ` 发送，实际发送吞吐 `333.22 MQ/s`，核心关闭吞吐 `165.17 alarm/s`。
- 核心链路没有线性堆积：队列最大 `ready=5`，stop event 最大 `PENDING=281`、最大 `PROCESSING=170`，终态 `APPLIED=100000`。
- 电解槽扩展表 `45000` 条全部可按 alarmId 关联，route 终态 `CLOSED=100000`，side effect 空闲窗口最终 `DONE=55000`。
- 同步 ectype 快照仍出现 `8` 次 `PERSIST_LOCK_RETRY`；按门禁规则，本轮不进入生产化候选。
- `initialAvailableDelayMs=200` 下仍有 `1059` 批 `ROUTE_MISSING_RETRY`，涉及 `31391` 条暂不可见 route。该项作为快照异步化后的复测重点。
