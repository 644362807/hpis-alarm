# 报警 2w MQ 每分钟未达标拆分分析

## 结论

Phase A 最小优化已经完成真实 RabbitMQ + MySQL 压测，但生产门禁未通过。

核心关闭链路已经接近目标，并且持续输入期间没有出现 MQ 或 stop event 线性堆积：

- `200000 MQ / 10min` 实际发送耗时 `600211ms`，发送吞吐 `333.22 MQ/s`。
- `100000` 条报警全部关闭，真实闭环耗时 `605430ms`，关闭吞吐 `165.17 alarm/s`。
- 目标为 `>= 333.33 MQ/s` 和 `>= 166.67 alarm/s`，当前分别差 `0.11 MQ/s` 和 `1.50 alarm/s`。
- RabbitMQ 终态 `ready=0`、`unacked=0`；压测报告观测到的最大 `ready=5`。
- stop event 终态 `APPLIED=100000`，无 `PENDING/PROCESSING/FAILED`。

本轮不能作为生产化候选通过，主要原因不是 stop worker 吞吐不足，而是同步电解槽当前点位快照仍然出现 MySQL deadlock。按既定规则，下一阶段只选择一个主任务：**将电解槽当前点位快照拆为可靠异步投影**。

## 全链路耗时拆分

### Start 持久化

`BATCH_GROUP_PROFILE` 共记录 `2005` 个 suffix 内批次。已记录的 start 持久化阶段总耗时为 `95689ms`：

| 阶段 | 总耗时 | 占 start 已记录耗时 | 平均批次耗时 | P95 | Max |
| --- | ---: | ---: | ---: | ---: | ---: |

| 电解槽历史扩展表 | `6287ms` | `6.57%` | `3.14ms` | `7ms` | `52ms` |
| ectype 当前点位快照 | `10735ms` | `11.22%` | `5.35ms` | `11ms` | `214ms` |
| alarm 主表 | `12937ms` | `13.52%` | `6.45ms` | `11ms` | `52ms` |

| 补偿处理 | `44393ms` | `46.39%` | `22.14ms` | `44ms` | `270ms` |

正常批次中补偿处理耗时占比最高，需要后续继续拆分其内部 SQL；但本轮最危险的信号是同步 ectype 快照出现锁竞争，因为它会扩大核心事务尾延迟并触发整批回滚重试。

### Stop 入队

- batch listener 已把连续 stop 聚合为默认 `100` 条 multi-values upsert。
- 单次 SQL 受 `500` 条硬上限保护。
- 本轮没有逐条 fallback。
- 当前日志还没有形成 stop 入队耗时直方图，无法可靠给出其 P50/P95。这是 Profiling 缺口，应在下一轮补充 Micrometer histogram 或低频聚合日志。

### Stop Worker

- stop event 在持续输入期间最大 `PENDING=281`、最大 `PROCESSING=170`，终态全部 `APPLIED`。
- RabbitMQ 最大 `ready=5`，没有线性堆积。
- `ROUTE_MISSING_RETRY` 记录 `1059` 批，共涉及 `31391` 条暂不可见 route。
- `initialAvailableDelayMs=200` 只能缓解，未消除 start route 提交晚于 stop claim 的竞争。
- 当前没有 claim P50/P95 的直接直方图，不能用日志条数替代 claim 批量分布。

### Side Effect

- 核心闭环完成时报告为 `DONE=1243, PENDING=53757`。
- 输入停止后空闲窗口最终达到 `DONE=55000`，无持续积压。
- side effect 不阻塞核心关闭，但生产灰度必须独立监控 backlog slope 和最长等待时间。

## 异常与干扰项

| 信号 | 结果 | 说明 |
| --- | ---: | --- |
| `PERSIST_LOCK_RETRY` | `8` | ectype 同步快照 upsert 的真实锁重试 |
| `Deadlock found` 日志匹配 | `12` | 包含异常链重复打印，不等同于独立事务数 |
| `FALLBACK_SINGLE` | `0` | 有限整体重试生效，没有退化成逐条 SQL |
| `ROUTE_MISSING_RETRY` | `1059` 批 | 仍需后续调可见窗口和 claim 聚批 |
| 应用日志大小 | 约 `199MB` | MyBatis DEBUG 仍被环境配置打开，压低真实性能并污染磁盘 |
| verifier 热采样 | 存在 | 已降频完整 count，但仍会给 MySQL 和 RabbitMQ 增加额外观测负载 |

## 最大瓶颈选择

下一阶段只处理一个主任务：**拆分电解槽当前点位快照**。

理由：

1. 已出现真实 deadlock，直接违反 Phase A 生产门禁。
2. 当前点位快照属于可最终一致的投影，不应继续扩大 start 核心事务。
3. 把它移出核心事务可以缩短 start 持锁时间，并降低 route 提交延迟，从而间接减少 `ROUTE_MISSING_RETRY`。
4. `ROUTE_MISSING_RETRY`、补偿处理内部拆分和日志级别治理保留为后续验证项，不与本轮主任务并行扩张改动面。
