# 报警文档体系完善思路

## 1. 目标

本文用于完善 `hpis-alarm` 后续文档体系，目标是让后续开发、测试、评审和交接都能快速判断：

- 哪份文档是当前权威。
- 哪些文档只是历史演进。
- 哪些结论已经被验证替代。
- 哪些计划还没有实现或没有通过门禁。
- 新增文档应该放在哪里、写什么、怎么复核。

## 2. 当前文档体系问题

### 2.1 文档数量多，但状态不总是显式

`doc/` 下已有大量设计说明、压测报告、修改记录和计划文档。工单/推送目录后来通过 README 标记了权威和过时状态，这是正确做法。但其它专题还没有统一的状态标记模板。

改进方向：每个专题目录或总入口都应有状态表。

### 2.2 计划文档和完成记录容易混淆

文档标题中出现“计划”“实施计划”“最终执行计划”“验证报告”“修改记录”等类型。读者如果只看标题，容易把未执行计划当成已完成事实。

改进方向：每份文档开头必须有“文档状态”和“是否可作为实现依据”。

### 2.3 历史结论需要保留，但必须降权

压测报告和早期设计中有些结论后来被替代。删除历史会丢失演进证据，但不标记过时会误导实现。

改进方向：历史文档保留，新增过时说明和替代文档指针。

## 3. 推荐目录结构

## 4. 文档状态标签

建议统一使用以下状态：

| 状态 | 含义 |
| --- | --- |
| 当前权威 | 可作为当前实现和评审依据。 |
| 当前参考 | 可补充边界，但不能覆盖当前权威。 |
| 验证报告 | 只证明某次环境和参数下的结果，不能自动等同生产结论。 |
| 修改记录 | 记录某轮改动事实，优先级高于旧计划。 |
| 历史参考 | 只解释演进背景，不能单独作为实现依据。 |
| 部分过时 | 部分事实仍可参考，但指定字段、流程或结论已经失效。 |
| 过时 | 不能作为当前实现依据，只能用于追溯。 |

## 5. 新文档模板

### 5.1 设计文档模板

```markdown
# 标题

## 文档状态

- 状态：当前权威 / 当前参考 / 历史参考 / 过时
- 是否可作为实现依据：是 / 否 / 仅限指定章节
- 替代或被替代文档：
- 最后确认日期：

## 背景

说明为什么要做，不写泛泛描述。

## 当前结论

只写已经确认的决策。

## 不做事项

明确排除范围，尤其是旧方案不能复活的点。

## 数据模型或接口影响

说明表结构、MQ payload、push payload、配置项和外部接口是否变化。

## 风险与回滚

说明幂等、数据一致性、可观测性、灰度和回滚。

## 验收标准

写可验证条件，不写空泛目标。
```

### 5.2 修改记录模板

```markdown
# 本轮修改记录-YYYYMMDD-主题

## 背景

## 改动范围

精确到类、Mapper、配置、SQL 或文档。

## 外部入口是否变化

## 数据库结构是否变化

## MQ 和 push payload 是否兼容

## 幂等和一致性风险

## 配置开关和回滚方式

## 已执行验证

## 未覆盖风险和下一步建议
```

### 5.3 验证报告模板

```markdown
# 验证报告-YYYYMMDD-主题

## 结论

明确 PASS / FAIL / 数据正确性通过但性能门禁未过。

## 环境

Java、Nacos、RabbitMQ、MySQL、日志级别、关键配置。

## 采样口径

说明采样工具、启动空窗、是否有 verifier 负载。

## 结果

列出核心指标。

## 不采纳结果

写明哪些 run 被污染，不能作为结论。

## 后续动作

一次只选择一个最大瓶颈。
```

## 6. 两轮复核流程

每次新增或大改文档后执行两轮复核。

### 第一轮：需求符合性复核

检查：

- 是否覆盖用户要求的主题。
- 是否写清资料范围。
- 是否写清权威性判定规则。
- 是否把过时文档隔离。
- 是否列出验证或下一步动作。

### 第二轮：风险表达复核

检查：

- 是否把计划误写成已完成。
- 是否把测试候选误写成生产化完成。
- 是否把过时方案写入最终结论。
- 是否存在占位词、未完成标记或乱码。
- 是否有“可能、似乎、大概”这类不承担结论责任的措辞。
- 是否有标题过宽或误导性描述。

## 7. skills 使用思路

针对文档工作，建议按以下方式使用 skills：

- 用 brainstorming 明确文档目的、读者、输出结构和取舍。
- 用 writing-plans 拆解多文档或大文档的落地步骤。
- 用 verification-before-completion 做最终静态检查，不能在未验证时宣称完成。
- 用 requesting-code-review 的思路做文档复核，即使不调用子代理，也要按“需求符合性”和“质量风险”两轮审阅。

本次新增的反思、学习路线、面试问题和文档体系文档，就是按该思路拆分：每份文档只回答一个主要问题，避免把所有内容继续堆进主总结。

## 8. 后续维护规则

1. 新增专题目录必须有 README 或索引。
2. README 必须维护文档状态表。
3. 过时文档不直接删除，先标记替代文档和过时原因。
4. 性能报告必须写不采纳条件。
5. 工单/推送相关新文档必须显式声明是否遵守 16 号权威口径。
6. 分片相关新文档必须显式声明是否仍遵守当前月 `00..255`、下月 `00..09`、月末只创建下月 `00`。
7. stop 相关新文档必须说明是否改变 MQ ack/nack、stop event 状态机和 side effect 原子性。
8. 新增配置项必须同步 `报警运行配置说明.md`。

## 9. 完善优先级

### P0：保持工单/推送 README 状态准确

这是当前最容易误实现的区域。任何新设计都必须先更新 README 的状态表。

### P0：维护 `docs/alarm-summary` 索引

本目录已经形成交接入口，新增总结型文档必须更新索引。

### P1：为分片、压测、stop 建立状态索引

可以逐步给分片、压测、stop 相关文档增加“当前权威/历史参考/过时”状态说明。

### P1：固化验证报告模板

尤其是压测报告，必须统一记录环境、采样口径和不采纳结果。

### P2：物理归档过时文档

当团队确认不会再从旧方案实现时，可以把过时文档移动到 `archive/`。移动时必须保留 README 指针和提交说明。

## 10. 结论

alarm 文档体系后续要从“记录很多事实”升级为“持续维护权威关系”。只要权威索引、过时隔离、验证证据和两轮复核流程稳定执行，文档就能支撑接手、评审和面试，而不是成为新的噪声源。
