## 4. 当前最终结论摘要

### 4.1 总体定位

`hpis-alarm` 当前围绕三条主线演进：

- 报警事实链路：MQ start 入库、时间容量分片、内部 `alarm_id` 路由、cid hot/stale 生命周期。
- 可靠消警链路：MQ stop 先落 `alarm_stop_event`，后台 worker 批量关闭业务表和 route，side effect 异步执行。
- 配置与处置链路：报警配置控制推送过滤和推送策略；确认后可直接处理或创建工单；`alarm_handle` 只表达最终处置结果。

当前工程的核心原则是低风险渐进改造：不轻易改变 MQ ack/nack、push payload、外部入口和既有查询语义；新增能力通过配置、可靠缓冲表、批量边界和灰度开关逐步落地。

### 4.2 分片最终口径

旧的 `alarm_id % 5` 固定分片已经被时间 + 容量分片替代。当前物理表后缀为 `yyyyMM_nn`，例如：

- `alarm_202511_00`
- `alarm_handle_202511_00`
- `alarm_electrolytic_cell_202511_00`

当前月默认注册 `00..255`，下个月默认注册 `00..09`。服务启动默认只创建当前月 `00`，月末任务只物理创建下个月 `00` 并显式刷新 DataSource。动态建表后的主动刷新只是补充保险，不替代 actualDataNodes 预注册。

旧 `alarm_0..4`、`alarm_handle_0..4`、`alarm_electrolytic_cell_0..4` 不再注册、不再兜底查询。新实现依赖 `AlarmShardingDataSourceFactory` 重建 ShardingSphere DataSource，并由 `RefreshableAlarmShardingDataSource` 原子切换。

### 4.3 ID 与 cid 路由

外部 MQ `rawData.alarmId` 当前作为 `alarm_cid` 使用；内部 `alarm_id` 使用可解析编码，包含日期、slice、worker、rowNo 等信息，用于按 ID 直达分片。

`alarm_cid_index` 只服务 active/hot 生命周期，`alarm_cid_stale_index` 服务长时间未关闭报警的过渡生命周期。它们不是永久历史索引。长期历史查询应走内部 `alarm_id` 或时间范围，不应依赖 cid 快速定位。

### 4.4 MQ start 当前口径

默认单条 listener 仍保留；高峰优化推荐使用 Spring AMQP consumer batch，而不是已经清理的自研 `submitAndWait` 聚合器。

推荐灰度起点来自压测文档：

- `insertConsumerBatchEnabled=true`
- `batchSize=100`
- `receiveTimeoutMs=50`
- `concurrency=2-4`
- `prefetch=100`

batch listener 会先处理同批 start，再处理 stop/status，降低同批 stop 先执行导致 route 尚未可见的窗口。ack/nack 仍逐条执行，不使用 `multiple=true`。

### 4.5 MQ stop 当前口径

stop 消息不再同步直接关闭业务表。当前主链路是：

1. MQ stop 写入或更新 `alarm_stop_event`。
2. 落库成功后 ack MQ。
3. worker 用 `PROCESSING + lock_token` 短事务认领。
4. 按 `alarm_cid` 批量查询 hot/stale route。
5. 按 `table_suffix` 分组关闭业务表、cid route 和 stop event。
6. side effect outbox 与核心关闭事务保持原子，远程 side effect 独立执行。

route 暂不可见时不立即失败，而是延迟回到 `PENDING` 重试；达到重试上限后才转 `FAILED/ROUTE_MISSING`。历史误失败在 route 后到时仍可通过恢复扫描关闭。

### 4.6 SQL 批处理硬边界

当前统一规则是：单条 SQL、单次 JDBC batch 和单个事务内业务写批次默认不得超过 `500` 条。涉及物理分表时必须先按 `table_suffix` 分组，再在分片内切 chunk。

异常逐条降级只允许作为小批兜底，默认最多 `100` 条。超过上限时不在 MQ consumer 或 worker 线程里展开无界 N+1 SQL，而是保留重试语义。

### 4.7 电解槽快照异步投影状态

Phase A 证明核心关闭链路接近 2w MQ/min 目标，但同步写 `alarm_electrolytic_cell_ectype` 出现 MySQL deadlock。后续已实施可靠异步投影：

- 新增 `alarm_electrolytic_cell_snapshot_command`。
- start 写 `ACTIVE` 命令。
- stop 在 `alarm_id` 匹配时写 `DELETED` 命令。
- 独立 snapshot worker 按 `point_hash` 稳定排序处理。
- 灰度模式支持 `SYNC -> DUAL_WRITE -> ASYNC`。

现阶段结论要谨慎：Phase B 数据正确性通过，deadlock 和快照失败信号清零，但严格性能门禁仍未通过，不应把它描述为可直接合并 `main` 或生产化完成。下一步主任务是降低 route 可见性竞争与无效重试，并隔离 verifier 负载和 MyBatis DEBUG 日志 I/O。

### 4.8 工单与推送最终口径

当前权威文档是 `doc/报警配置工单推送改造-20260618/16-问答确认后的设计修改方案.md`。

最终表职责如下：

| 表 | 当前职责 |
| --- | --- |
| `alarm` | 报警事实表，只保存发生、状态、开始结束时间、设备、类型、租户等事实。 |
| `alarm_configure` | 报警规则配置表，承载推送开关、推送策略编码和可选工单模板。 |
| `alarm_workorder` | 报警工单事实表，一个报警最多一张工单，保存当前状态、负责人、处理结果。 |
| `alarm_handle` | 报警最终处置记录表，直接处理或工单处理完成后最多写一条有效记录。 |

明确不做：

- 不新增 `alarm.workorder_id`。
- 不新增 `alarm.alarm_configure_id`。
- 不新增 `alarm.config_version`。
- 不新增 `alarm_workorder_flow`。
- 不把 `alarm_handle` 恢复为多动作时间线表。
- 不让确认、创建工单、接单、转派、退回分别写多条 `alarm_handle`。
- 不在 `alarm_handle` 新增 `status_before/status_after`。

推送过滤最小口径是：报警仍照常入库，after-commit 推送前解析 `alarm_configure`；`push_enabled=0` 时跳过推送；`push_message_type` 有值时作为推送策略编码，空值回退 `alarm_type`；不改变旧 push payload 主结构和 `push.open` 全局开关。

## 5. 时间线演进

### 2026-04 到 2026-05：时间容量分片与内部 ID

早期核心问题是固定 `alarm_id % 5` 分片无法按时间治理历史数据，也无法处理单月数据暴涨。文档逐步形成时间 + 容量分片方案：按 `alarm_beginTime` 定位月份，月内按容量切 slice，三张绑定表使用同一 `table_suffix`。

`报警ID与容量预占设计说明.md` 进一步解决了历史时间复跑、服务重启和 ID 冲突问题：内部 `alarm_id` 不再简单依赖业务时间和本地序列，而是通过可解析编码绑定日期、slice、worker 和 rowNo。

### 2026-05-23：批量 start 方案收敛

压测对比显示旧单条 listener 可用但吞吐有限；自研 submit-and-wait 聚合功能可用但实际 batch 被 consumer 数限制，吞吐更差。最终保留旧单条 listener 和 Spring AMQP consumer batch 两条入口，清理自研聚合器。

这一阶段同时强化了协作规范：`agent.md` 要求后续修改关键业务代码时补中文风险注释，每轮修改必须新增中文修改文档，并同步运行配置、链路说明、压测文档等资料。

### 2026-05-24 到 2026-05-31：ROUTE_MISSING 与 stop 可靠化

真实 MQ + MySQL 压测暴露出 start/stop 交替场景下 `ROUTE_MISSING` 误失败：route 后续实际存在，业务表仍未闭合。后续将 route missing 从立即失败改为可重试、可恢复。

随后 stop 链路从串行 scheduled worker 演进为 `PROCESSING + lock_token` 原子认领和 stop 专用线程池。`countPending` 从热路径移除，核心批处理按小批并行执行，side effect 从核心闭环中解耦。

### 2026-05-30：SQL 批处理治理

这一阶段不是单纯提升吞吐，而是先控制风险：限制 SQL 长度、事务大小、锁等待和异常回滚成本。统一 `AlarmBatchChunker` 后，`IN`、`CASE WHEN`、多 values `INSERT`、JDBC batch 和逐条 fallback 都有硬边界。

这个约束已经进入 `agent.md`，后续任何循环 SQL 或大批量 SQL 修改都要专项检查。

### 2026-06-01 到 2026-06-02：2w MQ/min 门禁与电解槽拆分

Phase A 最小优化后，短时 20000 MQ 场景通过；10 分钟持续输入已经非常接近目标，没有 MQ 或 stop event 线性堆积。但同步电解槽当前点位快照仍出现 deadlock，成为最大阻断。

因此下一阶段只选一个主任务：把电解槽当前点位快照拆成可靠异步投影。Phase B 数据正确性通过，但严格性能门禁仍未通过，主要剩余问题变为 route 可见性重试、verifier 终态完整 count 和 MyBatis DEBUG 日志 I/O。

### 2026-06-04 到 2026-06-08：分片节点刷新与月末预热

ShardingSphere 4.1.1 的 actualDataNodes 在 DataSource 创建时固定，运行中新建表不会自动加入规则。当前方案通过重建 DataSource 并原子切换解决。

合并记录显示，分片节点刷新与月末预热已完成自动化回归、打包、本地服务启动、真实 CRUD 接口回归。当前边界是单实例设计，不覆盖多实例同时月末建表的分布式互斥。

### 2026-06-10：配置统一与链路审查

文档统一了当前生产推荐配置，明确：

- 当前月注册 `00..255`。
- 下个月注册 `00..09`。
- 月末只物理创建下个月 `00`。
- 动态建表 after-commit 防抖刷新只是补充机制。

链路审查还记录了 `/alarm/alarmAdd` 吞异常返回 HTTP 200、HTTP/direct stop 仍为兼容路径、`identify -> update_by` 历史映射风险等后续确认项。

### 2026-06-18 到 2026-07-02：配置、工单、推送口径收敛

早期工单设计经历了多轮草案，曾把 `alarm_handle` 设计成多动作时间线表。最新 README 已明确：`16-问答确认后的设计修改方案.md` 是当前权威，`15-当前最小修改范围与过时文档清理.md` 是当前参考。

最终口径收敛为：报警事实不增加工单或配置版本字段；配置表承载推送和可选工单模板；工单表只维护当前事实；`alarm_handle` 只记录最终处置结果。

## 6. 当前核心链路总结

### 6.1 start 链路

start 主线是：

```text
MQ start -> 解析消息和设备缓存 -> 分配 month/slice/rowNo -> 生成内部 alarm_id -> 设置 AlarmShardContext -> 写 alarm_handle/alarm_electrolytic_cell/alarm -> 写 hot cid route -> afterCommit push
```

batch 模式下，多个 start 会先准备 `AlarmInsertContext`，再按 suffix 批量持久化。批量失败时复用 prepared context 拆单，避免重新执行 Redis 去重和副作用组装。

### 6.2 stop 链路

stop 主线是：

```text
MQ stop -> alarm_stop_event upsert -> ack -> worker claim -> route 批量查询 -> 按 suffix 关闭业务表和 route -> APPLIED -> side effect
```

该设计把 MQ 消费与最终业务关闭解耦，只要 stop event 可靠落库，后续 worker 就可以重试、恢复或人工排查。

### 6.3 route 与历史查询

cid route 是短生命周期索引，不是历史总索引。active/hot 和 stale route 用于关闭未结束报警；关闭并过期后会被清理。历史查询必须转向内部 `alarm_id` 或时间范围。

### 6.4 side effect

设备恢复、电解槽扩展清理、推送等 side effect 不应阻塞核心 `alarm_endTime` 闭环。当前原则是 side effect event 可靠落库，远程执行异步处理；如果 outbox 本身创建失败，核心关闭事务必须回滚，交给 stop event 后续重试。

### 6.5 工单闭环

工单闭环遵循一警一单和最终处置记录：

```text
报警确认 -> 直接处理或按配置创建工单 -> 工单只维护当前状态和负责人 -> 工单完成或关闭 -> 写一条最终处置型 alarm_handle
```

确认、创建工单、接单、转派、退回都不是最终处置，不写多条 `alarm_handle`。

## 8. 风险与边界

### 8.1 分片与 DataSource

- 当前方案依赖 actualDataNodes 预注册和 DataSource 重建刷新，不能期待 ShardingSphere 4.1.1 自动发现新表。
- 当前多实例月末建表没有分布式锁，仅按单实例运行设计。
- 当前月注册 `00..255`，但物理表不一定都已创建；列表分页必须携带可识别时间范围，避免广播到未物理创建节点。

### 8.2 MQ 顺序与幂等

- Rabbit 并发下同一 `alarmCid` 不保证严格顺序。
- batch listener 通过“同批 start 先持久化，再处理 stop/status”降低误判窗口，但不是严格串行锁。
- DB commit 成功但 ack 前宕机仍依赖 RabbitMQ 重投和业务幂等兜底。

### 8.3 stop 最终一致性

- stop 允许秒级最终一致，但最终必须写入 `alarm_endTime`。
- `ROUTE_MISSING_RETRY` 仍是主要治理对象之一。
- side effect 可以延迟，但 outbox 创建失败必须回滚核心关闭，不能产生“业务已关闭但副作用事件永久丢失”的状态。

### 8.4 压测结论

- 早期部分压测受 verifier 启动空窗、Windows class lock、MyBatis DEBUG 日志 I/O、Nacos 旧配置影响，不能直接作为真实性能结论。
- 后续性能结论应只采纳 orchestrator 生成、`True closed-loop elapsed ms != -1`、最终状态通过的 run。
- Phase B 数据正确性已通过，但严格性能门禁未通过，仍是测试候选，不是生产化完成状态。

### 8.5 配置风险

- 本地 `bootstrap.yml` 只负责连接 Nacos；真实运行配置通常来自 Nacos。
- `alarm.profile.*` 当前无读取入口，属于无效配置或历史压测残留。
- 生产必须同步当前推荐短横线配置，清理旧 `preCreateMonths: 2`、`includeLegacyTables: true`、MyBatis DEBUG 等旧基线。

### 8.6 工单追溯风险

当前最小方案不保存 `alarm.alarm_configure_id` 和 `config_version`，也不保存完整工单流转历史。这降低了改动面，但会削弱“当时为什么推送、为什么能建单、转派历史如何变化”的审计能力。后续如需要审计，应另设配置快照或工单流转表，而不是把 `alarm_handle` 重新扩展为过程表。

## 9. 改进思考和优先级

### P0：防止错误文档影响实现

- 保持 `报警配置工单推送改造-20260618/README.md` 为目录权威索引。
- 后续新增工单/推送相关文档时，必须在 README 中标记状态。
- 不再引用 10、11、12、13、14 号文档作为实施依据。

### P0：继续治理 route 可见性竞争

Phase B 的主要剩余问题是 `ROUTE_MISSING_RETRY`。建议下一轮只聚焦：

- stop 首次可见延迟与 claim 节奏。
- start route 提交与 stop claim 的时间窗。
- verifier 终态完整 count 对 MySQL 的额外负载。
- 关闭 MyBatis DEBUG 后重新执行相同门禁。

### P1：完善观测指标

当前多处仍依赖日志或阶段性 profile。建议补齐：

- stop 入队耗时 P50/P95。
- stop worker claim P50/P95。
- route missing 最长等待时间。
- side effect backlog slope 和最长等待时间。
- snapshot command 状态数量、最长等待、superseded 次数。

### P1：工单审计能力单独评审

当前最小工单方案不保留完整流转历史，这是明确选择。若后续业务需要审计转派、退回、催办，应新增独立工单流转表或审计表，不应复活旧 `alarm_handle` 多动作时间线方案。

### P1：多实例运行准备

当前分片月末预热、worker claim、side effect worker 等多处按单实例或待专项灰度描述。多实例部署前至少要评审：

- 月末建表互斥。
- `worker-id` 唯一性。
- side effect 认领隔离。
- snapshot worker 多实例 token/version 竞争。

### P2：文档治理

建议后续保留两层文档：

- 当前权威索引：只指向可执行口径、当前参考和过时隔离说明。
- 历史归档目录：保留旧草案，但文件名或目录明确带 `archive` 或 `obsolete`，避免误读。

### P2：配置中心治理

生产 Nacos 应与 `报警运行配置说明.md` 对齐。尤其是：

- `alarm.sharding.pre-create-months=0`
- `alarm.sharding.include-legacy-tables=false`
- `alarm.sharding.actual-data-nodes.current-month-max-slice-no=255`
- `alarm.sharding.actual-data-nodes.next-month-max-slice-no=9`
- `alarm.sharding.rule-refresh.month-end-pre-create-check-last-day=true`
- 关闭 MyBatis DEBUG 和无效 profiling 配置。
