# 报警模块面试问题清单

## 1. 使用方式

本文用于面试、交接验收或内部培训，不用于替代设计文档。问题按难度分为基础、进阶和高阶。建议先让候选人画链路，再追问异常、幂等、回滚和观测。

参考答案采用当前权威口径。过时方案只能作为反例讨论，不能作为正确答案。

## 2. 基础题

### 2.1 alarm 模块当前解决哪些核心问题？

参考答案：

- start 高吞吐写入。
- stop 可靠闭环。
- 时间 + 容量分片。
- cid hot/stale 生命周期路由。
- side effect 最终一致。
- 报警配置推送过滤和一警一单。

追问：

- 哪些链路是同步主事务。
- 哪些链路允许最终一致。

### 2.2 为什么旧 `alarm_id % 5` 分片被替换？

参考答案：

旧规则无法按时间治理历史数据，也无法在单月数据暴涨时继续扩容。当前使用 `yyyyMM_nn` 时间 + 容量分片，按 `alarm_beginTime` 定位月份，月内按容量切 slice。

追问：

- `nn` 从哪里来。
- 三张绑定表为什么必须同 suffix。

### 2.3 外部 alarmId 和内部 alarm_id 有什么区别？

参考答案：

外部 MQ `rawData.alarmId` 当前作为 `alarm_cid` 使用；内部 `alarm_id` 是可解析 ID，包含日期、slice、worker、rowNo 等信息，用于直达分片。

追问：

- 为什么不能只依赖外部 alarmId。
- 内部 alarm_id 对查询有什么价值。

### 2.4 cid route 是永久历史索引吗？

参考答案：

不是。`alarm_cid_index` 和 `alarm_cid_stale_index` 只服务 active/hot/stale 生命周期。长期历史应走内部 `alarm_id` 或时间范围。

追问：

- route 被清理后如何查历史。
- 为什么不保留永久 cid 索引。

## 3. MQ 与一致性题

### 3.1 MQ stop 为什么落 `alarm_stop_event` 成功后就 ack？

参考答案：

stop event 是可靠意图缓冲。只要落库成功，后续 worker 可以重试、恢复或人工排查，不需要 MQ 一直持有未确认消息。这样可以避免业务关闭慢、线程池满或 side effect 失败导致 stop 丢失。

追问：

- stop event 落库失败时怎么处理。
- worker 挂掉后如何恢复。

### 3.2 batch listener 为什么先处理同批 start，再处理 stop/status？

参考答案：

这样可以让同批 start 先写业务表和 hot route，降低 stop 先执行导致 `ROUTE_MISSING` 误判的窗口。但这不是严格同 cid 串行保证，只是降低竞争概率。

追问：

- Rabbit 并发下同一 alarmCid 是否严格有序。
- route missing 当前如何处理。

### 3.3 start 批量失败后为什么要复用 prepared context？

参考答案：

prepare 阶段可能已经做了 Redis 去重、设备解析和副作用上下文组装。批量失败后如果重新 prepare，可能错误释放或重复获取 Redis key，也可能重复触发副作用。复用 prepared context 可以保持幂等边界。

追问：

- 哪些失败可以拆单兜底。
- 逐条兜底为什么必须有上限。

### 3.4 DB commit 成功但 MQ ack 前宕机怎么办？

参考答案：

RabbitMQ 会重投消息，系统依赖业务幂等和 `alarmCid` 去重兜底。这个场景要求 start 入库链路和 route 写入不能因为重投产生不可控重复。

追问：

- 哪些字段或约束帮助幂等。
- 这个风险在灰度前应该如何验证。

## 4. stop worker 与 SQL 题

### 4.1 `PROCESSING + lock_token` 解决什么问题？

参考答案：

它把可处理事件短事务认领给某个 worker 批次。后续提交结果时必须匹配同一个 token，避免多个 worker 重复处理或旧线程覆盖新状态。

追问：

- token 丢失或超时如何处理。
- 多实例下还需要关注什么。

### 4.2 route missing 为什么不能立即标记失败？

参考答案：

高并发下 stop 可能先于 start route 提交。立即失败会留下业务报警未关闭。当前策略是延迟回到 `PENDING` 重试，达到上限后才 `FAILED/ROUTE_MISSING`，并保留恢复扫描。

追问：

- 怎么避免无限重试。
- 历史误失败如何恢复。

### 4.3 为什么批量 SQL 要有 `500` 硬上限？

参考答案：

为了控制 SQL 长度、参数数量、事务时长、锁等待、redo/undo 压力和失败回滚成本。吞吐不应通过无界超大 SQL 获得，而应通过小批并发和可重试 worker 提升。

追问：

- 分片表场景为什么要先按 suffix 分组。
- 异常逐条 fallback 的默认上限是多少。

### 4.4 side effect 失败是否回滚核心消警？

参考答案：

远程 side effect 执行失败不回滚已经可靠完成的核心消警。但 side effect outbox 创建失败必须回滚核心关闭事务，因为否则会产生业务已关闭但副作用意图永久丢失的状态。

追问：

- side effect backlog 如何监控。
- 多实例 side effect worker 需要什么隔离。

## 5. 分片与配置题

### 5.1 ShardingSphere 4.1.1 会自动感知新表吗？

参考答案：

不会。actualDataNodes 在 DataSource 创建时固定。运行中新建物理表后，需要重建 ShardingSphere DataSource，并通过 `RefreshableAlarmShardingDataSource` 原子切换。

追问：

- 创建新 DataSource 失败怎么办。
- 旧 DataSource 为什么要延迟关闭。

### 5.2 当前月和下个月 actualDataNodes 如何注册？

参考答案：

当前月默认注册 `00..255`，下个月默认注册 `00..09`。服务启动默认只物理创建当前月 `00`，月末任务只创建下个月 `00` 并刷新 DataSource。

追问：

- 为什么注册节点和物理创建节点不完全一致。
- 列表分页为什么必须带时间范围。

### 5.3 `alarm.profile.*` 当前有效吗？

参考答案：

当前代码没有读取入口，属于无效配置或历史压测残留。不能把它当作当前运行配置依据。

追问：

- 哪些 `alarm.*` 配置是有效绑定。
- 生产 Nacos 为什么要清理旧配置。

## 6. 电解槽异步投影题

### 6.1 为什么要拆分电解槽当前点位快照？

参考答案：

Phase A 压测显示同步 upsert `alarm_electrolytic_cell_ectype` 出现 MySQL deadlock。该表表达当前点位快照，不是报警历史事实，允许最终一致，因此适合拆为可靠异步投影。

追问：

- 哪些数据仍留在 start 核心事务内。
- 为什么不能直接扩大 MQ consumer 并发。

### 6.2 `ACTIVE` 和 `DELETED` 命令如何保证不误删？

参考答案：

start 写 `ACTIVE` 命令，stop 仅在命令当前 `alarm_id` 与 stop 对应报警一致时写 `DELETED`。旧 stop 晚到时不得删除新 start 已覆盖的点位。

追问：

- 为什么要用 `point_hash`。
- `version` 和 `lock_token` 分别防什么。

### 6.3 为什么 Phase B 不能视为生产化完成？

参考答案：

没有。Phase B 数据正确性通过，deadlock 和快照失败信号清零，但严格性能门禁未通过，因此仍是测试候选。下一阶段要治理 route 可见性竞争、verifier 测量负载和 MyBatis DEBUG 日志 I/O。

追问：

- 哪些指标没有达标。
- 为什么不能继续放大 50000/100000 MQ 测试。

## 7. 工单与推送题

### 7.1 当前工单/推送权威文档是哪份？

参考答案：

`doc/报警配置工单推送改造-20260618/16-问答确认后的设计修改方案.md` 是当前权威，`15-当前最小修改范围与过时文档清理.md` 是当前参考，README 负责索引和标记过时状态。

追问：

- 10 到 14 号文档为什么不能作为实现依据。
- 07 号文档哪里部分过时。

### 7.2 `alarm_handle` 当前是什么表？

参考答案：

它是报警最终处置记录表，不是多动作时间线表。直接处理或工单完成后最多写一条有效最终处置记录。

追问：

- 确认报警是否写 handle。
- 创建工单是否写 handle。
- 工单转派是否写 handle。

### 7.3 为什么不在 `alarm` 新增 `workorder_id`？

参考答案：

`alarm` 是报警事实表，应避免混入工单当前事实。工单事实放 `alarm_workorder`，通过 `alarm_id` 建立一警一单关系。

追问：

- 一警一单由什么兜底。
- 历史报警列表如何关联工单信息。

### 7.4 推送过滤是否影响报警入库？

参考答案：

不影响。报警照常入库，after-commit 推送前解析配置。`push_enabled=0` 只跳过推送；`push_message_type` 控制推送策略编码，空值回退 `alarm_type`。

追问：

- `push.open` 全局开关是否保留。
- 是否改变旧 push payload 主结构。

## 8. 高阶设计题

### 8.1 如果要支持完整工单流转历史，你会怎么设计？

参考答案要点：

- 不复活旧 `alarm_handle` 多动作时间线方案。
- 新增独立 `alarm_workorder_flow` 或审计表。
- `alarm_workorder` 保持当前事实。
- `alarm_handle` 继续只保存最终处置结果。
- 明确写入时机、幂等键、查询接口和数据保留策略。

### 8.2 如果要多实例部署 alarm，你会先评审什么？

参考答案要点：

- `alarm.sharding.id.worker-id` 唯一性。
- 月末建表分布式互斥。
- stop worker claim 锁竞争。
- side effect worker 多实例认领隔离。
- snapshot worker token/version 竞争。
- Nacos 配置一致性和灰度顺序。

### 8.3 如果 2w MQ/min 仍未达标，你如何定位？

参考答案要点：

- 先确认环境：Java 8、UTF-8、Nacos 候选配置、MyBatis DEBUG 关闭。
- 区分发送吞吐、队列 ready/unacked、start 持久化、stop upsert、stop worker、side effect、snapshot worker。
- 只采纳 orchestrator 生成且 `True closed-loop elapsed ms != -1` 的 run。
- 不并行扩大多个改动面，一次只治理一个最大瓶颈。

### 8.4 如何判断一个文档是否可以作为实现依据？

参考答案要点：

- 是否被 README 标记为当前权威或当前参考。
- 是否比冲突文档更新。
- 是否有对应实现和测试结果。
- 是否被后续文档标记过时。
- 是否只是计划而非完成记录。
