# 报警文档复盘反思与改进思考

## 1. 复盘目的

本文从 `hpis-alarm` 现有文档中提炼工程反思和改进思考，重点回答三个问题：

1. 这批文档暴露了哪些系统演进规律。
2. 哪些设计决策值得保留，哪些做法需要警惕。
3. 后续继续改 alarm 时，应该怎样降低风险。

本文不重新定义最终口径。最终口径仍以 `报警全量文档总结与改进思考-20260704.md` 和其中标记的当前权威文档为准。

## 2. 总体反思

alarm 模块的复杂度不是来自单个接口，而是来自多条链路同时存在：

- MQ start 要高吞吐写入。
- MQ stop 要可靠闭环。
- 分片要支持历史治理和容量扩展。
- cid route 要服务 active/hot 生命周期。
- side effect 要最终一致。
- 推送和工单要避免污染报警事实。

早期文档的问题不是“没有设计”，而是设计演进速度快于权威索引维护速度。结果是后续读者会同时看到旧方案、修正方案、测试报告、变更记录和最终计划，如果没有明确的权威规则，很容易把历史草案当成当前结论。

最有价值的经验是：复杂系统的文档不能只记录“做了什么”，还必须记录“哪些旧结论已经失效”和“为什么不能再按旧方案实现”。

## 3. 值得保留的设计思想

### 3.1 报警事实和过程动作分离

当前工单方案明确 `alarm` 只保存报警事实，`alarm_handle` 只保存最终处置结果，工单当前事实放 `alarm_workorder`。这避免了把确认、转派、退回、工单同步等过程动作都塞进同一张表。

这类分离值得保留。事实表越稳定，分片、历史查询、stop 闭环和数据迁移的风险越低。

### 3.2 stop 先可靠落库，再异步关闭

MQ stop 不再同步关闭业务表，而是先落 `alarm_stop_event`。这个设计把 MQ 消费成功和业务最终闭环解耦，避免高峰期因线程池、远程调用或副作用失败导致 stop 丢失。

该思路适合所有高流量、可最终一致的链路：先把意图可靠落库，再用可重试 worker 完成后续动作。

### 3.3 小批次、可重试、可观测

SQL 批处理统一限制在 `500`，异常逐条兜底默认不超过 `100`。这个约束表面上牺牲了单次吞吐，但换来了更可控的锁等待、事务时长和失败回滚成本。

高流量系统不能依赖超大 SQL 硬顶吞吐。更稳的路线是固定小批、并发认领、失败可恢复、指标可观测。

### 3.4 过时文档不删除，但必须隔离

保留历史文档有价值，可以解释为什么某些设计被废弃。但保留不等于继续有效。当前 README 标记过时文档的方式是正确方向：让历史可追溯，同时阻断误实现。

后续所有专题目录都应该有同类 README，明确“当前权威、当前参考、历史参考、过时”。

## 4. 暴露出的主要问题

### 4.1 文档权威层级不够早建立

工单/推送目录出现多个“最终设计”“详细设计”“执行计划”，后续又被 15、16 号文档修正。如果没有 README 的当前权威说明，读者很难判断哪份能执行。

反思：每个专题一开始就需要权威索引。哪怕只有两份文档，也要标记当前状态。

### 4.2 性能结论容易被测试环境污染

压测文档多次记录 verifier 启动空窗、Windows class lock、Nacos 旧配置、MyBatis DEBUG 日志 I/O 对结论的影响。这说明性能结论必须包含采样口径、环境条件和不采纳条件。

反思：任何性能数字如果没有说明采样边界，就不能作为生产决策依据。

### 4.3 计划、实现、验证三者容易混在一起

部分文档是实施计划，部分是修改记录，部分是验证报告。读者如果只看标题，可能把“计划要做”误解为“已经完成”。

反思：文档标题和开头必须明确状态，例如“计划中”“已实现”“验证通过”“门禁未通过”“过时方案”。

### 4.4 最小改动会带来审计能力缺口

当前工单方案不保存 `alarm_configure_id`、`config_version` 和完整流转历史，这是低风险选择。但它也明确削弱了后续追溯“当时为什么推送、为什么建单、谁转派过”的能力。

反思：低风险最小改动不是无代价。文档必须把被放弃的能力写清楚，避免后续误以为系统已经支持。

## 5. 后续改进原则

### 5.1 先定事实边界，再定扩展表

涉及报警、工单、推送、处理记录时，先判断字段属于：

- 报警事实。
- 当前状态。
- 过程动作。
- 审计追溯。
- 派生投影。

不同类型不要混表。事实字段进入事实表，过程动作进入流水或审计表，投影进入可重建表。

### 5.2 任何异步链路都要回答四个问题

新增 worker、outbox、MQ consumer 或异步投影时，必须写清：

1. 意图是否可靠落库。
2. 重复执行是否幂等。
3. 失败后谁来重试。
4. 如何观测 backlog 和最长等待时间。

不能只写“异步处理”，否则风险会从主事务转移到不可见的后台队列。

### 5.3 性能门禁必须带不采纳条件

压测报告除了写 PASS/FAIL，还要写清哪些结果不采纳：

- verifier 启动空窗过大。
- 环境日志级别污染。
- Nacos 配置不是候选配置。
- 队列或数据库存在历史脏数据。
- 手工中断或 Windows 文件锁影响运行。

这比单纯记录数字更重要。

### 5.4 文档复核至少两轮

第一轮复核需求覆盖：范围、章节、权威规则、过时隔离、资料索引。

第二轮复核风险表达：是否误把计划写成已完成，是否把过时文档写进最终结论，是否有模糊词、占位词和乱码。

alarm 文档已经证明，两轮复核可以及时发现“表述过宽”和“标题误导”这类问题。

## 6. 面向后续开发的行动建议

1. 改 alarm 前先读权威索引，不直接从某个历史计划开始实现。
2. 新增配置必须同步运行配置说明，写清默认值、非法值兜底、生产风险和回滚方式。
3. 新增批量 SQL 必须说明 chunk 上限、分片分组方式和异常降级上限。
4. 新增 worker 必须说明线程归属、token/lock、超时回收和多实例边界。
5. 新增工单或推送能力时，不复活旧 `alarm_handle` 多动作时间线方案。
6. 每轮修改文档必须说明外部入口、数据库结构、MQ payload、push payload、幂等和数据一致性是否变化。

## 7. 复盘结论

`hpis-alarm` 的文档价值不只在于记录实现细节，更在于记录系统如何从“能跑”逐步走向“可恢复、可观测、可灰度、可交接”。

后续最需要坚持的不是一次性写更多文档，而是让每份文档都有明确状态、明确权威关系、明确验证证据和明确过时边界。
